# 第1章：Introduction（引言）

## 章节概述

本章是《The Data Model Resource Book》（第二版）的引言部分，阐述了通用数据模型（Universal Data Models）的核心理念：企业大约75%的数据模型是通用的、可复用的，仅约25%是组织特有的。作者主张通过建立可复用的通用数据模型库，帮助数据建模人员避免“重复造轮子”，从而大幅节省系统开发的时间和成本，并实现企业级的集成化信息架构。本章还详细介绍了全书使用的图例约定、命名规范和CD-ROM配套资源。

## 核心问题（Problems）

- **重复建模浪费严重**：大多数数据建模工作都在重复创建其他组织早已完成的数据建模结构。大约75%的企业数据模型是通用的，但每个组织都在从零开始建设。
- **系统孤立导致数据冗余**：企业中的各个系统（客户管理、销售订单、项目管理、会计、预算、采购、人力资源等）往往独立建设，各自维护一套独立的信息池，导致同一类信息（客户、员工、产品、地理位置等）在数十个系统中冗余存储。
- **数据准确性和一致性无法保证**：当同一信息存储在多个系统中时，无法确定哪个来源是最新、最准确的。这对数据质量造成严重影响。
- **缺乏集成视图**：企业无法获得人员、组织、产品或库存的完整全貌，各部门之间信息割裂，客户服务、销售、采购和会计部门无法共享集成信息。
- **企业级数据建模（Corporate Data Modeling）失败率高**：虽然行业认识到集成设计的必要性，但构建企业数据模型耗时巨大、资源消耗惊人，实施成功率很低。
- **CASE工具未能解决根本问题**：计算机辅助系统工程（CASE）工具虽然能辅助文档化，但并不能缩短开发优秀企业模型所需的时间。
- **数据仓库方案存在固有缺陷**：数据仓库从多个不一致的源系统中提取数据，如果不同部门使用不同的转换算法和源系统（如一个部门用订单系统，另一个用发票系统），会加剧数据不一致的问题，导致高层管理者看到相互矛盾的结果，进而质疑所有信息的可信度。
- **缺少可参考的通用数据模型库**：虽然有大量关于如何���模的出版物，但很少有已发布的数据模型示例汇编可供参考和验证。
- **缺乏从逻辑模型到物理实现的全流程指导**：多数数据建模书籍仅关注技术和方法论，缺少从逻辑模型到数据仓库设计再到物理数据库实现的完整实例指导。

## 解决方案（Solutions）

- **构建通用数据模型库**：提供跨行业、跨组织通用的标准数据模型模板，让企业可以在现有模型基础上进行定制和优化，而非从零开始。这些模型可作为新系统开发的起点，也可用于验证已有数据模型。
- **采用整体化（Holistic）系统开发视角**：将企业的系统视为一个互联的整体，通过建立企业级数据框架（Enterprise-Wide Framework）来维护企业最有价值的资产——信息。共享的信息架构能让各系统更有效地协同工作。
- **以数据仓库为迁移路径**：数据仓库的转换过程可以帮助识别操作环境中存在的数据不一致和冗余问题，关键是利用这些信息逐步迁移到更集成的数据结构。数据仓库方案本身不应被放弃，而应与集成化数据结构相结合。
- **提供多样化模型覆盖**：本书不仅提供逻辑数据模型（第2-9章，规范化设计，不含派生属性），还提供数据仓库设计模型（第10-14章）以及详细的数据仓库星型模式。从逻辑模型到企业数据仓库再到部门数据集市都有覆盖。
- **第二版大幅增强**：在初版基础上新增了大量模型，包括Party角色与关系、产品特征、订单调整、装运单据、工作成果、发票支付、预算场景、员工福利与绩效等人力资源模型、以及库存管理、采购订单、装运、工作投入和财务分析等星型模式。
- **提供灵活的模型设计**：在不依赖特定企业场景的数据建模决策中，选择最灵活的数据建模方案，以适配尽可能多的企业需求。
- **区分逻辑模型与物理设计**：逻辑数据模型是规范化的（可需反规范化以适应物理数据库），不包含派生属性；数据仓库模型代表实际的物理数据库设计。
- **提供完整的实施方法指导**：第15章详细说明了如何将通用数据模型用于构建企业数据模型、逻辑数据模型和物理数据库设计，包含定制化示例和多种物理设计选项。
- **配套CD-ROM资源**：提供SQL脚本（支持多种数据库平台），可直接运行后通过反向工程导入到主流CASE工具中，大幅节省部署时间。

## 关键数据模型/概念

### 建模概念与术语

- **Entity（实体）**：企业需要存储信息的、具有重要意义的对象。书中用大写字母表示（如ORDER）。命名约定：使用有意义的单数名词，分类实体添加TYPE后缀（如ORDER TYPE）。
- **Subtype（子类型）和Supertype（超类型）**：子类型是更通用实体的分类，会继承超类型的属性和关系（如LEGAL ORGANIZATION和INFORMAL ORGANIZATION是ORGANIZATION的子类型）。超类型可以有多层级嵌套。
- **非互斥子类型集合（Non-Mutually Exclusive Subtypes）**：一个超类型可以按多种不同维度进行子类型划分。如一个REQUIREMENT可以既是CUSTOMER REQUIREMENT又是PRODUCT REQUIREMENT。书中用无名称的方框区分不同维度的子类型集合。
- **Attribute（属性）**：保存实体特定信息的字段。书中用粗体小写表示。标记约定：
  - `#` — 主键（Primary Key）属性
  - `*` — 必填（Mandatory）属性
  - `o` — 可选（Optional）属性
- **属性命名约定**：
  - `ID` — 系统生成的顺序唯一数字标识
  - `Seqid` — 父ID内的序列号
  - `Code` — 用户定义的唯一助记码（可含有意义信息）
  - `Name` — 专有名称
  - `Description` — 唯一编码的描述值
  - `Flag` 或 `Ind` — 二元选择值（是/否）
  - `from date` — 日期范围的起始日期（包含当天）
  - `thru date` — 日期范围的结束日期（包含当天）
- **Relationship（关系）**：定义两个实体之间的关联方式。每个关系有两个方向的关系名，读作完整语句格式："Each ENTITY {must be/may be} relationship name {one and only one/one or more} ENTITY."
- **关系的可选性（Optionality）**：虚线表示可选关系，实线表示必填关系。
- **关系的基数（Cardinality）**：
  - 一对多（One-to-Many）：crowsfoot在“多”的一侧
  - 一对一（One-to-One）：两端均无crowsfoot
  - 多对多（Many-to-Many）：两端均有crowsfoot
- **Foreign Key（外键）**：另一实体主键在当前实体中的存在。书中不在实体属性中显式列出外键（视为冗余），而是通过关系本身来标识。
- **Foreign Key Inheritance（外键继承）**：用波浪线（~）关系线表示被继承的外键是子实体主键的组成部分。这是一种简写记法，结合#标记属性和~标记关系可完整表达复合主键。
- **Intersection/Association Entity（交叉/关联实体）**：用于解析多对多关系，通常会继承所引用各实体的键。如PARTY CONTACT MECHANISM解析了PARTY和CONTACT MECHANISM之间的多对多关系。
- **Exclusive Arc（排他弧）**：用弧线穿过两个或多个关系线，表示一个实体与多个其他实体相关，但每次仅能存在其中一种关系。如INVENTORY ITEM要么位于FACILITY要么位于CONTAINER，但不能同时。
- **Recursive Relationship（递归关系）**：实体与自身的关系，可以是一对多递归或多对多递归（需交叉实体解析）。如WORK EFFORT可递归地分解为多个子工作，或表达工作之间的依赖关系。
- **TYPE实体**：即使通常只有ID和描述，也会在图中包含，用于展示允许值域或查找表。

### 图例与表格约定

- 实体用圆角矩形表示
- 子类型用实体内的嵌套矩形表示
- 交叉实体总是用~线连接引用实体
- crowsfoot一般指向左上方，保持可读一致性
- 物理模型图示中，方框代表表（Table），字段名为列（Column）
- 多卷引用格式：`Vx:Figure x.x`（V1表示卷一，V2表示卷二）

## 结论/要点

1. **不要重复造轮子**：企业75%的数据模型是通用的，直接使用通用数据模型模板可大幅节省时间和成本。
2. **集成优于孤立**：独立建设的系统导致数据冗余和不一致，整体化、集成化的数据架构是企业核心竞争力的基础设施。
3. **数据仓库不是万能解药**：若底层的源数据本身就不一致，数据仓库只会放大问题。正确做法是将数据仓库的转换过程作为发现不一致的工具，并以此驱动操作系统的集成化改造。
4. **本书是工具箱而非教义**：本书不教授数据建模方法论，而是提供可直接使用、定制和验证的模型构件（building blocks），读者应在其基础上进行企业特定的定制。
5. **模型是起点，不是终点**：所有提供的模型都需要根据具体企业的详细需求进行修改和定制，数据仓库模型尤其依赖于具体业务需求。
6. **CD-ROM大幅加速实施**：配套的SQL脚本可快速部署模型到多种数据库平台，并可反向工程导入CASE工具进行定制。
7. **全书覆盖从逻辑到物理的完整链路**：从规范化的逻辑数据模型，到企业数据仓库，再到部门数据集市和物理数据库设计，提供了完整的端到端指导。
