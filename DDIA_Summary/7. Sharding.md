# 第7章 Sharding（分片）——问题与解决方案总结

---

# 1. 单机无法承载不断增长的数据量和写入流量

## 问题

当系统规模持续增长时：

- 单机存储容量不足
- 单机写入吞吐达到瓶颈
- CPU与内存资源耗尽
- 无法继续通过升级硬件解决问题

即：

```text
数据量 ↑
请求量 ↑

↓

单机成为瓶颈
```

## 解决方案

采用 Sharding（分片）。

将数据拆分为多个独立Shard，每个Shard存放部分数据。

```text
Node1 -> Shard1
Node2 -> Shard2
Node3 -> Shard3
Node4 -> Shard4
```

实现：

- 水平扩展（Scale Out）
- 并行写入
- 并行查询
- 分散存储压力

---

# 2. 分片后数据分布不均（Data Skew）

## 问题

不同Shard数据量不均：

```text
Shard1 = 500GB
Shard2 = 20GB
Shard3 = 15GB
```

结果：

- 个别节点成为瓶颈
- 大量节点闲置
- 无法获得线性扩展收益

## 解决方案

选择合理的分片键（Partition Key）：

```text
Partition Key
  ↓
均匀映射到Shard
```

目标：

- 数据均匀分布
- 请求均匀分布

---

# 3. 热点分片（Hot Shard）

## 问题

某个Shard承担绝大部分流量。

```text
Shard1
  ↑
 90% 流量

Shard2
Shard3
Shard4
几乎空闲
```

例如：

- 当前月份所有订单
- 当前时间窗口数据
- 爆款商品

## 解决方案

### 方案1：Hash Sharding

```text
hash(key)
    ↓
均匀散列
```

使请求分布更均衡。

---

### 方案2：自动拆分热点Shard

```text
Hot Shard

↓

ShardA + ShardB
```

将热点负载拆散。

---

### 方案3：独立部署热点Key

```text
Celebrity User

↓

Dedicated Shard
```

单独占用资源。

---

# 4. 热点Key（Hot Key）

## 问题

某个Key流量极大。

例如：

```text
user:justin_bieber
```

大量读写集中到同一节点。

## 解决方案

随机前缀（Key Salting）

原Key：

```text
user123
```

变为：

```text
01_user123
32_user123
87_user123
```

写入分散到多个Shard。

---

## 代价

读取时必须：

```text
读取100个Key
        ↓
合并结果
```

因此：

- 写入更快
- 查询更复杂

---

# 5. Key Range Sharding中的热点问题

## 问题

按时间范围分片：

```text
2025-01
2025-02
2025-03
...
```

实时写入时：

```text
全部进入当前月份
```

产生热点Shard。

## 解决方案

组合Key设计：

```text
sensorId + timestamp
```

例如：

```text
A_20250101
B_20250101
C_20250101
```

写入被分散。

---

## 代价

查询：

```text
查最近一天数据
```

必须：

```text
查询多个sensor
再聚合
```

---

# 6. Shard扩容与缩容问题

## 问题

新增节点后：

```text
Node1
Node2
Node3

↓

Node1
Node2
Node3
Node4
```

数据需要重新均衡。

## 解决方案

Rebalancing（重平衡）

目标：

```text
数据均匀
负载均匀
```

实现方式：

- Split（拆分）
- Merge（合并）
- Move（迁移）

---

# 7. Key Range Sharding的扩容问题

## 问题

某Shard不断增长：

```text
A-M
```

越来越大。

## 解决方案

Shard Split

```text
A-M

↓

A-G
H-M
```

继续扩容：

```text
A-C
D-G
H-K
L-M
```

---

## 代价

拆分过程需要：

- 重写数据文件
- 网络传输
- 额外IO

可能加剧热点。

---

# 8. Hash取模分片（Hash Mod N）扩容问题

## 问题

最简单方案：

```text
hash(key) % N
```

例如：

```text
hash(key)%3
```

新增节点：

```text
hash(key)%4
```

结果：

```text
绝大多数Key重新映射
```

导致海量数据搬迁。

---

## 解决方案

不要直接使用：

```text
hash(key)%node_count
```

改用：

- Fixed Shard
- Consistent Hash

---

# 9. Fixed Shard方案问题

## 问题

预先创建：

```text
1000个Shard
```

但：

```text
未来规模未知
```

可能：

### Shard太少

```text
节点数 > Shard数
```

无法继续扩容。

### Shard太多

产生大量元数据开销。

---

## 解决方案

提前规划合理数量。

例如：

```text
1000
2048
4096
```

支持未来扩容。

---

## 代价

数量错了：

```text
Resharding
```

代价极高。

---

# 10. Hash Range Sharding的问题

## 问题

Hash后：

```text
相邻Key
```

被打散到：

```text
多个Shard
```

导致：

```text
Range Query失效
```

无法高效执行：

```sql
where create_time between ...
```

---

## 解决方案

适用于：

- Tenant ID
- User ID
- UUID

等随机查询场景。

---

## 代价

牺牲范围查询能力。

---

# 11. Consistent Hashing需要解决什么问题

## 问题

新增或删除节点时：

```text
最少迁移数据
```

很难实现。

---

## 解决方案

一致性哈希（Consistent Hashing）

满足：

### 负载均衡

```text
Key平均分布
```

### 最小迁移

```text
Node变化

↓

仅部分Key迁移
```

---

# 12. 自动重平衡风险

## 问题

系统自动判断：

```text
节点慢
=
节点挂了
```

触发：

```text
自动迁移
```

导致：

- 网络过载
- 节点过载
- 连锁故障

（Cascading Failure）

---

## 解决方案

### 人工审核

```text
Generate Plan
       ↓
Human Approve
       ↓
Execute
```

---

### 提前预热

例如：

- 黑五
- 双十一
- 世界杯

提前迁移数据。

---

# 13. 请求路由问题（Request Routing）

## 问题

客户端知道Key：

```text
user123
```

但不知道：

```text
在哪个节点
```

---

## 解决方案1：节点转发

```text
Client
    ↓
Random Node
    ↓
Target Node
```

---

## 解决方案2：Routing Layer

```text
Client
   ↓
Router
   ↓
Node
```

---

## 解决方案3：Client感知Shard

```text
Client
   ↓
直接访问目标Node
```

---

# 14. 分片元数据一致性问题

## 问题

需要维护：

```text
Shard
   ↓
Node
```

映射关系。

问题：

- Coordinator故障
- Split Brain
- 元数据过期

---

## 解决方案

采用：

- ZooKeeper
- etcd
- Raft

管理集群元数据。

```text
ZooKeeper
      ↓
Shard Mapping
      ↓
Clients / Routers
```

---

# 15. Local Secondary Index的问题

## 问题

每个Shard维护自己的索引。

```text
Shard1
  Red Cars

Shard2
  Red Cars
```

查询：

```sql
color='red'
```

时必须：

```text
查询所有Shard
```

---

## 影响

- 查询变慢
- Tail Latency增加
- 扩容效果变差

---

## 解决方案

Scatter / Gather

```text
Broadcast
     ↓
All Shards
     ↓
Merge Result
```

---

# 16. Global Secondary Index的问题

## 问题

全局索引提高查询效率：

```text
color:red
```

只查一个索引Shard。

但写入变复杂：

```text
更新记录
      ↓
更新多个索引Shard
```

---

## 解决方案

### 分布式事务

保证一致性：

```text
Primary Record
          +
Secondary Index
```

同时更新。

---

### 异步更新

例如DynamoDB：

```text
Write
   ↓
Async Index Update
```

---

## 代价

可能出现：

```text
Stale Read
```

（读到旧索引数据）

---

# 17. 分布式事务问题

## 问题

多个Shard同时更新：

```text
Shard A成功
Shard B失败
```

导致数据不一致。

---

## 解决方案

使用：

- Distributed Transaction
- Two Phase Commit
- 共识协议

保证跨Shard一致性。

---

# 最终总结

| 问题 | 解决方案 |
|--------|----------|
| 单机瓶颈 | Sharding |
| 数据倾斜 | 合理Partition Key |
| Hot Shard | Shard Split |
| Hot Key | Key Salting |
| 时间序列热点 | SensorID+Timestamp |
| 扩容数据迁移过多 | Consistent Hash |
| Shard增长过大 | 自动Split |
| Shard过小 | Merge |
| 自动扩容风险 | Human-in-the-loop |
| 路由问题 | Router/ZooKeeper |
| 元数据一致性 | ZooKeeper/etcd/Raft |
| Local Index查询慢 | Fan-out Query |
| Global Index写入复杂 | 分布式事务 |
| 跨Shard一致性 | Distributed Transaction |
| 节点增减 | Rebalancing |
| Query找不到Node | Request Routing |
