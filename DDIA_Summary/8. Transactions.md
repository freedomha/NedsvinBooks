## 一、核心问题

### 1. 数据系统面临的故障

在现实世界中，数据系统会遇到多种故障：
- 数据库软硬件随时可能崩溃（包括写操作进行中）
- 应用随时可能崩溃（包括一系列操作执行到一半时）
- 网络中断可能导致应用与数据库之间的连接断开
- 多个客户端可能同时写入数据库，互相覆盖彼此的变更
- 客户端可能读取到仅部分更新的、不完整的数据
- 客户端之间的竞态条件（race condition）可能导致令人困惑的bug

### 2. 事务要解决的核心问题

**事务是一种抽象层**，让应用可以假装某些并发问题和某些硬件/软件故障不存在。它将多个读写操作分组为一个逻辑单元：要么全部成功（commit），要么全部失败（abort/rollback）。

事务让应用开发者不必担心部分失败（partial failure），从而大大**简化了错误处理**。

### 3. ACID 的歧义性问题

ACID（Atomicity, Consistency, Isolation, Durability）虽然被广泛引用，但实际上：
- **不同数据库的 ACID 实现并不等同**
- Isolation 的含义非常模糊
- "ACID compliant" 已经成为营销术语，无法确定实际能提供的保证
- BASE（Basically Available, Soft state, Eventual consistency）的定义更加模糊，基本上等同于"不是ACID"

**ACID 四个字母的真实含义**：

| 字母 | 名义含义 | 实际含义 |
|------|---------|---------|
| A: Atomicity | 原子性 | **可中止性（Abortability）**——出错时可以回滚所有写入 |
| C: Consistency | 一致性 | 应用层的**不变量（invariants）**——非数据库独立属性 |
| I: Isolation | 隔离性 | **可序列化（Serializability）**——并发事务互不干扰 |
| D: Durability | 持久性 | 写入数据不会丢失的**承诺**——���实际上不存在完美的持久性 |

## 二、各类隔离级别的问题与能力

### 隔离级别异常对照表

| 隔离级别 | 脏读 | 脏写 | 读倾斜 | 丢失更新 | 写倾斜/幻读 |
|---------|------|------|--------|---------|------------|
| **Read Uncommitted** | ✗ 可能 | ✓ 防止 | ✗ 可能 | ✗ 可能 | ✗ 可能 |
| **Read Committed** | ✓ 防止 | ✓ 防止 | ✗ 可能 | ✗ 可能 | ✗ 可能 |
| **Snapshot Isolation** | ✓ 防止 | ✓ 防止 | ✓ 防止 | ? 取决于实现 | ✗ 可能 |
| **Serializable** | ✓ 防止 | ✓ 防止 | ✓ 防止 | ✓ 防止 | ✓ 防止 |

### 各异常详解

#### (1) 脏读（Dirty Read）
**问题**：一个事务读取到另一个事务尚未提交的写入。如果那个事务后来回滚，则读到了"从未存在过"的数据。

**影响**：用户可能看到不一致的部分更新状态；可能导致级联回滚（cascading aborts）。

#### (2) 脏写（Dirty Write）
**问题**：两个事务同时更新同一行，后来的写入覆盖了尚未提交的前一个写入。

**影响**：多对象更新出现混乱（如二手车买卖中，买家信息和发票指向不同的人）。

#### (3) 读倾斜（Read Skew）/ 不可重复读（Nonrepeatable Read）
**问题**：一个事务在不同时间点看到数据库的不同部分。例如转账时，一个账户显示扣款前的余额，另一个已显示扣款后的余额，导致"钱消失"的假象。

**影响**：
- 备份时可能产生永久性的不一致
- 分析查询和完整性检查可能返回无意义结果

#### (4) 丢失更新（Lost Update）
**问题**：两个事务同时执行"读取-修改-写入"循环，后写入的会覆盖前者的修改。例如两次并发递增计数器，结果只增加了一次。

**影响**：计数器不正确、账户余额错误、wiki编辑内容丢失等。

#### (5) 写倾斜（Write Skew）
**问题**：两个事务读取相同的对象，基于读到的结果做出决策，然后分别更新不同对象。但两个更新共同违反了某个业务约束。

**经典案例**：
- **医生值班**：两个医生同时请假（各自检查至少还有2人在岗 → 都批准 → 无人值班）
- **会议室预定**：两个人同时检查同一时段空闲 → 都预定 → 冲突
- **用户名注册**：两个人同时检查用户名可用 → 都注册 → 但唯一约束可以解决
- **双重支付**：两个消费同时发生，各自检查余额充足 → 都通过 → 余额为负

#### (6) 幻读（Phantom Read）
**问题**：一个事务的写入改变了另一个事务搜索查询的结果集。在写倾斜场景中，尤其棘手，因为幻读的对象是"不存在的行"——无法对其加锁。

## 三、三种可序列化实现的对比

### 1. 实际串行执行（Actual Serial Execution）

**原理**：直接去掉并发，单线程串行执行所有事务。

**必要条件**：
- 数据全部在内存中
- 事务必须短小快速
- 使用存储过程（stored procedure）消除交互式等待

**优点**：实现简单，无需锁和并发控制开销。

**缺点**：
- 吞吐量受限于单CPU核心
- 跨分片事务很慢（约1000次/秒）
- 需要改写为存储过程（各数据库语言不通用、难以调试和版本管理）

**代表系统**：VoltDB/H-Store、Redis、Datomic

### 2. 两阶段锁（Two-Phase Locking, 2PL）

**原理**：
- 读操作需要共享锁，写操作需要排他锁
- 写者阻塞读者，读者也阻塞写者
- 锁在事务结束时才释放（两阶段：获取阶段 + 释放阶段）

**关键特性**：
- 提供完整的可序列化隔离
- 使用谓词锁（predicate lock）防止幻读（实际用索引区间锁近似）
- 需要死锁检测和自动回滚

**优点**：防止所有竞态条件，包括写倾斜和幻读。

**缺点**：
- **性能差**：并发度低，大量等待
- **延迟不稳定**：一个有竞争的查询可能拖慢整个系统
- **死锁频繁**：需要不断重试被中止的事务
- 大范围查询（如全表扫描）可能导致数据库长时间不可写入

**代表系统**：MySQL (InnoDB) serializable、SQL Server serializable、IBM Db2 repeatable read

### 3. 可序列化快照隔离（Serializable Snapshot Isolation, SSI）

**原理**：
- 基于快照隔离之上
- 乐观并发控制（optimistic concurrency control）：允许事务先执行，提交时检查是否违反可序列化性
- 检测两类情况：过时的MVCC读、写入影响了之前的读取

**优点**：
- **读者不阻塞写者，写者不阻塞读者**（延续快照隔离的优势）
- 延迟可预测，波动小
- 不受单核CPU限制，可以横向扩展
- 比2PL性能好得多

**缺点**：
- 高竞争场景下中止率上升
- 读写事务不能太长
- 有一定的检测开销

**代表系统**：PostgreSQL serializable、CockroachDB、FoundationDB、SQL Server Hekaton

## 四、分布式事务的问题

### 原子提交问题（Atomic Commitment Problem）

在分布式环境中，事务可能在部分节点提交、部分节点中止，导致节点间不一致。

### 两阶段提交（Two-Phase Commit, 2PC）

**流程**：
1. **Phase 1 (Prepare)**：协调者询问所有参与者是否准备好提交
2. **Phase 2 (Commit/Abort)**：全票通过则提交，否则全部中止

**两个不可逆节点**：
- 参与者回复 "yes" 后，承诺一定能提交（放弃单方面中止权）
- 协调者做出决定后，决定不可撤销

### 协调者故障问题——in-doubt 状态

**核心问题**：参与者已投票 "yes" 但协调者崩溃，参与者不知道是提交还是中止——**只能等待**。

- 协调者恢复前，锁一直持有，阻塞其他事务
- 如果协调者日志丢失，需要人工介入手动决定提交/中止
- **启发式决策（heuristic decisions）是一个危险的逃生舱口——本质上是"可能破坏原子性"**

### XA 事务的问题

- 协调者是单点故障
- 协调者与参与者之间只能通过应用代码通信
- 是异构系统的最低公分母，无法支持 SSI、跨系统死锁检测
- 不适合生产环境的大规模使用

### 解决方案

**数据库内部分布式事务**相比XA有根本优势：
- 可以复制协调者（通过共识协议实现故障自动切换）
- 协调者与数据分片可以直接通信
- 可以与分布式并发控制协议紧密结合

**代表系统**：CockroachDB、TiDB、Spanner、FoundationDB、YugabyteDB

## 五、Exactly-Once 消息处理

### 问题

如何确保消息处理恰好一次执行？——即使处理过程中发生崩溃需要重试。

### 结论

**不需要分布式事务（跨消息队列+数据库的原子提交）。**

替代方案——**幂等性方法**：
1. 每条消息有唯一ID
2. 数据库中维护已处理消息ID表
3. 处理前检查ID是否已存在
4. 如果已处理则直接确认并丢弃
5. 如果未处理则插入ID并处理
6. 提交数据库事务后再确认消息

这种方法只需要**数据库内部事务**，通过记录消息ID使处理幂等，安全重试不会产生重复副作用。

## 六、总体结论

### 1. 事务的价值

- 事务不是自然法则，而是**有目的地创造**的抽象——**简化应用编程模型**
- 并非所有应用都需要事务，有时为了性能或可用性可以弱化或放弃事务
- 但缺乏事务可能导致严重问题（如英国Post Office Horizon丑闻的技术根源就是缺乏ACID事务）

### 2. 隔离级别的选择

- **Read Committed** 是最低可接受标准（防止脏读、脏写），是大多数数据库的默认级别
- **Snapshot Isolation** 解决了读倾斜问题，适合备份、分析查询等长事务场景
- **Serializable** 能防范所有竞态条件，是最安全的选择
- NoSQL 时代"事务不可扩展"的观念已被证明是**错误的**——NewSQL 数据库证明事务可以扩展到大规模

### 3. 实现建议

| 场景 | 推荐隔离级别 |
|------|------------|
| 简单单记录读写 | 可能不需要事务 |
| 多对象更新、资金操作 | 至少 Snapshot Isolation + 显式锁 |
| 需要强制业务约束（排班、预定） | Serializable (SSI 优先) |

### 4. 关键提醒

- **"ACID" 标签不可信**——需要理解具体数据库的实现细节
- **"Repeatable Read" 在不同数据库中含义完全不同**（PostgreSQL是快照隔离，MySQL较弱，Db2是序列化）
- **弱隔离级别编写的代码看似正常工作，但在并发压力下可能产生难以发现的bug**——这些bug已导致比特币交易所破产
- **持久性没有绝对保证**——只能通过各种风险降低技术（写磁盘、复制、备份）的组合来降低风险
- **SSI 是当前最平衡的可序列化实现**——性能���、可扩展、延迟可预测

### 5. 分布式事务

- **2PC 与 2PL 是完全不同的概念**（前者是原子提交协议，后者是隔离级别实现）
- 数据库**内部**分布式事务（NewSQL）工作良好
- 跨异构系统的 XA 事务问题重重，应避免
- 可以通过**幂等性**而非分布式事务来实现 exactly-once 语义
