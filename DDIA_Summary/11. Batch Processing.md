# 第11章 批处理 — 问题与解决方案总结

> 来源：《Designing Data-Intensive Applications》第二版第11章 Batch Processing

---

## 一、批处理的核心问题领域

### 1. 在线系统 vs 离线系统

| 问题 | 解决方案 |
|------|----------|
| 在线系统（OLTP）无法处理海量数据的计算任务（如训练AI模型、大规模数据转换、分析） | 引入**批处理（离线系统）**，以只读方式消费输入数据，生成派生输出，无副作用 |
| 在线系统中，bug代码写入错误数据后难以恢复 | 批处理将输入视为不可变，输出可从零生成；出错的输出直接删除、修复代码后重新运行（人力容错 human fault tolerance）；对象存储/开放表格式支持时间旅行（time travel） |
| 在线系统的响应延迟是首要性能指标 | 批处理以**吞吐量**为性能核心指标，适合分钟到天级别的长时间运行 |

---

### 2. 单机处理能力的局限

| 问题 | 解决方案 |
|------|----------|
| Unix工具链（`awk \| sort \| uniq`）只能单机运行，数据集超出单机内存/磁盘时失效 | 引入**分布式批处理框架**（Spark、Flink、MapReduce），将计算和存储分布到多机集群 |
| 内存哈希表聚合（Python脚本）在去重键过多时OOM | Unix的`sort`可自动溢出到磁盘并多核并行，使用归并排序的磁盘友好特性；但最终仍需分布式方案处理超大规模 |

---

### 3. 分布式文件系统的挑战

| 问题 | 解决方案 |
|------|----------|
| 需要管理分布在多台机器上的大文件 | **分布式文件系统（DFS）**（HDFS、GlusterFS、CephFS）：文件分块（HDFS 128MB），块级复制到多机实现冗余 |
| DFS块大（128MB），本地文件系统（ext4 4KB）无法直接使用 | 在操作系统文件系统之上实现DFS，块可以部分写入，不要求整块分配 |
| 需要追踪文件在集群中的位置 | 元数据服务：HDFS NameNode、3FS + FoundationDB |
| 机器和磁盘故障 | 多副本复制 + 纠删码（Reed-Solomon）；共享无架构（shared-nothing），无需专用硬件 |
| 热点数据重复读取 | 利用操作系统页缓存将热块保持在数据节点内存中；JuiceFS额外提供客户端缓存和本地磁盘缓存 |

---

### 4. 对象存储的局限性

| 问题 | 解决方案 |
|------|----------|
| DFS和NAS/SAN架构昂贵或需要专用硬件 | 采用**对象存储**（S3、GCS、Azure Blob）：基于HTTP的get/put接口，无需POSIX兼容 |
| 对象不可变，无法追加写入（多数实现） | 更新需完整重写整个对象（PUT）；Azure Blob和S3 Express One Zone支持追加 |
| 没有真正的目录结构 | 使用键前缀模拟层级目录；用零字节对象表示空目录；前缀列表等同于`ls -R` |
| 不支持硬链接、符号链接、文件锁定、原子重命名 | 设计时接受这些限制；重命名通过复制+删除实现 |
| 对象存储分离了存储和计算 | 可能导致更多网络带宽消耗，但好处是CPU和存储可独立弹性伸缩，且现代数据中心网络速度极快 |

---

### 5. 分布式作业编排

| 问题 | 解决方案 |
|------|----------|
| 需要在集群中决定何时何地运行作业 | 采用**作业编排器**（YARN、Kubernetes），包含三个组件：**任务执行器**（NodeManager/kubelet）、**资源管理器**（全局集群状态）、**调度器**（分配任务到节点） |
| 安全隔离 | 使用Linux cgroups提供进程和性能隔离 |
| 特定应用需要自定义调度逻辑 | YARN的ApplicationMaster / Kubernetes的Operator模式提供应用级调度 |
| 资源分配是NP-hard问题 | 使用启发式算法：FIFO、主导资源公平（DRF）、优先级队列、容量/配额调度、装箱算法 |

**资源分配难题示例**：5节点共160核，两个作业各需100核

| 策略 | 问题 |
|------|------|
| 各分80核，等任务完成后补足 | 公平但两个作业都慢 |
| gang scheduling：一个作业先占满 | 可能导致闲置节点和死锁 |
| 持有预留等待全部可用 | 可能导致饥饿（starvation） |
| 抢占（preempt）低优先级任务 | 降低集群效率（被抢占的任务需重新运行） |

---

### 6. 工作流依赖管理

| 问题 | 解决方案 |
|------|----------|
| 作业之间存在依赖关系（输出→输入），形成DAG | 使用**工作流调度器**（Airflow、Dagster、Prefect），管理作业之间的依赖，支持50-100个作业的复杂流水线 |
| 单作业调度器（YARN ResourceManager、Spark Scheduler）不管理多作业依赖 | 工作流调度器等待全部上游依赖完成后才触发下游作业 |
| 跨流水线的数据可发现性 | 引入Data Mesh、Data Contract、Data Fabric实践规范 |

---

### 7. 故障处理

| 问题 | 解决方案 |
|------|----------|
| 长时间运行作业中难免有节点崩溃/网络中断 | 输出从零生成，可重试单个任务而非整个作业 |
| 调度器可能主动抢占低优先级任务（spot实例） | 利用spot实例降低成本，接受抢占后重试 |
| 中间数据写入DFS开销大（MapReduce方式） | **Spark**：中间数据保存在内存/本地磁盘，按谱系（lineage）重算；**Flink**：周期性checkpoint |
| 工作流中上下游任务依赖可能导致级联失败 | MapReduce将中间数据写入DFS，等待完成后再让下游读取，保证容错 |

## 二、批处理模型的问题与演进

### 8. MapReduce的局限性

| 问题 | 解决方案 |
|------|----------|
| 编程模型低层次，需手写map/reduce函数 | 后续系统引入SQL、DataFrame等高层抽象 |
| 复杂处理（如Join）需手写实现 | 数据流引擎（Spark、Flink）内置关系操作符 |
| 每个map和reduce之间强制排序和DFS写入 | 数据流引擎仅按需排序，中间数据保持在内存 |
| 无法流水线化——上游完成后才能启动下游 | 数据流引擎在输入就绪时即可启动下游算子 |
| JVM启动开销大 | 数据流引擎重用已有进程启动新算子 |
| 已过时，Google内部不再使用 | 迁移到Spark、Flink、BigQuery等现代系统 |

---

### 9. 数据流引擎的优势

| MapReduce问题 | 数据流引擎解决方案 |
|---------------|---------------------|
| 固定map→reduce模式 | 灵活组装算子（join、group by、filter、aggregate），不限定交替结构 |
| 每阶段间写入DFS | 中间数据在内存/本地磁盘传递，只最终输出写DFS |
| 缺乏全局优化 | 调度器可做数据本地性优化（将消费任务放在数据生产节点附近） |
| 排序是默认步骤（开销大） | 仅在需要时执行排序 |
| 相邻map/filter分别独立任务 | 合并为单一任务，减少数据拷贝 |

---

### 10. 数据混洗（Shuffle）的复杂性

| 问题 | 解决方案 |
|------|----------|
| 如何在分布式环境中排序PB级数据集 | **混洗算法**：Map阶段按hash(key)分区写本地文件→Reduce阶段拉取对应分区文件→归并排序→按键分组调用Reducer |
| 数据倾斜 | 每个Mapper为每个Reducer创建独立输出文件，按key的哈希值决定分区 |
| 混洗是性能瓶颈 | BigQuery等现代系统将混洗数据保持在内存中，或使用外部排序服务加速 |
| 同key数据分散在不同Mapper中 | 混洗确保相同key的数据汇聚到同一Reducer，是实现JOIN和GROUP BY的基础 |

---

### 11. 编程模型的演进

| 时期 | 模型 | 解决的问题 |
|------|------|------------|
| MapReduce | `map()` / `reduce()` 回调 | 首次实现大规模分布式批处理 |
| 数据流引擎 | Dataflow API（关系型构建块） | 提升性能和编程易用性 |
| SQL引擎 | Hive、Trino、Spark SQL、Flink SQL | 分析师可直接使用，交互式查询，成本优化器自动选择算法 |
| DataFrame API | Spark DataFrame、Daft、Snowpark | 数据科学家可用R/Pandas习惯的API处理分布式数据 |
| 图处理 | Pregel/BSP模型（Giraph、GraphX、Gelly） | 批处理迭代图算法（PageRank等） |
| LLM训练 | Kubeflow、Flyte、Ray | 专门为AI/ML工作负载构建，集成PyTorch、TensorFlow等 |

**数据仓库与批处理的融合**：
- 批处理系统引入SQL和列式存储（Parquet）
- 云数据仓库（BigQuery、Snowflake）采用批处理的调度、容错和混洗技术
- 但SQL仍不适合图迭代算法、复杂ML、多模态AI数据处理

## 三、批处理核心应用场景

### 12. ETL数据集成

| 问题 | 解决方案 |
|------|----------|
| 需要从多个源系统提取、转换并加载数据 | 批处理作业天然适合"尴尬并行"（embarrassingly parallel）的数据转换工作 |
| 数据管道故障定位困难 | 工作流调度器（Airflow）内置重试机制和失败标记；失败文件可直接检查 |
| 单团队维护所有数据管道负担重 | Data Mesh/Data Contract/Data Fabric降低门槛，各团队可自主管理自己的数据产出 |
| 管道转换和分析查询分离 | 统一到相同执行引擎（SparkSQL、Trino、DuckDB），模糊了工程和分析的界限 |

### 13. 分析（OLAP）

| 问题 | 解决方案 |
|------|----------|
| 海量数据的聚合查询 | **数据湖仓（Data Lakehouse）**：分析查询直接在DFS/对象存储上运行，用Iceberg/Unity管理表元数据 |
| 仪表盘需要快速响应 | 预聚合：将数据rollup为OLAP Cube或Data Mart，推送到实时OLAP系统（Druid、Pinot） |
| 业务人员需要自助分析 | SQL支持让批处理框架对接Tableau、Power BI、Looker、Superset等可视化工具 |
| 迭代交互查询需要低延迟 | 快速查询引擎（Trino、Spark SQL）减少等待时间 |

### 14. 机器学习

| 问题 | 解决方案 |
|------|----------|
| 原始数据不能直接用于训练 | 批处理做**特征工程**：过滤、转换文本/离散值为数值格式 |
| 模型训练需要大规模并行计算 | 训练数据作为输入，模型权重作为输出；Spark MLlib、FlinkML提供特征工程工具和分类器 |
| 需要批量推理 | 训练好的模型在批处理中做批量预测和评估 |
| LLM训练前的数据准备 | 批处理流水线：HTML→纯文本提取→低质量/去重检测→分词→Embedding |
| 数据科学家习惯Notebook环境 | Jupyter/Hex notebook通过DataFrame API或SQL查询批处理系统 |

**图处理特殊挑战**：

| 问题 | 解决方案 |
|------|----------|
| 图算法（如PageRank）需迭代遍历边 | **批量同步并行（BSP/Pregel）模型**：每次迭代连接相邻顶点传播信息，直至收敛 |

### 15. 派生数据的服务化

| 问题 | 解决方案 |
|------|----------|
| 批处理结果需推送到线上数据库对外服务 | **推荐方案**：将结果推送到**Kafka消息流**，下游系统（ES、Pinot、Druid、Venice、ClickHouse）从流中消费 |
| 直接写数据库每条记录发一次网络请求，性能极差 | 流系统专为顺序写入优化，天然适合批处理的大批量写入 |
| 并行写入同一数据库可能压垮线上DB | 流系统作为缓冲，下游可限速消费，不影响线上服务 |
| 部分成功的作业产生"脏"可见输出 | Kafka → 下游系统支持"未提交"隔离：数据不可见直到收到完成通知 |
| 全量写入场景（初始化数据库） | **批量导入**：在批处理内构建新数据库文件，用TiDB Lightning、Pinot Hadoop Import、RocksDB SST Bulk Import直接加载，原子切换新老版本 |
| 需要同时支持全量引导和增量更新 | 混合方案：Venice支持hybrid store，允许行级更新和全量替换 |

## 四、关键设计原则总结

| 原则 | 说明 |
|------|------|
| **输入不可变** | 只读取不修改，允许无副作用重跑 |
| **输出可丢弃** | 出问题直接删除输出、修改逻辑重跑 |
| **人力容错** | 代码bug可以退回，数据不会永久损坏 |
| **最小化不可逆性** | 有利于敏捷开发，快速迭代不怕犯错 |
| **共享无架构** | 普通硬件 + 标准网络，不用专用设备 |
| **计算与存储分离** | 对象存储模式下独立弹性伸缩 |
| **任务级重试** | 单个任务失败不影响其他并行任务 |
| **Sort-Merge Join** | 通过排序使同key数据相邻，无需哈希表即可join |
| **声明式优于命令式** | SQL/DataFrame让查询优化器自动选择最优算法和执行顺序 |

## 补充参考：第12章预告

批处理的输入是**有界的**（bounded），而**流处理**（第12章）的输入是**无界的**（unbounded），作业永远不会结束。两者有相似性，但无界流的假设彻底改变了系统构建方式。
