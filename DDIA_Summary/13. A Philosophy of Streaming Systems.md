# 第13章：流式系统哲学 — 问题与解决方案总结

> 来源：《Designing Data-Intensive Applications, 2nd Edition》Chapter 13: A Philosophy of Streaming Systems

---

## 一、数据集成问题

### 问题1：多工具组合的复杂性
- **描述**：复杂应用中，数据往往以多种方式被使用（OLTP、全文搜索、分析、缓存、机器学习等），没有单一软件能同时满足所有访问模式。
- **后果**：需要在多个异构存储系统之间手动保持数据同步，容易出现不一致。

### 解决方案
- **派生数据（Derived Data）**：将一种系统指定为「记录系统」（system of record），其他数据通过转换从中派生。
- **变更数据捕获（CDC）**：以确定性的、幂等的方式从事件日志更新派生数据系统。
- **单一写入入口**：将所有用户输入汇集到单一系统，由它决定所有写入的排序，其他系统按相同顺序处理。

### 问题2：分布式事务 vs 派生数据的权衡
- **分布式事务**：通过锁实现互斥排序，原子提交保证一次性效果，读取立即保持一致。
- **派生数据**：通过日志排序 + 确定性重试 + 幂等性，异步更新导致读取可能有延迟。

### 解决方案
- **日志派生的数据系统**是整合不同数据系统最有前景的方法（在缺乏广泛分布式事务协议支持的现状下）。
- 后续探索在异步派生系统上实现更强保证的中间地带方案。

## 二、全序排序的局限性

### 问题3：全序广播（Total Order Broadcast）无法无限扩展
- **单节点吞吐量瓶颈**：构建全序日志要求所有事件通过单个领导节点。
- **地理分布**：多数据中心场景下，跨数据中心同步协调效率低，事件顺序不明确。
- **微服务架构**：每个服务独立部署，无共享持久状态，事件顺序由各自决定。
- **离线/移动客户端**：客户端和服务端可能看到不同的事件顺序。

### 解决方案
- **因果依赖捕获**：日志记录用户做决策前看到的系统状态，事件附带唯一标识，后续事件可引用以记录因果依赖。
- **冲突解决算法**：自动冲突解决（如CRDT）用于维持状态。
- **按对象ID路由**：同一对象的所有更新路由到同一日志分片以维持顺序。
- **分片日志**：通过哈希分区扩 展吞吐量。

### 问题4：因果依赖丢失（社交网络案例）
- **描述**：用户解除好友关系 → 发消息抱怨前伴侣。若好友关系和消息存储在不同位置，因果顺序可能丢失，导致前伴侣收到不该看到的通知。

### 解决方案
- 将解除好友事件和发送消息事件都记录为事件，用唯一标识建立因果依赖关系。

## 三、批处理与流处理的统一

### 问题5：Lambda架构的问题
- Lambda架构（批处理层+流处理层）存在多种问题，已逐渐被淘汰。

### 解决方案：Kappa架构 / 统一批流处理
- **事件重放能力**：同一处理引擎既能处理实时流，也能重放历史事件。
- **精确一次语义（Exactly-once）**：故障发生后输出应与无故障时一致。
- **按事件时间开窗**：非处理时间，因为重放历史事件时处理时间无意义。
- 代表工具：Apache Beam + Apache Flink / Google Cloud Dataflow。

### 问题6：应用演进与模式迁移
- **描述**：数据模式需要随需求变化演进，传统迁移需要停机或复杂操作。

### 解决方案
- **派生视图渐进迁移**（铁路双轨类比）：新旧模式作为同一底层数据的两个独立派生视图并存，逐步切换用户流量。
- **数据重处理（Reprocessing）**：通过批处理重处理历史数据来派生新视图。

## 四、数据库的解绑（Unbundling）

### 问题7：Unix哲学 vs 关系数据库哲学的张力
- Unix：低层硬件抽象，管道+文件（字节序列），简单但功能有限。
- 关系数据库：高层抽象（SQL、事务），功能强大但实现复杂。
- NoSQL运动可以理解为将Unix式低层抽象应用于分布式OLTP存储。

### 解决方案：两种合成路径

#### 路径A：联邦数据库（Federated Databases）— 统一读取
- 在多个底层存储引擎上提供统一查询接口（如Trino、PostgreSQL FDW）。
- 遵循关系型传统：高层查询语言+优雅语义，但实现复杂。
- **局限**：只解决只读查询，不同步写入。

#### 路径B：解绑数据库（Unbundled Databases）— 统一写入 ⭐推荐
- 通过事件日志 + 幂等写入在不同技术间同步写入。
- 遵循Unix传统：小工具各司其职，通过管道（事件流）通信，用高层语言（流处理器）组合。
- **优势**：
  1. **系统层面**：异步事件流使系统对故障/性能退化更鲁棒，故障被隔离而非放大。
  2. **人类层面**：不同团队可独立开发、改进、维护各自的组件。
- **务实原则**：如果单一产品能满足所有需求，直接用即可；解绑仅在无单一工具满足需求时才有价值。

### 问题8：数据库不适合部署应用代码
- 不满足现代应用开发需求（依赖管理、版本控制、滚动升级、监控、网络服务调用等）。

### 解决方案
- **应用代码与状态分离**：使用Kubernetes等工具部署无状态服务，状态管理由数据库负责。
- **流处理器**：应用代码作为流算子运行，处理数据库内置功能不提供的任意派生逻辑。

## 五、数据流应用设计

### 问题9：被动数据库模型 vs 响应式需求
- 传统数据库是「被动变量」，应用通过轮询检测变化，无内置变更订阅机制。
- 电子表格早在1979年就有了响应式计算（VisiCalc），但数据系统落后于此。

### 解决方案：以数据流为中心的应用设计
- **变更订阅**：状态变更通过流推送给所有依赖方（类似电子表格的自动重算）。
- **流算子组合**：类似Unix管道，每个算子接收状态变更流，产生其他状态变更流。
- **流处理 + 消息系统**：日志消息代理提供有序、容错的消息传递。

### 问题10：微服务REST API vs 数据流的性能问题
- 同步网络请求（如REST API查询汇率）引入延迟，增加故障耦合。
- 最快的网络请求是没有网络请求。

### 解决方案
- **数据流方式替代RPC**：
  - 汇率更新服务订阅汇率变更流，存入本地数据库。购买处理时只需查询本地数据库。
  - 将RPC替换为流连接（stream join）：购买事件流 + 汇率更新事件流。
  - 更快速、更鲁棒（其他服务故障不传播）。

## 六、读路径与写路径的边界

### 问题11：预计算 vs 实时计算的权衡
- 全文搜索索引：不建索引则写入轻但读取重（grep扫描），建索引则写入重但读取轻。
- 缓存、索引、物化视图的本质：在写路径上做更多预计算，以节省读路径上的工作量。

### 解决方案
- **灵活边界移动**：根据访问模式调整读写路径边界（类似社交网络timeline推拉模型）。
- **有状态离线客户端**：将设备本地状态视为服务器状态的缓存，UI是物化视图。
- **端到端事件流**：状态变更从服务器一直推送到终端用户设备（Server-Sent Events/WebSocket），减轻离线/弱网影响。

### 问题12：读取也是事件
- 传统设计：写入通过事件日志，读取是瞬态网络请求（分开处理）。

### 解决方案
- **将读取表示为事件**：读写都路由到同一流算子处理 = 流表连接（stream-table join）。
- 记录读取事件可追踪因果依赖和数据溯源：重建用户做决策前看到的内容。
- 支持复杂多分片查询的分布式执行。

## 七、正确性（Correctness）

### 问题13：事务的可靠性被高估
- 弱隔离级别的混乱，Jepsen实验揭示了许多产品声称的安全保证与实际行为的差距。
- 应用代码正确使用数据库功能本身就容易出错。
- 串行化事务和原子提交成本高：通常只能在单数据中心运行，限制可扩展性。

### 问题14：重复执行与数据损坏
- TCP去重仅在一个连接内有效，HTTP POST重试可能导致重复事务。
- 用户在弱网下可能手动重试提交，服务端视为独立请求。

### 解决方案：端到端参数（End-to-End Argument）

#### 请求去重
- 生成唯一请求ID（UUID），从客户端一路传递到数据库。
- 数据库通过唯一约束 + 事务确保每个请求ID只执行一次。
- **核心原则（Saltzer, Reed, Clark 1984）**：低层机制（TCP去重、数据库事务）不足以确保端到端正确性，只有应用层端到端措施才能完整、正确地实现功能。

#### 在数据系统中的应用
- 应用层必须采取端到端措施（如去重），不能仅依赖数据库的安全特性。
- 我们需要更好的容错抽象，让应用代码在分布式环境中轻松提供应用特定的端到端正确性。

## 八、约束强制（Enforcing Constraints）

### 问题15：唯一性约束需要共识
- 分布式环境中强制唯一性需要共识/全序广播：决定哪个冲突操作被接受。
- 通常通过单领导节点实现：所有写入通过单个节点 = 扩展性瓶颈。
- 异步多主复制不可用：不同领导可能同时接受冲突写入。

### 解决方案

#### 日志分片 + 流处理器（用户名唯一性）
1. 用户名请求编码为消息，按用户名哈希追加到对应分片。
2. 流处理器顺序读取日志分片（单线程），用本地数据库跟踪已占用用户名。
3. 可用则发送确认，不可用则发送拒绝。

#### 多分片请求处理（转账案例）
1. 客户端生成请求ID，按源账户ID追加到日志分片。
2. 源账户流处理器检查余额，预留资金，发送付款事件到源/目标/手续费分片。
3. 各目标分片独立处理，通过请求ID去重。
4. **原子性**来自写入初始请求事件的原子操作，而非分布式事务。所有下游事件最终都会写入（可能重复但去重）。

## 九、时效性 vs 完整性

### 问题16：一致性的两层含义被混淆
| 属性 | 含义 | 违反后果 |
|------|------|----------|
| **时效性（Timeliness）** | 用户看到系统最新状态 | 「最终一致性」— 等待后自行恢复 |
| **完整性（Integrity）** | 无数据损坏、无矛盾/虚假数据 | 「永久不一致」— 需显式检查和修复 |

ACID事务通常同时提供时效性（线性化）和完整性（原子提交）保证，模糊了两者的区别。

### 解决方案：数据流系统解除时效性与完整性的耦合
- **完整性是流系统的核心**：精确一次语义、容错消息传递、去重、幂等操作维持完整性。
- **时效性可以弱化**：异步处理天然不完全保证时效性，但完整性不可妥协。
- 完整性通过以下组合实现：
  1. 写操作内容表示为单个消息（适合事件溯源）
  2. 用确定性函数派生所有状态更新
  3. 客户端生成请求ID贯穿所有处理层
  4. 消息不可变 + 数据可重处理以从错误中恢复

### 问题17：严格约束并非总是必须的
- 真实业务中，许多「硬约束」实际上允许违反：
  - 仓库库存可能因叉车事故损坏
  - 航空公司和酒店故意超售
  - 银行允许透支（收取透支费，限制每日额度）

### 解决方案：松散约束 + 补偿事务
- **补偿事务（Compensating Transaction）**：事后道歉修复（退款、补发、道歉邮件）。
- **免协调数据系统（Coordination-Avoiding）**：
  - 数据流系统可在无需原子提交、线性化、同步跨分片协调的情况下维持完整性。
  - 支持多数据中心多主配置，异步复制，各数据中心独立运行。
  - 仅在必要时引入同步协调（如不可恢复的操作）。
  - **核心权衡**：协调减少因不一致导致的道歉，但也降低性能和可用性（增加因宕机的道歉），需找到最佳平衡点。

## 十、信任但验证（Trust, but Verify）

### 问题18：硬件和软件并非完全可靠
- 即使经过广泛测试的数据库（MySQL、PostgreSQL）也出现过唯一性约束和隔离级别的bug。
- 应用代码的bug更多（缺乏数据库级别的审查和测试）。
- 传统ACID一致性假设事务本身无bug，但实际并非如此。

### 解决方案

#### 持续完整性校验
- 不要盲目信任系统的安全保证，需要自验证/自审计系统。
- HDFS和S3的做法：后台进程持续读取文件、对比副本、迁移数据以防范静默损坏。
- 定期从备份恢复测试，确保备份可用。

#### 可审计性设计
- **确定性派生**：事件日志 + 确定性派生代码 = 可重复的结果。
- **数据溯源清晰**：明确的数据流使完整性检查更可行。
  - 使用哈希校验事件日志是否损坏。
  - 重新运行批/流处理器验证派生状态。
- **时间旅行调试**：确定性数据流支持重现导致异常事件的确切环境。

#### 加密完整性工具
- **Merkle树**：高效证明记录存在于数据集中的能力。
- **证书透明度（Certificate Transparency）**：使用加密验证的追加日志 + Merkle树检查TLS证书有效性。
- 区块链（Bitcoin/Ethereum）本质是拜占庭容错的追加日志，但开销过高；其加密工具可在轻量场景中使用。

## 总结

本章提出的**核心哲学**：

1. **数据流为中心**：应用应围绕数据流构建，而非围绕请求/响应交互。
2. **派生数据模式**：将记录系统与派生系统分离，通过异步日志维护一致性。
3. **解绑数据库**：将数据库组件拆解为松散耦合的独立服务，通过事件流组合。
4. **端到端正确性**：低层机制不足以保证正确性，应用层必须采取端到端措施。
5. **分离完整性与时效性**：完整性必须保证（通过幂等、去重、确定性派生），时效性可按需权衡。
6. **免协调设计**：通过松散约束 + 补偿事务，在维持完整性的前提下避免同步协调。
7. **信任但验证**：持续审计数据完整性，建立可验证的数据系统。
