# Chapter 12: Stream Processing - 问题与解决方案报告

> 基于《Designing Data-Intensive Applications, 2nd Edition》第十二章内容总结

---

## 一、核心问题：批处理的局限性

### 问题 1.1：批处理要求输入数据是有限的（Bounded）
- 批处理（如 MapReduce）假设输入数据**有已知的、有限的大小**
- MapReduce 的排序操作必须读取全部输入后才能开始输出
- 最后一笔输入记录可能具有最小的键，因此必须是最早的输出

### 问题 1.2：现实数据是无界的（Unbounded）
- 用户持续产生数据（昨天、今天、明天...），数据集永远不会「完整」
- 批处理必须人为地将数据分割为固定时间段（按天、按小时处理）

### 问题 1.3：批处理延迟过高
- 日批处理的输入变更需要一天后才能反映到输出
- 对于需要低延迟的用户来说速度太慢

### 解决方案
- **流处理（Stream Processing）**：持续处理每一个事件，彻底抛弃固定时间片
- **流（Stream）** = 随时间增量可用的数据
- 流处理是批处理在无界数据上的推广，兼顾低延迟与正确性

## 二、问题：如何可靠传输事件流

### 问题 2.1：传统轮询方案效率低
- 生产者写入存储，消费者定期轮询
- 轮询越频繁，返回新事件的比例越低，开销越大

### 问题 2.2：消息生产者与消费者速度不匹配
- 生产者发送速度快于消费者处理速度时，系统面临三种选择：**丢弃消息**、**缓冲队列**、**背压**

### 问题 2.3：节点崩溃或离线时消息丢失
- 需要持久化（写入磁盘、复制）来保证可靠性
- 持久的代价是性能损失

### 问题 2.4：直接消息传递系统的局限
- **UDP 组播**、**ZeroMQ**、**StatsD** 等方案要求生产者和消费者始终在线
- 消费者离线会错过消息
- 生产者崩溃会导致待重试的消息缓冲区丢失

### 问题 2.5：AMQP/JMS 风格消息代理的「破坏性消费」问题
- 消息被确认后即从代理中删除
- 新增消费者只能接收注册后发送的消息，历史消息不可恢复
- **无法像批处理那样反复重放、实验和调试**

### 问题 2.6：负载均衡与重投递导致消息乱序
- 消费者崩溃时消息重投递到另一个消费者
- 结合负载均衡不可避免地导致消息重排序
- 可能导致**因果关系依赖**被破坏

### 问题 2.7：毒消息（Poison Message）死循环
- 生产者序列化格式错误的消息
- 消费者永远无法处理，代理不断重投递
- 强序保证下系统完全阻塞

### 解决方案

| 方案 | 说明 |
|------|------|
| **消息代理（Message Broker）** | 集中化服务器，负责消息的持久化、投递和消费者管理 |
| **基于日志的消息代理（Log-based Broker）** | 如 Kafka、Kinesis，日志即只追加的消息序列，消费不删除 |
| **分区/分片（Sharding）** | 日志分片实现水平扩展，主题=一组分片的集合 |
| **消费者组（Consumer Groups）** | 同时支持负载均衡（组内）和扇出（组间） |
| **确认与重投递（Ack + Redelivery）** | 消费者崩溃未确认的消息重投递 |
| **死信队列（Dead Letter Queue, DLQ）** | 毒消息移入独立队列，释放主队列 |
| **分层存储（Tiered Storage）** | 旧消息移至对象存储，支持 Iceberg 表直接做批处理分析 |
| **消息回放（Replay）** | 日志消息可重复读取，支持实验和错误恢复 |

## 三、问题：异构数据系统同步

### 问题 3.1：多系统的数据不一致
- 应用可能同时使用 OLTP 数据库、缓存、全文索引、数据仓库
- 同一数据需要在多个系统中保持同步

### 问题 3.2：双写（Dual Writes）的竞态条件
- 客户端 1 写 X=A 到数据库，客户端 2 写 X=B 到数据库 → 数据库最终值为 B
- 但搜索索引先收到 B 后收到 A → 搜索索引最终值为 A
- **两个系统永久不一致，且无错误报告**

### 问题 3.3：双写的容错问题
- 一个写入成功、另一个失败 → 系统不一致
- 需要原子提交（两阶段提交），代价极高

### 解决方案：变更数据捕获（Change Data Capture, CDC）

**原理：**
- 以**数据库**为唯一 Leader（系统记录），所有变更写入其复制日志
- 搜索索引、缓存、数据仓库作为 Follower，消费变更日志
- 数据库决定写入顺序 → 所有下游系统按相同顺序应用变更 → 避免竞态条件

**实现方式：**
| 工具 | 说明 |
|------|------|
| **Debezium** | CDC 开源项目，支持 MySQL、PostgreSQL、Oracle、Cassandra 等 |
| **Kafka Connect** | Kafka 生态的 CDC 连接器框架 |
| **Maxwell** | MySQL binlog 解析 |
| **GoldenGate** | Oracle CDC 解决方案 |

**处理挑战：**
- **初始快照**：需要从一致快照+已知日志位置开始
- **日志压缩（Log Compaction）**：只保留每个键的最新值，支持从日志重建完整数据库 → 无需重复全量快照
- **Schema 变化隔离**：使用 **Outbox Pattern**，在数据库内部维护独立的 outbox 表作为 CDC 的外部 Schema，通过单事务保证一致性

## 四、问题：可变状态与不可变事件的对立

### 问题 4.1：可变数据的故障恢复困难
- 错误代码可直接覆写数据 → 恢复极难
- 无法审计和诊断历史操作

### 问题 4.2：不可变日志的存储与删除冲突
- 高更新/删除率数据 → 日志体积膨胀
- GDPR 等法规要求真正删除个人数据

### 问题 4.3：应用层与底层变更的抽象差异
- **CDC**：低层状态变更日志（数据库行级变更）
- **Event Sourcing**：高层应用事件日志（用户意图表达）

### 解决方案

| 技术 | 说明 |
|------|------|
| **日志压缩（Log Compaction）** | 仅保留每个键的最新值，丢弃重复/旧值，减少存储 |
| **只追加不可变日志** | 财务记账模型：错误通过补偿交易修正，不删除原始记录 |
| **CQRS（命令查询职责分离）** | 写优化日志 + 读优化视图分离，同一日志可派生多种视图 |
| **加密粉碎（Crypto-shredding）** | 敏感数据加密存储，需删除时丢弃加密密钥 |
| **快照（Snapshot）** | 定期保存派生状态快照，避免完整日志重放 |
| **增量视图维护（IVM）** | 如 Materialize、RisingWave，将 SQL 转为增量算子，仅处理变更部分 |

## 五、问题：流处理中的时间推理

### 问题 5.1：处理时间 vs 事件时间混滑
- 许多流处理框架默认使用**处理时间**（机器本地时钟）
- 仅在延迟极短时合理

### 问题 5.2：处理延迟导致错误分析
- 流处理器重启恢复时处理积压事件
- 基于处理时间的窗口会产生**虚假峰值**

### 问题 5.3：延迟事件（Straggler Events）
- 网络中断、移动设备离线缓存等导致事件迟到
- 无法确定窗口何时真正「完成」

### 问题 5.4：设备时钟不可信
- 用户设备时钟可能错误
- 服务器时钟更准确但与用户行为时间无关

### 解决方案

| 问题 | 解决方案 |
|------|----------|
| **事件时间 vs 处理时间** | 使用事件内部的**时间戳**而非系统时钟；日志三个时间戳（事件发生时间、发送时间、接收时间）来估计设备时钟偏差 |
| **Straggler 事件** | 超时后声明窗口完成，忽略迟到事件（跟踪丢弃指标）或发布**修正值 + 撤回旧值** |
| **Watermark** | 特殊消息声明「此后不会再有时间戳早于 t 的消息」，消费者据此触发窗口关闭 |
| **窗口类型** | Tumbling（固定不重叠）、Hopping（固定可重叠）、Sliding（基于间隔）、Session（基于用户活动期） |

## 六、问题：流上的连接（Join）

### 问题 6.1：流-流连接的时序不确定性
- 搜索事件和点击事件到达顺序可能颠倒
- 点击可能永远不发生
- 时间间隔高度可变

### 问题 6.2：流-表连接的状态时效性
- 远程查询数据库慢且可能过载数据库
- 用户资料随时变化，需保持本地副本最新

### 问题 6.3：表-表连接的事件顺序
- 社交网络时间线的粉丝关系变化与帖子发布的交错顺序
- 不同流/分片间无顺序保证

### 问题 6.4：连接的时间依赖性与确定性
- 税率随时间变化 → 发票应关联销售时税率，而非当前税率
- 跨流事件顺序不确定 → 连接结果不确定 → 重跑可能不同

### 解决方案

| 连接类型 | 实现方式 |
|----------|----------|
| **流-流连接（Stream-Stream Join）** | 维护时间窗口内的事件索引（如按 session ID），匹配相关事件；窗口过期时发出未点击事件 |
| **流-表连接（Stream-Table Join）** | 通过 CDC 订阅表变更流，在流处理器本地维护哈希表/索引，避免远程查询 |
| **表-表连接（Table-Table Join）** | 两端都是变更日志，任一变更触发物化视图的增量更新；类比微积分乘积法则 `(u·v)′ = u′v + uv′` |
| **确定性连接** | 引入版本标识符 → 发票记录税率版本 ID（Slowly Changing Dimension 技术） |

## 七、问题：流处理的容错与精确一次语义

### 问题 7.1：流无法「完成后展示输出」
- 批处理可等任务完成后再展示输出
- 流是无限的，**必须持续产出**，无法等待

### 问题 7.2：失败重试导致外部副作用重复
- 微批处理/检查点可保证框架内 exactly-once
- 但写入外部系统（数据库、邮件、外部消息代理）可能重复

### 问题 7.3：有状态算子的故障恢复
- 窗口聚合、连接索引等状态必须在故障后恢复
- 远程查询数据库太慢

### 问题 7.4：非幂等操作的重试
- 计数器递增不是幂等的
- 失败重试会导致重复计数

### 解决方案

| 技术 | 说明 |
|------|------|
| **微批处理（Microbatching）** | Spark Streaming，约 1 秒为一个批处理单元；小批次低开销，大批次高延迟 |
| **检查点（Checkpointing）** | Flink，周期性生成状态快照写入持久存储，基于 barrier 触发 |
| **原子提交协议** | Google Cloud Dataflow、Kafka 内部事务管理状态+消息，非跨异构技术的分布式事务 |
| **幂等性（Idempotence）** | 利用 Kafka offset 判断更新是否已应用；删除操作天然幂等；非幂等操作通过附加元数据改造 |
| **状态复制** | Kafka Streams 将状态变更写入 log-compacted topic；Flink 定期快照到分布式文件系统；VoltDB 冗余处理每条消息 |
| **状态重放** | 如果窗口短，直接从输入流重放重建状态；通过 CDC 从日志压缩流重建数据库副本 |

## 八、应用场景总结

| 场景 | 典型应用 |
|------|----------|
| **复杂事件处理（CEP）** | 欺诈检测、金融交易、制造监控、军事情报 — 基于事件模式匹配 |
| **流分析（Stream Analytics）** | 事件速率测量、滚动平均值、同比/环比趋势检测 — 窗口化聚合 |
| **物化视图维护** | 缓存、搜索索引、数据仓库的增量更新 — 从 CDC 变更日志持续刷新 |
| **流搜索（Search on Streams）** | 媒体监控、房产订阅通知 — 查询提前注册，文档流经查询匹配 |

## 九、关键架构选择对比

| 维度 | AMQP/JMS 消息代理 | 基于日志的消息代理 |
|------|-------------------|---------------------|
| 消息消费 | 确认后删除（破坏性） | 读取不删除（非破坏性） |
| 历史消息 | 不可恢复 | 可回放重处理 |
| 消息顺序 | 单分区可保序 | 分片内严格保序，跨分片无序 |
| 并行模型 | 逐消息分发 | 按分片分配 |
| 适用场景 | 任务队列、RPC 异步通信 | 数据集成、流处理管道 |

## 十、核心设计原则

1. **不可变性优先**：日志即系统记录（System of Record），可变状态仅是从日志派生的优化
2. **分离读写模型**：写入优化的事件日志 + 读取优化的物化视图（CQRS）
3. **确定性处理**：事件时间戳决定窗口归属，避免处理时间带来的不确定性
4. **容错设计**：丢弃失败的部分输出 → exactly-once 语义
5. **状态与流同构**：每个数据库写入都是事件，每个复制日志都是流 — 统一抽象
