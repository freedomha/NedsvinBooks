# 第4章 Storage and Retrieval（存储与检索）—— 问题与解决方案总结

> 核心主题：数据库如何高效地存储数据，以及如何快速地把数据取出来。
>
> 本章围绕两个核心目标展开：
>
> 1. Write Fast（高效写入）
> 2. Read Fast（高效读取）

---

# 一、存储系统面临的核心矛盾

数据库设计本质上是在平衡：

|目标|挑战|
|------|------|
|快速写入|尽量少维护索引|
|快速查询|需要更多索引|
|减少存储空间|需要压缩|
|提高性能|需要更多副本和缓存|
|高吞吐|可能增加延迟|
|OLTP优化|不利于OLAP|
|OLAP优化|不利于OLTP|

核心Tradeoff：

```text
Write ↔ Read
Space ↔ Speed
Latency ↔ Throughput
OLTP ↔ OLAP
```

# 二、Append-only Log 的问题与解决方案

## 问题1：查询性能极差

最简单数据库：

```bash
db_set()
db_get()
```

实现方式：

```text
Write:
append

Read:
full scan
```

时间复杂度：

```text
Write = O(1)

Read = O(n)
```

数据越大查询越慢。

---

## 解决方案：Hash Index

维护内存索引：

```text
Key → Offset
```

例如：

```text
42 → byte 102400
```

查询流程：

```text
Key
 ↓
HashMap
 ↓
Offset
 ↓
Disk Seek
 ↓
Value
```

结果：

```text
Read：
O(n)

↓

O(1)
```

---

## 问题2：旧数据不断累积

更新：

```text
42=v1
42=v2
42=v3
42=v4
```

旧版本永久保留。

---

## 解决方案：Compaction

压缩前：

```text
42=v1
42=v2
42=v3
42=v4
```

压缩后：

```text
42=v4
```

删除：

- 被覆盖版本
- 删除记录
- 过期记录

---

## 问题3：系统重启慢

HashMap不在磁盘。

重启时：

```text
Scan entire log
```

TB级数据极慢。

---

## 解决方案：SSTable

使用：

```text
Sorted String Table
```

特性：

- Key有序
- Key唯一
- 支持稀疏索引

重启时：

```text
直接加载索引
```

无需全表扫描。

---

## 问题4：范围查询困难

Hash结构：

```sql
10000~20000
```

需要：

```text
查10000
查10001
...
查20000
```

---

## 解决方案：有序存储

SSTable按Key排序：

```text
10000
10001
10002
...
```

支持：

```sql
BETWEEN

ORDER BY

RANGE SCAN
```

---

# 三、LSM Tree 的问题与解决方案

LSM：

```text
Log Structured Merge Tree
```

使用场景：

```text
RocksDB
Cassandra
ScyllaDB
HBase
BigTable
```

---

## 问题1：排序结构写入成本高

SSTable必须有序。

不能直接插入：

```text
A
B
D
```

插入：

```text
C
```

需要重写整个文件。

---

## 解决方案：MemTable

写入流程：

```text
Write
 ↓
WAL
 ↓
MemTable(RAM)
 ↓
Flush
 ↓
SSTable
```

特点：

```text
写入内存
后台排序
批量落盘
```

---

## 问题2：系统Crash丢失数据

MemTable只存在内存。

---

## 解决方案：WAL

Write Ahead Log

流程：

```text
Write

↓

WAL

↓

MemTable
```

Crash恢复：

```text
Replay WAL
```

重建MemTable。

---

## 问题3：读放大（Read Amplification）

数据散落在：

```text
Segment1
Segment2
Segment3
Segment4
...
```

查询一个Key可能：

```text
扫描多个文件
```

---

## 解决方案：Bloom Filter

用途：

```text
快速判断Key是否存在
```

返回：

```text
Definitely Not

or

Probably Yes
```

特点：

```text
无False Negative

允许False Positive
```

典型配置：

```text
10 bit/key

≈1%误判率
```

---

## 问题4：删除数据困难

SSTable不可修改。

不能直接：

```sql
DELETE
```

---

## 解决方案：Tombstone

写入：

```text
Delete Record
```

即：

```text
Tombstone
```

Compaction时：

```text
旧数据
+
Tombstone

↓

彻底删除
```

---

## 问题5：SSTable越来越多

长期运行：

```text
L0
L1
L2
L3
...
```

读性能下降。

---

## 解决方案：Compaction

### Size-Tiered Compaction

```text
多个小文件

↓

一个大文件
```

特点：

```text
写入性能最好
```

适合：

```text
日志系统
IoT
时序系统
```

---

### Leveled Compaction

```text
L0
 ↓
L1
 ↓
L2
```

特点：

```text
查询效率更高
```

适合：

```text
在线业务数据库
```

---

# 四、B-Tree 的问题与解决方案

---

## 问题1：如何快速定位数据

全扫描：

```text
O(n)
```

无法接受。

---

## 解决方案：树形索引

结构：

```text
Root
 ↓
Internal
 ↓
Leaf
```

查找：

```text
O(log n)
```

例如：

```text
250TB数据

仅需4层树
```

---

## 问题2：页面写入导致损坏

场景：

```text
Page Split
```

写一半宕机：

```text
Orphan Page
Corruption
```

---

## 解决方案：WAL

流程：

```text
Write WAL

↓

fsync

↓

Update Page
```

恢复：

```text
Replay WAL
```

---

## 问题3：页满

插入：

```text
334
```

目标Page空间不足。

---

## 解决方案：Page Split

拆分：

```text
333~345

↓

333~337

337~345
```

同时更新：

```text
Parent Page
```

保持平衡树结构。

# 五、LSM Tree 与 B-Tree 对比

|维度|LSM Tree|B-Tree|
|------|------|------|
|写入性能|★★★★★|★★★|
|随机写性能|★★★★★|★★|
|读取性能|★★★|★★★★★|
|范围查询|★★★★|★★★★★|
|压缩率|★★★★★|★★★|
|磁盘利用率|★★★★★|★★★|
|写放大|较低|较高|
|适合场景|写多读少|读多写少|


```text

```

例如：

```text

```

# 六、SSD面临的问题与解决方案

## 问题：随机写性能差

SSD特性：

```text
Read：Page粒度

Erase：Block粒度
```

例如：

```text
Page = 4KB

Block = 512KB
```

随机写导致：

```text
大量GC
写入放大
寿命下降
```

---

## 解决方案

采用：

```text
顺序写
```

即：

```text
LSM Tree
```

优势：

```text
减少GC

减少Write Amplification

延长SSD寿命
```

---

# 七、OLAP存储问题与解决方案

---

## 问题1：查询仅访问少量列

例如：

```sql
SELECT

date_key,
product_key,
SUM(quantity)
```

事实表：

```text
100+列
```

真正只用：

```text
3列
```

---

## 解决方案：Column Store

传统：

```text
Row Storage
```

改为：

```text
Column Storage
```

结构：

```text
Date Column

Product Column

Quantity Column
```

收益：

```text
减少IO

减少网络流量

减少CPU消耗
```

---

## 问题2：PB级数据量

数据仓库：

```text
TB

PB

EB
```

---

## 解决方案：列压缩

技术：

### Bitmap Encoding

```text
0
1
0
0
1
```

---

### Run-Length Encoding

```text
000000

↓

(0,6)
```

---

### Roaring Bitmap

动态切换压缩格式。

---

# 八、查询执行问题与解决方案

---

## 问题：聚合计算慢

例如：

```sql
SUM

AVG

COUNT
```

需要扫描：

```text
十亿行
```

---

## 解决方案1：Query Compilation

过程：

```text
SQL

↓

Machine Code

↓

Execution
```

类似：

```text
JIT
```

优势：

```text
减少解释执行成本
```

---

## 解决方案2：Vectorized Execution

批量处理：

```text
1000条

↓

一次处理
```

而非：

```text
逐行处理
```

利用：

```text
SIMD
CPU Cache
Pipeline
```



```text
Full Scan
```

# 十一、全文检索问题与解决方案

---

## 问题

查询：

```text
red apples
```

需要：

```text
同时满足多个关键词
```

普通索引无效。

---

## 解决方案：Inverted Index

结构：

```text
Term

↓

Document List
```

例如：

```text
apple

↓

doc1
doc5
doc8
```

查询：

```text
red AND apples
```

实际：

```text
Bitmap AND
```

核心系统：

```text
Lucene

Elasticsearch

Solr
```
