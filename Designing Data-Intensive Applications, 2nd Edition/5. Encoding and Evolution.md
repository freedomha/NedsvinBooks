# DDIA 第5章：Avro 与 Protobuf 总结——问题与解决方案

## 核心问题

现代分布式系统面临一个根本矛盾：

```text
代码不断升级
数据长期存在
```

例如：

```text
OMS V1
   ↓
Kafka Event V1
   ↓
存储

半年后

OMS V2
   ↓
Kafka Event V2
```

此时系统必须解决：

- 新程序读取旧数据
- 旧程序读取新数据
- 微服务滚动升级
- Kafka长时间保留消息
- 数据库保存多年历史数据

否则：

```text
升级 = 数据损坏
```

# 解决方案

## Backward Compatibility

新代码读取旧数据

```text
New Code
    ↓
Old Data
```

例如：

```json
{
  "userName":"Martin"
}
```

新代码：

```java
userName
email
```

没有：

```text
email
```

使用：

```text
default value
```

---

## Forward Compatibility

旧代码读取新数据

```text
Old Code
    ↓
New Data
```

旧程序看到：

```json
{
  "userName":"Martin",
  "email":"..."
}
```

不认识：

```text
email
```

直接忽略。

# 问题4：字段如何标识？

## 方案1：Protobuf

核心思想：

```text
Tag = Identity
```

Schema：

```proto
string user_name = 1;
string email = 2;
```

---

编码：

```text
1 = Martin
2 = abc@test.com
```

---

优点

```text
编码速度快
空间小
```

---

缺点

```text
Tag必须永久维护
```

---

# Protobuf 解决方案

行业规则：

```proto
Tag Once Used
Never Reuse
```

删除字段：

```proto
reserved 2;
```

---

允许：

```proto
email
↓
userEmail
```

改名字。

---

禁止：

```proto
email=2

改

email=5
```

# Protobuf 与 Avro 最终对比

| 维度 | Protobuf | Avro |
|--------|----------|-------|
| 来源 | Google | Apache |
| 标识方式 | Tag | Field Name |
| 编码大小 | 很小 | 更小 |
| 性能 | 极高 | 很高 |
| Schema演化 | 优秀 | 更优秀 |
| 动态Schema | 一般 | 极强 |
| RPC | 最佳 | 一般 |
| Kafka | 可用 | 主流 |
| Data Lake | 较少 | 主流 |
| Code Generation | 很强 | 一般 |
| gRPC | 标准 | 很少 |
| Schema Registry | 支持 | 主流 |
