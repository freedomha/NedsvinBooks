## 第一层 — 概览（Overview）

### 背景与动机
第 11 章确立了**批处理**：读取*有界*输入，产出*派生数据*。整个模型假设你知道输入何时结束。但大多数真实数据是**无界**的——事件随时间不断产生。批处理作业用固定时间片（每天/每小时）伪装成“流”，代价是延迟（每日任务要等到一天后才反映输入）。

**流处理**去掉固定时间片：事件一来就处理，持续不断。

### 核心问题
| | 批处理 | 流处理 |
|---|---|---|
| 输入 | 有界（有限、已知大小） | 无界（随时间到达） |
| “完成？” | 是——输入耗尽时 | 永不 |
| 延迟 | 分钟~小时 | 毫秒~秒 |
| 故障模型 | 重跑整个作业 | 必须在飞行中存活并保留状态 |

本章的深层问题：**如何从一个永不停止的系统中，获得批处理的好特性（可复现、容错、易推理）？**

### 章节路线图（四个乐章）
1. **传输事件流** — 事件如何移动：消息系统 vs 基于日志的 broker（Kafka）。
2. **数据库与流** — 二元性：流就是数据库的*变更日志*；变更数据捕获（CDC）与事件溯源（event sourcing）。
3. **处理流** — 你拿事件*做什么*：CEP、分析、物化视图、窗口、连接（join）、容错。
4. **统一洞见**（贯穿全章） — **状态、流与不可变性**：从不可变事件日志派生当前状态；通过重放来重建/恢复/重处理。

### 关键概念地图
| 概念 | 一句话定义 | 位置 |
|---|---|---|
| 事件 Event | 小、不可变、自包含、记录某时刻发生的事（带时间戳） | §传输事件流 |
| 消息 broker | 解耦生产者与消费者的缓冲 | §消息系统 |
| 基于日志的 broker | 追加写、分区、可重放的日志（Kafka） | §基于日志的 Broker |
| 偏移 Offset | 消费者在分区中的位置（持久化） | §消费者偏移 |
| CDC | 把数据库的提交日志流式发给其他系统 | §变更数据捕获 |
| 事件溯源 | 应用状态 = 对不可变事件日志的折叠 | §CDC vs 事件溯源 |

## 第二层 — 概念详解（Concept Detail）

### A 部分 — 传输事件流

**事件**是基本单位：不可变对象，带时间戳；编码为文本/JSON/二进制（见第 5 章）。例子：一次页面浏览、一次传感器读数、Web 服务器日志的一行。

#### 消息系统
两种 生产者→消费者 拓扑：
- **直连消息**（UDP 多播、HTTP/webhook、ZeroMQ）：生产者直发消费者。脆弱——消费者宕机时无缓冲。
- **消息 broker**（中介）：缓冲消息，解耦收发，应对慢/故障消费者。

**消息 broker 与数据库对比** — broker 本质是个为*瞬时*数据优化的数据库：
- 消息被消费后即删除（数据库保留）。
- broker 优化吞吐 + 低延迟；几乎不查询。
- 二者都落盘保证持久性；都做复制。

**多消费者** — 两种投递模式：
| 模式 | 行为 | 场景 |
|---|---|---|
| **负载均衡** | 每条消息 → N 个消费者之一；分摊工作 | 横向扩展处理 |
| **扇出 Fan-out** | 每条消息 → *所有*消费者 | 多个独立订阅方 |

**确认与重投** — 消费者处理完发 ACK；超时未 ACK 的消息被重投。张力：**至少一次**（不 ACK 就重投，可能重复处理）vs **至多一次**（发送即删，可能丢失）。精确一次需要额外工作（见容错）。

#### 基于日志的消息 Broker（Kafka 风格）
- **用日志存消息**：topic = 分区、复制、追加写日志。生产者追加；消费者顺序读。
- **日志 vs 传统消息**：
  - 传统：消费即删 → 不可重放。
  - 日志型：消息保留；消费者用**偏移** → 可从任意点重放。
- **消费者偏移**：每个消费者按分区记录偏移；重启后从上次偏移继续。偏移 = 让处理**确定性且可重放**的机制。
- **磁盘占用**：顺序写很快；保留按时间/大小；旧段删除。
- **重放旧消息**：从偏移 0 重新发布 → 重处理历史（重建状态/修 bug 的杀手锏）。

**对比（取自章末总结表）：**
| | AMQP/JMS 风格 broker | 基于日志的 broker |
|---|---|---|
| 投递 | 推送，消费即删 | 拉取，保留 + 偏移 |
| 重放 | 否 | 是 |
| 消费者模型 | 竞争消费者 | 独立偏移读取者 |
| 擅长 | 任务队列 | 事件日志 / 流处理 |

### B 部分 — 数据库与流

#### 保持系统同步
问题：数据散落多处（DB、缓存、搜索索引、数仓）。每处都要反映其他处。旧解法两种：
- 双重写入（应用同时写 DB *和* 缓存）→ 部分失败时不一致。
- 周期批处理 ETL → 陈旧。

更好：从**一份变更日志**派生所有视图。

#### 变更数据捕获（CDC）
- 捕获数据库的**提交日志**（WAL）并流式发出。
- **实现 CDC**：解析 WAL / 用逻辑复制；为增/改/删发事件。
- **初始快照**：新消费者需要当前状态 → 先打快照，再切到实时日志（快照 + 增量）。
- **日志压缩 Log compaction**：只保留每个 key 的*最新*值（按主键做 key）。无需无限历史即可“从日志重建一张表”。
- **变更流的 API 支持**：现代数据库暴露变更流（如 MongoDB change streams、Postgres 逻辑解码）。
- **CDC vs 事件溯源**：
  - CDC：日志是有状态数据库变更的*副作用*。
  - 事件溯源：事件日志*本身就是*真相源；状态是派生的。
- **CDC 与数据库 schema**：schema 变更需传播；日志要携带 schema 版本信息。

#### 状态、流与不可变性
- **不可变事件的优势**：可审计、可重放、时间查询、解耦。
- **并发控制**：不可变追加日志规避许多锁问题（每分区追加天然有序）。
- **不可变性的局限**：存储增长；需压缩/快照；并非所有领域天然适合事件溯源；GDPR“被遗忘权”与不可变性冲突（需用加密销毁 crypto-shredding）。

### C 部分 — 处理流

#### 流处理的用途
- **复杂事件处理 CEP**：在事件流上做模式匹配（如“3 次登录失败然后一笔提款”）。
- **流分析**：窗口上的聚合（计数、均值）。
- **维护物化视图**：事件到达时保持派生数据集新鲜。
- **增量视图维护**：用*增量*而非重算来更新视图。
- **流上搜索**：事件流入时建索引（如 Elasticsearch 摄取）。
- **事件驱动架构 vs RPC**：异步事件 vs 同步请求/响应；事件解耦服务，但让流程推理更复杂。

#### 关于时间的推理 ⭐（最实用的小节）
- **事件时间 vs 处理时间**：
  - *事件时间* = 事件发生时刻（事件内时间戳）。
  - *处理时间* = 你处理它的时刻。
  - 二者因排队、网络故障、重启、重处理而背离。
  - **混淆二者 → 脏数据。** 例：用处理时间衡量“每秒请求数”，重启后排空积压时会假现尖峰。
- **迟到事件 Straggler**：事件在其窗口关闭*之后*才到。需水位线 watermark / 允许延迟 / 窗口留 slack。
- **用谁的时钟？**：多机事件 → 时钟偏移。优先事件时间戳；警惕 NTP 漂移（见第 8 章时钟）。
- **星球大战类比**：上映顺序（处理时间）≠ 剧集顺序（事件时间）。算法必须能处理这种错位。

**窗口类型**（按事件时间对事件分组）：
| 窗口 | 定义 | 例子 |
|---|---|---|
| **滚动 Tumbling** | 固定、不重叠的桶 | 1 分钟计数，无重叠 |
| **跳跃 Hopping** | 固定大小、固定滑动（重叠） | 每 30 秒一个 1 分钟窗口 |
| **滑动 Sliding** | 彼此在 T 之内的所有事件 | “最近 5 分钟”滚动 |
| **会话 Session** | 基于间隔：按活动分组，空闲超过 gap 即关 | 用户会话 |

#### 流连接（Stream Joins）
三种，每种都需在一侧持有**状态**并在另一侧查询：
1. **流–流（窗口连接）**：在时间窗口内连接两流事件。
2. **流–表（流 enrichment）**：用查表丰富流事件（如给点击附上用户档案）。
   ```sql
   SELECT follows.follower_id AS timeline_id,
          array_agg(posts.* ORDER BY posts.timestamp DESC)
   FROM posts
   JOIN follows ON follows.followee_id = posts.sender_id
   GROUP BY follows.follower_id
   ```
   时间线就是该连接的*物化视图*，每次底层变化即刷新。
3. **表–表（物化视图维护）**：把两个变化表的连接维护成视图。
- **乘积法则类比** 🔢：若流是表的*导数*（stream = d(table)），连接是乘积 u·v，则连接视图的变化遵循微积分乘积法则：
  > **(u·v)′ = u′·v + u·v′**
  > 即 `posts` 的变更与当前 `follows` 连接，`follows` 的变更与当前 `posts` 连接。
- **连接的时间依赖性**：分区内事件顺序很重要（先关注后取关 ≠ 先取关后关注）。单分区顺序保留；跨分区不保证。

#### 容错
- **微批与检查点**（Spark Streaming）：切成极小批次；检查点偏移 + 状态；失败重跑该批。推理简单，延迟略高。
- **原子提交重访**：跨流 + 输出的分布式 2PC → 精确一次但重；通常不值。
- **幂等 Idempotence** 🔑：让操作可安全重试。
  > *幂等* = 执行一次或多次效果相同。删 key 是幂等的；计数器自增不是。
  >
  > 给非幂等操作加元数据使其幂等：把触发写入的消息的 **Kafka 偏移** 连同值一起写出；若偏移 ≤ 已应用的，就跳过。要求：相同消息按相同顺序重放（日志 broker）+ 处理确定性 + 无并发写者。
- **失败后重建状态**：
  - 远端数据存储 + 复制（每条消息查远端，慢）。
  - 本地状态 + 周期快照到持久存储（Flink 把算子状态快照到 DFS；Kafka Streams 把状态变更发到压缩 topic）。
  - 或**从输入流重建**：重放窗口对应事件（无需复制）。

## 第三层 — 设计经验、要点与关联

### 各机制的优劣权衡
| 机制 | 优势 | 代价 / 弱点 |
|---|---|---|
| 消息 broker（消费即删） | 简单、低延迟 | 不可重放；难重建 |
| 基于日志的 broker | 可重放、可重放、可重放 | 磁盘；偏移记账 |
| CDC | 跨系统一致同步 | schema 演进痛苦 |
| 事件溯源 | 完整审计 + 重放 | 存储；不可变性受限 |
| 窗口（事件时间） | 正确的时间聚合 | 水位线/延迟复杂度 |
| 幂等 | 廉价的精确一次 | 需确定性 + 有序重放 |
| 检查点 | 类批的故障模型 | 延迟略高 |

### 统一洞见（本章真正想说的）
> **流是表的导数；状态是流的积分。**
> 持有一份*不可变*事件日志 → 你可派生任意物化视图、失败后重建状态、修 bug 后重处理、并保持异构系统同步。这正是批与流的调和：流给了你批的可复现性，却没有它的延迟。

这重述了全书：第 11 章（批）与第 12 章（流）是**同一派生数据思想的两种视图**——而日志是桥梁。

### 🔗 与你*自己*系统的关联
你身处流处理的相邻领域——这些并非抽象：
- **APM RCA（拓扑 + span + Prometheus）**：你的 span *就是*事件流。“事件时间 vs 处理时间”解释了为何 RCA 级联分析必须基于 **span 时间戳（事件时间）**，而非摄取时间——否则一次积压重放会被误判为尖峰（正是本章警告的假阳性）。迟到/追踪乱序问题直接对应星球大战类比。
- **云容量 Prophet 预测**：Prophet 工作在*事件/观测时间*。“重放旧消息”思想即你做回测的方式：从偏移 0 重新发布指标流并重跑预测，以验证置信区间退化修复。日志压缩 ↔ 你的 14 点降采样阈值（每桶保留最新值）。
- **幂等**：你的 `ForecastValidator`/`MetricCleaner` 应幂等——给每条预测打上输入窗口偏移，重试不会重复插入（正是本章的同款模式）。
- **物化视图 / 增量维护**：你的 golden-signals 仪表盘就是指标流上的物化视图；窗口选择（滚动 vs 跳跃）影响告警噪声。
