## Layer 1 — Overview

### Background & Motivation
Chapter 11 established **batch processing**: read a *bounded* input, produce *derived data*. The whole model assumes you know when the input ends. But most real data is **unbounded** — users keep producing events forever. Batch jobs fake "streaming" by chopping time into fixed slices (daily/hourly), but that adds latency (a daily job reflects input only a day later).

**Stream processing** drops the fixed slices: process each event as it arrives, continuously.

### The Core Problem
| | Batch | Stream |
|---|---|---|
| Input | Bounded (finite, known size) | Unbounded (arrives over time) |
| "Done?" | Yes — when input exhausted | Never |
| Latency | Minutes–hours | Milliseconds–seconds |
| Fault model | Re-run whole job | Must survive failure *mid-flight* while keeping state |

The deep question of the chapter: **how do you get the good properties of batch (reproducibility, fault tolerance, easy reasoning) from a system that never stops?**

### Chapter Roadmap (the 4 movements)
1. **Transmitting Event Streams** — how events move: messaging systems vs log-based brokers (Kafka).
2. **Databases and Streams** — the duality: a stream is the *change feed* of a database; Change Data Capture (CDC) and event sourcing.
3. **Processing Streams** — what you *do* with events: CEP, analytics, materialized views, windows, joins, fault tolerance.
4. **The unifying insight** (woven throughout) — **state, streams, and immutability**: derive current state from an immutable event log; replay to rebuild/recover/reprocess.

## Layer 2 — Concept Detail

### Part A — Transmitting Event Streams

**Events** are the unit: immutable objects with a timestamp; encoded as text/JSON/binary (Ch.5). Examples: a page view, a sensor reading, one line of a web-server log.

#### Messaging Systems
Two producer→consumer topologies:
- **Direct messaging** (UDP multicast, HTTP/webhooks, ZeroMQ): producer sends straight to consumer. Fragile — no buffer if consumer is down.
- **Message broker** (intermediary): buffers messages, decouples send/receive, handles slow/failed consumers.

**Message brokers compared to databases** — a broker is essentially a DB optimized for *transient* data:
- Messages are deleted after consumption (DB keeps them).
- Brokers optimize for throughput + low latency; little querying.
- Both persist to disk for durability; both replicate.

**Multiple consumers** — two delivery patterns:
| Pattern | Behavior | Use case |
|---|---|---|
| **Load balancing** | Each message → one of N consumers; partitions the work | Scale-out processing |
| **Fan-out** | Each message → *all* consumers | Different independent subscribers |

**Acknowledgments & redelivery** — consumer ACKs after processing; un-ACKed messages are redelivered after a timeout. Tension: **at-least-once** (redeliver on no-ACK, may double-process) vs **at-most-once** (delete on send, may lose). Exactly-once needs extra work (see Fault Tolerance).

#### Log-based Message Brokers (Kafka-style)
- **Using logs for message storage**: topic = partitioned, replicated, append-only log. Producers append; consumers read sequentially.
- **Logs vs traditional messaging**:
  - Traditional: message deleted on consume → no replay.
  - Log-based: messages retained; consumers use **offsets** → can replay from any point.
- **Consumer offsets**: each consumer tracks its offset per partition; on restart, resumes from last offset. Offset = the mechanism that makes processing **deterministic & replayable**.
- **Disk space usage**: sequential writes are fast; retention is time/size-based; old segments deleted.
- **Replaying old messages**: republish from offset 0 → reprocess history (the killer feature for rebuilding state / fixing bugs).

**Comparison (from chapter's summary table):**
| | AMQP/JMS-style broker | Log-based broker |
|---|---|---|
| Delivery | Push, delete-on-consume | Pull, retained + offset |
| Replay | No | Yes |
| Consumer model | Competing consumers | Independent offset readers |
| Best for | Task queues | Event log / stream processing |

### Part B — Databases and Streams

#### Keeping Systems in Sync
Problem: data lives in many places (DB, cache, search index, DW). Each must reflect the others. Two old answers:
- Dual writes (app writes to DB *and* cache) → inconsistent on partial failure.
- Periodic batch ETL → stale.

Better: **derive all views from one log of changes.**

#### Change Data Capture (CDC)
- Capture the DB's **commit log** (WAL) and stream it out.
- **Implementing CDC**: parse WAL / use logical replication; emit events for inserts/updates/deletes.
- **Initial snapshot**: new consumers need the current state → take a snapshot, then switch to the live log (snapshot + delta).
- **Log compaction**: a topic where only the *latest* value per key is retained (keyed by PK). Enables "rebuild a table from the log" without infinite history.
- **API support for change streams**: modern DBs expose change streams (e.g., MongoDB change streams, Postgres logical decoding).
- **CDC vs event sourcing**:
  - CDC: log is a *side-effect* of mutating a stateful DB.
  - Event sourcing: the event log *is* the source of truth; state is derived.
- **CDC and DB schemas**: schema changes must propagate; the log carries schema versioning concerns.

#### State, Streams, and Immutability
- **Advantages of immutable events**: auditability, replayability, temporal queries, decoupling.
- **Concurrency control**: immutable append-only logs sidestep many lock issues (append is naturally ordered per partition).
- **Limitations of immutability**: storage growth; need compaction/snapshots; not all domains are naturally event-sourced; GDPR "right to be forgotten" clashes with immutability (needs crypto-shredding).

### Part C — Processing Streams

#### Uses of Stream Processing
- **Complex event processing (CEP)**: pattern matching over event streams (e.g., "3 failed logins then a withdrawal").
- **Stream analytics**: aggregations (counts, averages) over windows.
- **Maintaining materialized views**: keep a derived dataset fresh as events arrive.
- **Incremental view maintenance**: update a view by *diff* rather than recompute.
- **Search on streams**: index events as they flow (e.g., Elasticsearch ingest).
- **Event-Driven Architectures vs RPC**: async events vs synchronous request/response; events decouple services but complicate reasoning about flow.

#### Reasoning About Time ⭐ (most practically important section)
- **Event time vs processing time**:
  - *Event time* = when it happened (timestamp in the event).
  - *Processing time* = when you processed it.
  - They diverge due to queueing, network faults, restarts, reprocessing.
  - **Confusing them → bad data.** Example: measuring "requests/sec" by processing time spikes falsely when you drain a backlog after a restart.
- **Handling straggler events**: an event arrives *after* its window already closed. Need watermark / allowed-lateness / keep windows open for slack.
- **Whose clock?**: events from many machines → clock skew. Prefer event timestamps; beware NTP drift (cf. Ch.8 clocks).
- **Star Wars analogy**: release order (processing time) ≠ episode order (event time). Algorithms must handle this.

**Types of windows** (for grouping events by event time):
| Window | Definition | Example |
|---|---|---|
| **Tumbling** | Fixed, non-overlapping buckets | 1-min counts, no overlap |
| **Hopping** | Fixed size, fixed slide (overlap) | 1-min window every 30s |
| **Sliding** | All events within T of each other | "last 5 min" rolling |
| **Session** | Gap-based: group by activity, close after idle gap | User sessions |

#### Stream Joins
Three kinds, each requires holding **state** from one side and querying it on the other:
1. **Stream–stream (window join)**: join events from two streams within a time window.
2. **Stream–table (stream enrichment)**: enrich a stream event by looking up a table (e.g., add user profile to a click).
   ```sql
   SELECT follows.follower_id AS timeline_id,
          array_agg(posts.* ORDER BY posts.timestamp DESC)
   FROM posts
   JOIN follows ON follows.followee_id = posts.sender_id
   GROUP BY follows.follower_id
   ```
   The timeline is a *materialized view* of this join, refreshed on every change.
3. **Table–table (materialized view maintenance)**: maintain the join of two changing tables as a view.
- **The product-rule analogy** 🔢: if a stream is the *derivative* of a table (stream = d(table)), and a join is a product u·v, then changes to the joined view follow the calculus product rule:
  > **(u·v)′ = u′·v + u·v′**
  > i.e. a change in `posts` is joined with current `follows`, and a change in `follows` is joined with current `posts`.
- **Time-dependence of joins**: event order within a partition matters (follow-then-unfollow ≠ unfollow-then-follow). Single-partition order is preserved; cross-partition is not.

#### Fault Tolerance
- **Microbatching & checkpointing** (Spark Streaming): process in tiny batches; checkpoint offsets + state; replay a batch on failure. Simpler reasoning, slightly higher latency.
- **Atomic commit revisited**: distributed 2PC across stream + output → exactly-once but heavy; rarely worth it.
- **Idempotence** 🔑: make operations safe to retry.
  > *Idempotent* = same effect if applied once or many times. Deleting a key is idempotent; incrementing a counter is not.
  >
  > Make non-idempotent ops idempotent with metadata: write the **Kafka offset** of the triggering message alongside the value; skip if offset ≤ last applied. Requires: same messages replayed in same order (log broker) + deterministic processing + no concurrent writers.
- **Rebuilding state after a failure**:
  - Remote datastore + replicate (slow per-message queries).
  - Local state + periodic snapshot to durable storage (Flink snapshots operator state to a DFS; Kafka Streams ships state changes to a compacted topic).
  - Or **rebuild from the input stream** by replaying the window's events (no replication needed).

## Layer 3 — Design Lessons, Takeaways & Connections

### Strengths / Trade-offs of each mechanism
| Mechanism | Strength | Cost / weakness |
|---|---|---|
| Message broker (delete-on-consume) | Simple, low latency | No replay; hard to rebuild |
| Log-based broker | Replay, replay, replay | Disk; offset bookkeeping |
| CDC | Consistent cross-system sync | Schema evolution pain |
| Event sourcing | Full audit + replay | Storage; immutability limits |
| Windows (event-time) | Correct time-based analytics | Watermarks/lateness complexity |
| Idempotence | Cheap exactly-once | Needs determinism + ordered replay |
| Checkpointing | Batch-like fault model | Slightly higher latency |

### The unifying insight (what the chapter is really about)
> **A stream is the derivative of a table; state is the integral of a stream.**
> Hold an *immutable* event log → you can derive any materialized view, rebuild state after failure, reprocess after a bug fix, and keep heterogeneous systems in sync. This is the.batch-vs-stream reconciliation: streams give you batch's reproducibility *without* its latency.

This reframes the whole book: Ch.11 (batch) and Ch.12 (stream) are **two views of the same derived-data idea** — and the log is the bridge.

### 🔗 Connections to *your* systems
You live in streaming-adjacent land — these aren't abstract:
- **APM RCA (topology + spans + Prometheus)**: your spans *are* an event stream. "Event time vs processing time" explains why RCA cascade analysis must key on **span timestamps (event time)**, not ingest time — otherwise a backlog replay looks like a spike (exactly the false-positive the chapter warns about). Straggler/trace-ordering issues map directly to the Star Wars analogy.
- **cloud-capacity Prophet forecasts**: Prophet works in *event/observation time*. The "replay old messages" idea is how you'd backtest: republish the metric stream from offset 0 and re-run the forecast to validate confidence-interval degeneration fixes. Log compaction ↔ your 14-point downsampling threshold (keep latest per bucket).
- **Idempotence**: your `ForecastValidator`/`MetricCleaner` should be idempotent — tag each forecast with the input window offset so a retry doesn't double-insert (the chapter's exact pattern).
- **Materialized views / incremental maintenance**: your golden-signals dashboards are materialized views over the metric stream; window choice (tumbling vs hopping) changes alert noise.
