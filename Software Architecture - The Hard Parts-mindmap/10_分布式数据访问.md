# 第10章 分布式数据访问 — 问题与解决方案

## 章节概述

在单体系统使用单一数据库时，开发者很少为读取数据库表而烦恼。SQL表连接是家常便饭，一个简单的查询就能在一次数据库调用中获取所有需要的数据。然而，当数据被拆分到由不同服务独立拥有的独立数据库或schema中时，**读操作的数取访问**开始变得困难。

本章描述了服务如何获取对它们不拥有的数据（即在需要数据的服务的有界上下文之外的数据）的读访问权限。书中讨论了四种数据访问模式：

| 模式 | 英文名 | 核心理念 |
|------|--------|----------|
| 服务间通信模式 | Interservice Communication Pattern | 通过远程调用请求数据 |
| 列模式复制模式 | Column Schema Replication Pattern | 跨表复制数据列 |
| 复制缓存模式 | Replicated Caching Pattern | 通过内存复制缓存共享数据 |
| 数据域模式 | Data Domain Pattern | 共享schema合并表 |

每种模式都有其优缺点——即**权衡（Trade-offs）**。本章以Wishlist Service（心愿单服务）和Catalog Service（目录服务）为例来阐述每种模式。

> **示例场景**：Wishlist Service维护客户的心愿单（客户ID、商品ID、添加日期），但它缺少商品描述（item_desc），该数据由Catalog Service在紧密的有界上下文中拥有。当用户查看心愿单时需要返回商品描述，因此架构师必须使用本章中的某一种数据访问模式来获取这些数据。

## 核心概念与定义

### 1. 有界上下文（Bounded Context）
数据由某个特定的服务拥有和管理，其他服务不能直接访问。数据所有权（Data Ownership）和变更控制（Change Control）集中在拥有方。

### 2. 数据耦合（Data Coupling）
当服务需要访问不属于自己的数据时，就会产生各种形式的耦合：
- **语义耦合（Semantic Coupling）**：一个服务在功能上依赖另一个服务的数据
- **静态耦合（Static Coupling）**：一个服务必须直接依赖另一个服务的接口来获取数据

### 3. 数据一致性（Data Consistency）
在分布式架构中，当数据在多个地方存在副本时，如何保证数据的一致性是一个核心挑战。一致性需求的高低直接影响模式选择。

### 4. 数据延迟类型
- **网络延迟（Network Latency）**：数据包在服务间传输的时间（30ms-300ms）
- **安全延迟（Security Latency）**：端点授权所需的额外时间（20ms-400ms）
- **数据延迟（Data Latency）**：多次数据库调用累积的时间（10ms-50ms/次）

### 5. 缓存模型对比

| 缓存模型 | 数据位置 | 是否同步 | 适用场景 |
|----------|----------|----------|----------|
| 单体内存缓存 | 每个服务内存内部 | 否 | 提升各自服务响应性 |
| 分布式缓存 | 外部缓存服务器 | 共享 | 一般数据共享 |
| 复制缓存 | 每个服务内存内部 | 是 | 分布式数据访问 |

## 问题清单

### 问题1：跨服务读数据性能低下
- 服务需要的数据不在自己的数据库中
- 每次请求都需要通过远程调用获取
- 网络延迟 + 安全延迟 + 数据延迟累加，可能高达**1秒**

### 问题2：服务间耦合导致可用性问题
- 获取数据的服务依赖数据拥有方服务必须在线
- 被依赖的服务不可用 → 依赖方服务也不可用
- 容错性（Fault Tolerance）差

### 问题3：扩展性受限
- 一个服务扩展时，它依赖的服务也必须同步扩展
- 吞吐量（Throughput）瓶颈

### 问题4：数据一致性管理
- 当在多个地方存储数据副本时
- 数据更新需要同步传播
- 高更新频率下的数据不一致风险

### 问题5：数据所有权治理
- 当数据被复制到其他服务的表中
- 其他服务可能意外修改数据
- 破坏有界上下文的边界

### 问题6：高数据量场景的可行性
- 内存缓存有容量限制（如超过500MB）
- 多实例的累积内存占用问题

### 问题7：云环境下的配置难题
- 复制缓存依赖TCP/IP广播和查找
- 容器化环境中IP地址不固定
- 防火墙和可用区交叉问题

## 解决方案（四种数据访问模式）

### 模式一：服务间通信模式（Interservice Communication Pattern）

#### 描述
这是分布式系统中最常见的数据访问模式。当一个服务需要读取它无法直接访问的数据时，它通过某种远程访问协议向拥有该数据的服务发起请求。

#### 工作方式
```
WishlistService → (REST/消息) → CatalogService → 数据库
     ↓                              ↓
  远程调用                    查询并返回item_desc
```

Wishlist Service每次获取客户心愿单时，都要向Catalog Service发起同步远程调用，传入商品ID列表，换取对应的商品描述列表。

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 实现简单 | 网络、数据、安全延迟导致性能差 |
| 无数据量问题 | 扩展性和吞吐量问题 |
| — | 无容错性（可用性问题） |
| — | 需要服务间契约 |

---

### 模式二：列模式复制模式（Column Schema Replication Pattern）

#### 描述
将需要的列（column）复制到其他服务的数据库表中，使数据在另一个有界上下文中也可用，无需远程调用即可访问。

#### 工作方式
```
CatalogService: product (item_id, item_desc, ...) 
          ↓ 异步同步（队列/主题/事件流）
WishlistService: wishlist (customer_id, item_id, date_added, item_desc)
```

将`item_desc`列添加到Wishlist表中，Wishlist Service通过简单的SQL JOIN即可获取所有数据。

#### 数据同步机制
- Catalog Service在创建、删除或修改商品时，必须通知Wishlist Service
- 通常通过**异步通信**实现（队列、主题或事件流）
- 除非需要即时事务同步，否则异步通信优于同步通信（提升响应性、减少可用性依赖）

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 数据访问性能好 | 数据一致性问题 |
| 无扩展性和吞吐量问题 | 数据所有权问题 |
| 无容错性问题 | 需要数据同步机制 |
| 无服务依赖 | — |

#### 适用场景
- 数据聚合（Data Aggregation）
- 报表场景（Reporting）
- 其他模式因大数据量、高响应性要求或高容错要求而不适用的场景

> ⚠️ **注意**：作者通常不建议在Wishlist Service和Catalog Service这种场景使用此模式，但在特定情况下可以考虑。

---

### 模式三：复制缓存模式（Replicated Caching Pattern）

#### 描述
利用复制式内存缓存（Replicated In-Memory Caching），使其他服务需要的数据可以在每个服务的内存中直接获取，而无需主动请求。每个服务持有相同的缓存数据，通过缓存产品在后台异步同步。

#### 工作方式
```
CatalogService: [写] 内存缓存（product descriptions）
     ↕ 缓存同步（后台异步传播）
WishlistService: [只读] 内存副本（product descriptions）
```

- Catalog Service拥有缓存的写入权限（唯一可修改缓存的服务）
- Wishlist Service持有缓存的只读副本
- 当Catalog Service更新商品描述时，缓存产品会自动更新Wishlist Service中的缓存

#### 支持的缓存产品
- Hazelcast
- Apache Ignite
- Oracle Coherence

#### 启动依赖说明
- **初始启动**：Catalog Service必须先于Wishlist Service启动（因为需要填充缓存）
- **后续实例**：一旦已有Wishlist实例在运行，新实例可以从其他Wishlist实例获取缓存数据
- **运行中**：缓存建立后，Catalog Service的上下线不影响Wishlist Service

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 极好的数据访问性能（纳秒级） | 云和容器化环境配置困难 |
| 无扩展性和吞吐量问题 | 不适合大数据量（>500MB需谨慎） |
| 良好的容错性 | 不适合高更新频率的数据 |
| 数据保持一致 | 初始启动有服务依赖 |
| 数据所有权得到保留 | — |

#### 数据量评估公式
```
总内存 = 缓存大小 × 需要该数据的服务实例总数
```
例如：500MB缓存 × 5个实例 = 2.5GB总内存

#### 不适用场景
- **高数据量**：缓存过大导致内存浪费
- **高更新频率**：如产品库存计数等易变数据
- **云环境**：TCP/IP广播和IP动态分配带来配置挑战

---

### 模式四：数据域模式（Data Domain Pattern）

#### 描述
将多个服务共享的数据表放在同一个schema中，形成一个更广的有界上下文。服务通过简单的SQL连接（JOIN）访问所需数据，无需任何远程调用、数据复制或缓存同步。

#### 工作方式
```
共享Schema (Data Domain):
├── wishlist (customer_id, item_id, date_added)
└── product (item_id, item_desc, ...)
     ↑                    ↑
WishlistService      CatalogService
   (连接同一个schema)
```

Wishlist和Product表不再由任一服务单独拥有，而是共享于一个数据域中。

#### 数据库完整性特性
在此模式中，以下数据库特性得以保留：
- **外键约束（Foreign-Key Constraints）**
- **视图（Views）**
- **存储过程（Stored Procedures）**
- **触发器（Triggers）**

#### 优缺点

| 优点 | 缺点 |
|------|------|
| 数据访问性能好 | 更广的有界上下文，管理数据变更困难 |
| 无扩展性和吞吐量问题 | 数据所有权治理挑战 |
| 无容错性问题 | 数据访问安全问题 |
| 无服务依赖 | — |
| 数据保持一致 | — |

#### 关键权衡
- **Schema即契约**：表结构成为服务间的契约，这既是优点也是缺点
- 与Interservice Communication和Replicated Caching不同，这些模式在表结构之上形成了抽象层，允许在不影响其他服务的情况下变更表结构
- Data Domain模式中，表结构变更可能影响所有共享该schema的服务
- 安全性：一个服务可能访问到它不该访问的数据

## 关键权衡对比

### 四种模式整体对比

| 维度 | 服务间通信 | 列模式复制 | 复制缓存 | 数据域 |
|------|-----------|-----------|---------|--------|
| **数据访问性能** | ❌ 差 | ✅ 好 | ✅ 极好 | ✅ 好 |
| **容错性** | ❌ 差 | ✅ 好 | ✅ 好 | ✅ 好 |
| **扩展性** | ❌ 差 | ✅ 好 | ✅ 好 | ✅ 好 |
| **实现复杂度** | ✅ 简单 | ❌ 高 | ❌ 高 | ✅ 中等 |
| **数据一致性** | ✅ 强一致 | ❌ 问题 | ✅ 好 | ✅ 强一致 |
| **服务解耦** | ❌ 紧耦合 | ✅ 解耦 | ✅ 基本解耦 | ✅ 完全解耦 |
| **数据所有权** | ✅ 清晰 | ❌ 模糊 | ✅ 清晰 | ❌ 模糊 |
| **大数据量** | ✅ 适用 | ❌ 问题 | ❌ 问题 | ✅ 适用 |
| **高更新频率** | ✅ 适用 | ❌ 问题 | ❌ 问题 | ✅ 适用 |
| **云环境适配** | ✅ 好 | ✅ 好 | ❌ 难 | ✅ 好 |

### 选择决策树

1. **是否可以接受远程调用的性能开销？** → 服务间通信模式（最简单）
2. **数据一致性是否关键？且数据量大/更新频繁？** → 数据域模式
3. **数据量小、更新频率低、需要高性能？** → 复制缓存模式
4. **需要高性能但复制缓存不适用？** → 列模式复制模式

## Sysops Squad案例：Ticket Assignment的数据访问

### 背景
Ticket Assignment Service需要频繁访问专家档案表（expert profile table），但该表由User Management Service拥有。直接远程调用不可行，因为票据分配算法对数据库查询量太大。

### 备选方案分析

| 方案 | 评估结果 |
|------|---------|
| **服务合并** | ❌ 排除 — 服务属于完全不同的领域 |
| **共享数据域** | ❌ 排除 — Ticket Assignment Service不能同时连接两个不同的数据库 |
| **服务间通信** | ⚠️ 备选 — 有性能和容错问题 |
| **复制缓存** | ✅ 选择 — 数据量小（~1.2MB），数据相对静态 |

### 数据量估算

| 参数 | 数值 |
|------|------|
| 专家总数 | 900 |
| 每个专家所需数据 | ~1.3KB（技能、服务区域、标准排班） |
| 总缓存大小 | ~1200KB（约1.2MB） |
| User Management Service最大实例数 | 2 |
| Ticket Assignment Service最大实例数 | 4 |

### 最终决策：使用内存复制缓存

**决策理由**：
1. 数据量非常小（仅约1.2MB），内存占用可忽略
2. 数据相对静态（专家技能和排班信息变更不频繁）
3. 比服务间通信方案具有更好的性能和容错性
4. 共享数据域不可行（Ticket Assignment Service已连接票据数据域，无法再连接额外schema）

### 识别的权衡

1. **启动依赖**：
   - User Management Service必须在Ticket Assignment Service启动之前运行
   - 但一旦缓存填充完成，User Management Service的上下线不影响Ticket Assignment

2. **容错性优势**（相比服务间通信）：
   - 服务间通信方案：User Management Service宕机 → Ticket Assignment不可用
   - 复制缓存方案：缓存填充后User Management Service宕机 → Ticket Assignment正常运行

3. **技术风险**：
   - 团队对复制缓存缺乏经验
   - Taylen自愿进行产品调研和概念验证（POC）
   - Addison负责调研许可成本和部署环境的兼容性（可用区、防火墙等）

### ADR（架构决策记录）

**决策**：在User Management Service和Ticket Assignment Service之间使用复制缓存，User Management Service为写入操作的唯一拥有者。

**后果**：
- 启动首个Ticket Assignment Service实例时，至少需要一个User Management Service实例运行
- 需要缓存产品的许可成本
