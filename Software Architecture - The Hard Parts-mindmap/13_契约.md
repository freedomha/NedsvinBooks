# 第13章：契约（Contracts）

## 章节概览

第13章讨论分布式架构中一个横切性的核心议题——**契约（Contracts）**。契约是架构中各部分之间传递信息或表达依赖关系的格式，它不仅影响通信、一致性与协调三大架构力（如图13-1的三维交集模型所示），还作为"第四维度"贯穿所有这些维度。本章深入探讨了严格契约与松散契约的光谱、微服务中的契约实践、消费者驱动契约（Consumer-Driven Contracts）以及戳记耦合（Stamp Coupling）的正反两面应用。最后通过 Sysops Squad 的工单管理工作流案例展示了契约选择的实际决策过程。

核心论点是：**契约不是二元的，而是从严格到松散的一个连续光谱**，架构师需要根据具体上下文做出合适的取舍。

---

## 核心概念与定义

### 1. 契约的通用定义

> **Hard Parts 中的契约**：架构中各部分用于传递信息或表达依赖关系的格式。

这个定义比传统的 SOAP、REST、gRPC 等协议更广泛，涵盖了：
- 框架与库的传递性依赖
- 内部与外部集成点
- 缓存
- 架构中任何部分之间的通信

### 2. 严格契约 vs 松散契约光谱

契约并非二元的严格或松散，而是分布在一个连续光谱上（如图13-2所示）：

| 最严格 | → | → | → | 最松散 |
|--------|----|----|----|--------|
| RMI（远程方法调用）| gRPC | JSON Schema | REST / GraphQL | 纯名称-值对 |

- **严格契约**：要求名称、类型、顺序等所有细节精确匹配，不容歧义。例如 Java 中的 RMI 远程方法调用，完全模拟内部方法调用的语义。
- **松散契约**：仅传递最原始的名称-值对（name-value pairs），没有附加元数据、类型信息或约束。

### 3. 戳记耦合（Stamp Coupling）

**戳记耦合**是指在服务之间传递一个大型数据结构，但每个服务实际上只与其中的一小部分数据进行交互。它可能是一种模式，也可能是一种反模式，取决于使用场景。

### 4. 消费者驱动契约（Consumer-Driven Contracts）

一种**拉模型**的契约定义方式：由消费者（消费者服务）定义他们需要从提供者那里获取什么信息，并创建契约合同传递给提供者。提供者将此契约纳入其构建流程，并保证契约测试始终通过。这是一种自动化的架构治理机制。

### 5. 适应性函数（Fitness Functions）

用于在构建时自动验证契约约定的架构治理测试，弥补松散契约缺乏类型检查的不足。

## 问题清单

本章识别并讨论了以下关键架构问题：

### 问题1：严格契约导致的脆弱性
严格契约（如 gRPC、RMI）虽然提供了高契约保真度（contract fidelity），但也造成了紧密耦合，使集成架构变得脆弱。当契约发生变化时，所有共享该契约的服务都必须同步修改，产生连锁影响。

### 问题2：松散契约缺乏契约确定性
使用纯名称-值对传递消息虽然高度解耦，但缺乏类型检查、命名正确性验证等保障，容易出现拼写错误、字段缺失等问题。

### 问题3：戳记耦合的反模式
架构师在害怕未来变化（"万一会需要"心态）的驱使下，过度指定契约中的字段，导致：
- 不必要的契约断裂——Profile 中 Wishlist 不关心的字段变更也会导致契约破裂
- 浪费带宽——假设每次请求 500KB 载荷，每秒 2000 次请求就需要 1,000,000 KB/秒的传输量，而只传递必要信息可能仅需 400 KB/秒

### 问题4：微服务中解耦目标与契约保真度的矛盾
微服务架构追求高度解耦（bounded context），但同时需要保证服务间集成的契约正确性。这两个目标看似矛盾。

### 问题5：编排vs编排中的复杂工作流管理
在编排式（choreography）方案中处理复杂工作流时，需要一种机制来管理跨服务的工作流状态和事务一致性。

### 问题6：App Store部署延迟导致的契约同步难题
对于通过公共应用商店部署的移动应用，审批流程可能导致数天的延迟，使得严格契约的版本同步变得困难。

## 解决方案

### 方案1：按需选择契约严格程度

架构师不应盲目使用某种契约格式，而应该根据服务间的语义耦合程度来选择：

- **语义耦合紧密的服务间**：使用严格契约（如 gRPC、JSON Schema）。例如工单管理与工单分配服务，因为新功能类型的变化需要两方同步。
- **语义耦合松散的服务间**：使用松散契约（如纯 JSON 名称-值对）。例如通知与调查服务，其信息变化较慢，不需要脆弱的紧密耦合。

关键原则：**契约只包含"须知"级别（need to know）的信息**，在语义耦合和必要信息之间取得平衡，避免不必要的脆弱性。

### 方案2：消费者驱动契约（Consumer-Driven Contracts）

这是解决"松散耦合 + 契约保真度"矛盾的核心方案：

1. **工作方式**：消费者服务定义自己需要从提供者获取的信息格式，创建契约合同并传递给提供者。
2. **提供者职责**：将消费者的契约测试纳入 CI/CD 流水线，保持测试始终为绿色。
3. **自动化治理**：通过构建时的契约测试自动验证集成点的正确性（如图13-5）。
4. **可变严格度**：每个消费者可以根据自身需求制定不同严格程度的契约。

```json
// 示例：通过 JSON Schema 实现严格契约
{
  "$schema": "http://json-schema.org/draft-04/schema#",
  "properties": {
    "acct": {"type": "number"},
    "cusip": {"type": "string"},
    "shares": {"type": "number", "minimum": 100}
  },
  "required": ["acct", "cusip", "shares"]
}
```

### 方案3：反戳记耦合——按需裁剪契约

避免将服务的完整数据结构暴露给只关心其中少量字段的消费者。例如 Wishlist 服务只关心 Profile 中的名称字段：

```graphql
# Wishlist 的 Profile 表示——仅包含所需字段
type Profile {
  name: String
}

# 完整 Profile 表示——不必要地暴露给 Wishlist
type Profile {
  name: String
  addr1: String
  addr2: String
  country: String
  # ...
}
```

不应为了防止未来可能的需求而将不需要的字段纳入契约。

### 方案4：戳记耦合用于工作流管理（正面应用）

在编排式架构中处理复杂工作流时，可以使用戳记耦合来管理工作流状态：

- 契约中同时包含**领域信息**和**工作流状态**（状态、事务状态等）
- 每个领域服务接收契约后，更新自己负责的部分和整体工作流状态，然后传递给下一个服务
- 工作流结束时，接收方可以查询契约确定成功或失败状态
- 如需事务一致性，领域服务应将契约重新广播给之前访问过的服务以恢复原子一致性

这种方案在需要高吞吐量和可扩展性时，比中介者模式更有吸引力。

### 方案5：移动应用的松散契约 + 扩展机制

对于通过应用商店部署的移动端应用，需要使用更松散的契约以降低变更频率。同时建立**扩展机制**（extension mechanism）支持临时性短期的灵活性扩展。

## 关键权衡

### 严格契约的权衡（表13-1）

| 优势 | 劣势 |
|------|------|
| **契约保真度保证**：Schema 验证确保值、类型和元数据精确匹配 | **紧密耦合**：契约变更时，所有共享方都必须同步修改 |
| **版本化**：支持管理不同版本的契约，便于渐进式演进 | **版本化陷阱**：如果没有明确的废弃策略或支持过多版本，会变成集成噩梦 |
| **构建时验证**：可集成到 CI/CD 中进行类型级别的集成点检查 | |
| **更好的文档**：明确的参数和类型提供了无歧义的文档 | |

### 松散契约的权衡（表13-2）

| 优势 | 劣势 |
|------|------|
| **高度解耦**：微服务架构最灵活的选择 | **契约管理困难**：缺乏 Schema 可能导致拼写错误、字段缺失等问题 |
| **易于演进**：实现细节的变化不易破坏集成点 | **需要适应性函数**：必须通过消费者驱动契约等机制弥补契约检查的缺失 |

### 消费者驱动契约的权衡（表13-3）

| 优势 | 劣势 |
|------|------|
| **允许松散耦合**：使用名称-值对是最松散的耦合方式 | **需要工程成熟度**：只有纪律严明、持续执行 CI 和契约测试的团队才能真正受益 |
| **可变严格度**：适应性函数可以比传统 Schema 工具提供更精细的验证（如值的可接受范围） | **需要两个而非一个机制**：名称-值对 + 消费者驱动契约两个机制配合使用，增加了一定复杂度 |
| **可演进性**：松散契约天然支持演进 | |

### 戳记耦合的权衡（表13-4）

| 优势 | 劣势 |
|------|------|
| **支持编排式方案中的复杂工作流** | **人为制造高耦合**：语义耦合本应通过实现降低，但戳记耦合反而加剧了耦合 |
| | **高扩展下的带宽问题**：载荷过大时可能造成严重的带宽消耗 |

## Sysops Squad 案例：工单契约管理

### 背景

Addison 和 Sydney 在餐厅讨论工单管理工作流中各服务之间的契约选择。Addison 画出了如图13-9所示的契约类型分配方案。

### 决策分析

#### 工单编排器 ↔ 工单管理 & 工单分配服务 → **严格契约**

**原因**：这些服务之间语义耦合高度紧密，可能一起变化。例如增加新的管理项类型时，分配服务必须同步更新。

#### 工单编排器 ↔ 通知服务 & 调查服务 → **松散契约**

**原因**：这些信息变化较慢，使用紧密耦合反而弊大于利，不需要为了多余的保真度而牺牲灵活性。

#### 工单编排器 ↔ Sysops Squad 专家移动应用 → **松散契约**

**原因**：移动应用通过公共应用商店部署，审批流程耗时较长。如果使用严格契约，版本同步会因为商店审批延迟而受阻。采用松散契约可以换取灵活性，降低变更频率。

### 架构决策记录（ADR）

```
ADR: 对 Sysops Squad Expert 移动应用使用松散契约

上下文
系统管理专家使用的移动应用必须通过公共应用商店部署，
这会在契约更新能力上产生延迟。

决策
- 我们将使用松散的名称-值对契约在编排器和移动应用之间传递信息
- 我们将构建扩展机制，支持临时的短期灵活性

后果
- 如果应用商店策略允许更快（或持续）部署，该决策应被重新评估
- 更多契约验证逻辑需要驻留在编排器和移动应用中
```

### 关键启示

1. **契约选择因服务而异**：即使在同一个工作流中，不同服务对之间也需要根据语义耦合程度选择不同的契约严格度。
2. **部署管道影响架构决策**：基础设施约束（如应用商店审批延迟）直接影响契约策略的选择。
3. **松散契约 = 更多应用逻辑**：选择松散契约意味着必须在应用程序中实现更多验证逻辑来补偿 Schema 的缺失。
4. **ADR 是重要的架构沟通工具**：对于契约选择这类有显著影响但未来可能需要重新评估的决策，应及时记录以备将来审查。
