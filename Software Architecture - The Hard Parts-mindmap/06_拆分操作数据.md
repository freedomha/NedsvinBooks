# 第六章：拆分操作数据（Pulling Apart Operational Data）

## 一、章节概述

第六章聚焦于分布式架构中拆分单体数据库这一最核心也是最困难的挑战。数据是公司最重要的资产，拆分数据的风险远大于拆分应用功能，因为数据与业务逻辑高度耦合，难以在庞大的数据模型中找到清晰的接缝。本章系统地探讨了数据分解的驱动因素、分解技术（五步流程）、以及不同数据库类型的选型权衡，为架构师和数据团队提供了从单体数据向数据自治服务演进的完整方法论。

---

## 二、核心概念与定义

### 2.1 数据领域（Data Domain）
**数据领域**是一组相互耦合的数据库对象（表、视图、外键、触发器）的集合，这些对象与特定业务领域相关，且在有限的功能范围内频繁一起使用。可以将数据库想象成一个足球，每个白色六边形代表一个独立的数据领域。

### 2.2 架构量子（Architectural Quantum）
定义见第二章：一个可独立部署的工件，具有**高功能内聚**、**高静态耦合**和**同步动态耦合**。数据库包含在功能内聚部分——因此，要形成独立的量子，就必须拆分数据库。

### 2.3 边界上下文（Bounded Context）
源自Eric Evans的《领域驱动设计》。源代码、业务逻辑、数据结构、数据全部绑定在一个特定上下文中。良好的边界上下文将变更隔离在上下文内部，是控制数据库变更影响范围的关键机制。

### 2.4 数据自治与服务一一对应（Data Sovereignty Per Service）
分布式架构的"涅槃"状态——每个服务拥有自己的数据。好处：团队可独立修改数据库模式、每个服务可使用最适合的数据库技术。代价：跨服务大数据量访问带来性能问题、无法在数据库层面维护参照完整性、所有跨域的存储过程和函数必须迁移到服务层。

### 2.5 聚合导向（Aggregate Orientation）
源自DDD的聚合概念。偏好操作相关联且具有复杂结构的数据，如工单（ticket）及其所有依赖表。优点：易于集群分发、减少join、减少应用模型与存储模型的阻抗不匹配。缺点：难以正确定义聚合边界、跨聚合数据分析困难。

## 三、问题清单

### 3.1 变更控制问题（Change Control）
**问题描述**：当数据库表发生破坏性变更（删除表/列、修改列名/列类型）时，所有访问这些表的服务都需要同步更新、测试和部署。服务数量越多，协调越困难、越易出错。

**场景**：400个微服务共享一个单体关系数据库——要找到所有使用某个表的服务本身就是噩梦，更不用说协调它们一起部署。

**问题本质**：共享数据库导致高耦合，破坏性变更的波及范围不可控。

### 3.2 连接管理问题（Connection Management）
**问题描述**：数据库连接是昂贵资源。单体应用中连接池由应用服务器统一管理，但在分布式架构中每个服务实例都有自己的连接池。服务数量增加和实例扩展会导致连接数爆炸式增长。

**量化示例**：
- 原单体应用：200个连接
- 拆分为50个服务，每服务10个连接
- 最少2个实例：50 × 10 × 2 = **1,000个连接**
- 半数服务扩展至平均5个实例：**1,700个连接**（远超原始的200个）

**并发风险**：连接等待、请求超时、断路器跳闸。

### 3.3 可扩展性问题（Scalability）
**问题描述**：分布式系统中所有部分都需要扩展——包括数据库。服务扩展后对数据库的吞吐量和容量造成巨大压力。

**连接配额失效**：即使制定了连接配额（如100个连接分配给5个服务），一旦服务开始扩展（多实例），实际使用的连接数（如242个）远超可用数（100个），导致性能下降和超时。

### 3.4 容错性问题（Fault Tolerance）
**问题描述**：多个服务共享同一个数据库时，数据库成为单点故障。数据库宕机或维护时，**所有**服务都不可用，整个系统停止运行。

**分布式架构的必要条件**：要提高容错性，必须通过拆分数据库来消除单点故障。

### 3.5 架构量子冲突问题（Architectural Quanta Conflict）
**问题描述**：当服务A和B需要与其他服务不同的架构特性时，由于共享数据库的存在，它们无法形成独立的架构量子——所有服务+数据库组成一个大量子，无法差异化部署。

### 3.6 数据库类型优化问题（Database Type Optimization）
**问题描述**：单体数据库强制所有数据遵守同一数据库类型。并非所有数据都适合关系模型。例如：
- 参考数据（国家代码、产品代码等键值对数据）不适合关系数据库
- 知识库数据可能更适合图数据库
- 调查问卷数据可能更适合文档数据库

### 3.7 数据关系问题（Data Relationships）
**问题描述**：外键、触发器、视图和存储过程将表紧密耦合在一起。要形成数据领域，必须移除跨数据领域的这些耦合关系。这意味着：
- 移除跨数据领域的外键约束
- 移除跨数据领域的视图
- 移除跨数据领域的触发器和存储过程

### 3.8 分布式事务问题（Database Transactions）
**问题描述**：当数据拆分为独立schema或数据库后，不再存在单一事务的工作单元。ACID事务无法跨服务使用——一个表更新成功而另一个失败时，会导致数据一致性和完整性问题。

## 四、解决方案

### 4.1 数据分解驱动因素分析框架

#### 4.1.1 数据分解器（Data Disintegrators）——拆分数据的驱动因素

| 分解器 | 核心问题 | 触发条件 |
|--------|----------|----------|
| 变更控制 | 数据库表变更影响多少服务？ | 多服务因一个DB变更而需要同步部署 |
| 连接管理 | 数据库能处理多服务的连接需求吗？ | 频繁出现连接等待、请求超时 |
| 可扩展性 | 数据库能否随服务扩展而扩展？ | 服务扩展后数据库成为瓶颈 |
| 容错性 | 数据库宕机影响多少服务？ | 需要部分服务在数据库故障时仍可用 |
| 架构量子 | 共享数据库是否导致不期望的单一量子？ | 不同服务需要不同的架构特性 |
| 数据库类型优化 | 能否通过多种数据库类型优化数据？ | 存在非关系型数据（键值、图、文档等） |

#### 4.1.2 数据集成器（Data Integrators）——保持数据合一的驱动因素

| 集成器 | 核心问题 | 考虑要点 |
|--------|----------|----------|
| 数据关系 | 是否存在外键、触发器、视图形成的紧密关系？ | 移除这些耦合是否有副作用？ |
| 数据库事务 | 是否需要单一事务单元保证数据一致性？ | 分布式事务的复杂性是否可以接受？ |

**关键决策方法**：在分解器和集成器之间进行权衡分析。例如："变更控制是否比保留外键关系更重要？""容错性是否比保留物化视图更重要？"

### 4.2 连接配额策略（Connection Quota Strategy）

用于缓解共享数据库中的连接饱和问题。

#### 4.2.1 均匀分配法（Even Distribution）
- **适用场景**：服务首次部署，尚不清楚各服务需求
- **优点**：简单易实施
- **缺点**：效率不高——有些服务配额用不完，有些不够用

#### 4.2.2 可变分配法（Variable Distribution）
- **适用场景**：了解各服务功能和扩展需求后
- **优点**：优化连接利用率
- **缺点**：需要了解服务功能和扩展需求

**推荐实践**：
1. 从均匀分配开始
2. 建立适应度函数（fitness functions）持续监控各服务的并发连接使用情况
3. 将配额值保存在外部配置服务器/服务中，便于手动或通过ML程序化调整

#### 4.2.3 配额调优示例

| 阶段 | 服务A配额 | 服务B配额 | 服务C配额 | 服务D配额 | 服务E配额 | 等待情况 |
|------|-----------|-----------|-----------|-----------|-----------|----------|
| 均匀分配 | 20 | 20 | 20 | 20 | 20 | B、D等待 |
| 首次调整 | 10(-5) | 25(+5) | 20 | 25(+5) | 20 | B仍等待 |
| 最终调优 | 8(-2) | 29(+4) | 20 | 25 | 18(-2) | **无等待** |

### 4.3 边界上下文抽象（Bounded Context Abstraction）

通过在服务之间传递合约（JSON/XML/对象），调用方被**抽象于底层数据库模式之外**。

**实例**：
```sql
-- 数据库表结构
CREATE TABLE Wishlist (
  CUSTOMER_ID VARCHAR(10),
  ITEM_ID VARCHAR(20),
  QUANTITY INT,
  EXPIRATION_DT DATE
);
```

```json
// JSON合约（字段名和类型可以不同）
{
  "cust_id": "string",
  "item_id": "string", 
  "qty": "number",
  "exp_dt": "number"   // epoch毫秒数，而非DATE
}
```

**关键好处**：数据库删除`EXPIRATION_DT`列，只需要修改服务D，服务C完全不受影响。直到合约变动前，服务D可以发送远期日期或0值来兼容旧合约。

### 4.4 单体数据库拆分五步流程（Five-Step Process）

这是本章最核心的解决方案，是一个**进化的、迭代的**过程。

#### 第一步：分析数据库并创建数据领域（Analyze Database and Create Data Domains）

**目标**：识别数据库中的领域分组。

**方法**：将相关表分组，确定可能的数据领域。

| Sysops Squad 表 | 所属数据领域 |
|-----------------|-------------|
| customer, customer_notification | Customer |
| survey, question, survey_administered, survey_question, survey_response | Survey |
| billing, contract, payment_method, payment | Payment |
| sysops_user, profile, expert_profile, expertise, location | Profile |
| article, tag, keyword, article_tag, article_keyword | Knowledge Base |
| ticket, ticket_type, ticket_history | Ticketing |

**可视化**：将数据库想象为足球——每个白色六边形是一个数据领域，包含领域相关的表及其所有耦合工件。

#### 第二步：将表分配到数据领域Schema（Assign Tables to Data Domains）

**目标**：将属于特定数据领域的表分组到各自的schema中。

**操作**：如将billing表从原schema移动到payment schema：
```sql
ALTER SCHEMA payment TRANSFER sysops.billing;
```

**Schema与Data Domain的关系**：
- Data Domain是**架构概念**
- Schema是**数据库构造**
- 通常一对一映射
- 当数据关系紧密耦合时可能需要合并数据领域

**临时方案——同义词（Synonyms）**：
可以创建同义词来处理跨schema引用，但这只是**过渡方案**：
```sql
CREATE SYNONYM ticketing.sysops_user FOR profile.sysops_user;
```
同义词虽然不消除跨schema查询，但便于依赖检查和代码分析，为后续拆分奠定基础。

#### 第三步：将数据库连接分离到不同数据领域（Separate Database Connections to Data Domains）

**目标**：重构每个服务的数据库连接逻辑，确保服务**只**连接到指定的schema，只读/写自己数据领域中的表。

**关键原则**：需要其他领域数据时，**不要直接访问其数据库**，而是通过拥有该数据的**服务**来获取。

**这是五步中最困难的一步**：所有跨schema的访问必须在服务层面解决。

**结果**：进入数据自治状态（Data Sovereignty Per Service）。

#### 第四步：将Schema移到独立数据库服务器（Move Schemas to Separate Database Servers）

**目标**：将数据领域物理分离到不同的数据库服务器。

**两种方案**：

**方案A：备份与恢复（Backup and Restore）**
1. 备份每个schema及其数据领域
2. 为每个数据领域设置新的数据库服务器
3. 恢复schema到新服务器
4. 将服务连接到新服务器上的schema
5. 从原服务器删除schema

**特点**：通常需要停机维护窗口。

**方案B：复制（Replicate）**
1. 为每个数据领域设置新的数据库服务器
2. 复制schema到新服务器
3. 切换连接
4. 从原服务器删除schema

**特点**：避免停机，但需要更多工作量来设置复制和协调。

#### 第五步：切换到独立数据库服务器（Switch Over to Independent Database Servers）

**目标**：完成迁移，移除对旧数据库服务器的连接。

**最终状态**：
- 每个数据领域运行在自己的数据库服务器上
- 可独立优化可用性和扩展性
- 可分析数据特征来为每个服务选择最合适的数据库类型
- 引入**多语言持久化（Polyglot Persistence）**架构

### 4.5 数据库类型选型指南（Selecting a Database Type）

六维评估体系：
1. **学习曲线（Ease-of-learning curve）**
2. **数据建模难易度（Ease of data modeling）**
3. **可扩展性/吞吐量（Scalability/throughput）**
4. **可用性/分区容忍性（Availability/partition tolerance）**
5. **一致性（Consistency）**
6. **语言支持/产品成熟度/SQL支持/社区（Programming language support, product maturity, SQL support, and community）**
7. **读/写优先级（Read/write priority）**

#### 4.5.1 关系型数据库（Relational Database）

| 维度 | 评分 | 说明 |
|------|------|------|
| 学习曲线 | ★★★★★ | 学校广泛教授，文档和教程成熟 |
| 数据建模 | ★★★★★ | 灵活建模，像电子表格般自然 |
| 可扩展性 | ★★★☆☆ | 主要垂直扩展，复制和自动切换复杂 |
| 可用性 | ★★☆☆☆ | 倾向一致性而非可用性和分区容忍 |
| 一致性 | ★★★★★ | ACID属性是核心优势 |
| 社区成熟度 | ★★★★☆ | 历史悠久，但新架构概念采用较慢 |
| 读写优先级 | 平衡 | 同一数据库可处理不同类型的负载 |

**代表产品**：MySQL, Oracle, Microsoft SQL Server, PostgreSQL

#### 4.5.2 键值数据库（Key-Value Database）

| 维度 | 评分 | 说明 |
|------|------|------|
| 学习曲线 | ★★☆☆☆ | 容易理解但需改变思维习惯（不能查"所有key"） |
| 数据建模 | ★★★☆☆ | 聚合导向，仅可通过key/ID查询 |
| 可扩展性 | ★★★★★ | 无join和order by，极快的key查找 |
| 可用性 | ★★★★☆ | 可配置quorum（all/one/quorum/default） |
| 一致性 | ★★★☆☆ | 可调一致性——读写时可调整 |
| 社区成熟度 | ★★★★☆ | 良好语言支持，HTTP REST API |
| 读写优先级 | 读优先 | 适合会话存储、用户属性/偏好缓存 |

**代表产品**：Riak KV, Amazon DynamoDB, Redis

**分片（Sharding）说明**：分区是同一服务器上的表数据分集；分片是数据分布在不同的服务器/节点上。

#### 4.5.3 文档数据库（Document Database）

| 维度 | 评分 | 说明 |
|------|------|------|
| 学习曲线 | ★★★★☆ | 类似键值但值可读（JSON/XML），企业已熟悉 |
| 数据建模 | ★★★★☆ | 聚合导向但比键值更宽容，可索引聚合内部属性 |
| 可扩展性 | ★★★★☆ | 聚合导向易于扩展，复杂索引降低扩展性，分片增加复杂度 |
| 可用性 | ★★★★☆ | 可配置高可用，分片复制集群设置复杂 |
| 一致性 | ★★★☆☆ | 部分数据库开始支持集合内ACID，可使用quorum机制调优 |
| 社区成熟度 | ★★★★★ | NoSQL中最流行，活跃社区，丰富教程和驱动 |
| 读写优先级 | 读优先 | 聚合导向+二级索引，偏向读 |

**代表产品**：MongoDB, Couchbase, AWS DocumentDB

**Schema-less说明**：NoSQL数据库中schema名和数据都可重复。两个条目不必有相同的schema。但数据始终有隐式schema——应用需处理多版本schema。

#### 4.5.4 列族数据库（Column Family Database / Wide Column Database）

| 维度 | 评分 | 说明 |
|------|------|------|
| 学习曲线 | ★☆☆☆☆ | 最难理解——每行可拥有不同的name-value对 |
| 数据建模 | ★★★☆☆ | 需多次迭代设计row key，CQL语言降低了门槛 |
| 可扩展性 | ★★★★★ | 高度可扩展，水平扩展读/写，适合高吞吐场景 |
| 可用性 | ★★★★★ | 天然集群操作，节点故障对客户端透明，默认复制因子3 |
| 一致性 | ★★★☆☆ | 可调一致性——可配置ANY到ALL级别 |
| 社区成熟度 | ★★★★☆ | 活跃社区，SQL-like界面降低了采用门槛 |
| 读写优先级 | 写优先 | SSTables/commit log/memtables架构适合高写量场景 |

**代表产品**：Apache Cassandra, Scylla, Amazon SimpleDB

#### 4.5.5 图数据库（Graph Database）

| 维度 | 评分 | 说明 |
|------|------|------|
| 学习曲线 | ★☆☆☆☆ | 学习曲线陡峭——理解节点、关系、关系类型需时间 |
| 数据建模 | ★★☆☆☆ | 难以将领域建模为节点和关系，初期容易添加不必要的属性到关系 |
| 可扩展性 | ★★★☆☆ | 复制节点改善读扩展，写吞吐受分片限制，关系遍历极快 |
| 可用性 | ★★★☆☆ | 部分支持分布式，可用节点提升为Leader |
| 一致性 | ★★★★☆ | 多数支持ACID事务 |
| 社区成熟度 | ★★★★☆ | 内置算法（Dijkstra、节点相似度），Gremlin跨库框架，Cypher语言 |
| 读写优先级 | 读优先 | 存储优化关系遍历，无需查询时计算关系 |

**代表产品**：Neo4j, Infinite Graph, Tiger Graph

**关键注意**：改变关系类型代价高昂——每条关系必须重建，两个节点都要访问，因此必须仔细设计边类型。

#### 4.5.6 NewSQL数据库

| 维度 | 评分 | 说明 |
|------|------|------|
| 学习曲线 | ★★★★☆ | 与关系数据库相同——SQL接口+水平扩展+ACID |
| 数据建模 | ★★★★☆ | 与关系数据库相同，额外需考虑分片设计 |
| 可扩展性 | ★★★★★ | 多活跃节点设计，水平扩展能力强 |
| 可用性 | ★★★★★ | 多活跃节点，如CockroachDB能幸免磁盘/机器/数据中心故障 |
| 一致性 | ★★★★★ | 强一致性ACID事务 |
| 社区成熟度 | ★★★★☆ | 开源可及，部分支持与关系数据库的线兼容协议 |
| 读写优先级 | 平衡 | 类似关系数据库，新增地理分布索引能力 |

**代表产品**：VoltDB, ClustrixDB, CockroachDB

#### 4.5.7 云原生数据库（Cloud Native Database）

| 维度 | 评分 | 说明 |
|------|------|------|
| 学习曲线 | 因产品而异 | Redshift像关系数据库容易掌握；Snowflake有SQL界面但存储/计算机制不同；Datomic完全不同 |
| 数据建模 | 因产品而异 | Datomic不需要表概念；Snowflake/Redshift适合数据仓库 |
| 可扩展性 | 整体较好 | 云平台自动分配资源——代价是价格 |
| 可用性 | 因产品而异 | Datomic（Production Topology）无单点；Snowflake跨区域/账户复制；Redshift单可用区 |
| 一致性 | ★★★★☆ | Datomic支持ACID；Snowflake和Redshift也支持 |
| 社区成熟度 | ★★★☆☆ | 较新，找有经验的帮助难，云账号形成门槛 |
| 读写优先级 | 因产品而异 | Snowflake/Redshift偏读（数据仓库）；Datomic双支持（EAVT索引） |

**代表产品**：Snowflake, Datomic, Amazon Redshift, Azure CosmosDB

#### 4.5.8 时序数据库（Time-Series Database）

| 维度 | 评分 | 说明 |
|------|------|------|
| 学习曲线 | ★★★★☆ | 每条数据挂timestamp，几乎总是insert，不update不delete |
| 数据建模 | ★★★★☆ | 分析随时间的变化——每个标签只放一个信息（ticket_status=Open,ticket_id=374737 优于 ticket_info=Open.374737） |
| 可扩展性 | 因产品而异 | Timescale基于PostgreSQL；InfluxDB集群模式（meta节点+data节点） |
| 可用性 | 因产品而异 | InfluxDB支持meta/data节点配置+复制因子 |
| 一致性 | ★★★☆☆ | 基于关系数据库的引擎获得ACID；其他可调 |
| 社区成熟度 | ★★★★☆ | 最近流行，资源丰富，InfluxDB提供SQL-like的InfluxQL |
| 读写优先级 | 读优先 | 纯追加模式，适合读重负载 |

**代表产品**：InfluxDB, kdb+, Amazon Timestream, Timescale

**注意事项**：时序数据库**不是通用数据库**——数据按时间窗口查询。

## 五、关键权衡

### 5.1 拆 vs 不拆的平衡
- **数据分解器（Disintegrators）** vs **数据集成器（Integrators）**的博弈
- 目标是找到数据粒度的黄金平衡点

### 5.2 数据自治的代价
数据自治带来的好处与代价并存：
- **好处**：独立模式变更、多语言持久化
- **代价**：跨服务数据访问性能下降、参照完整性无法在数据库保证、跨域存储过程迁移成本

### 5.3 连接配额策略的权衡
- **均匀分配**：简单但低效
- **可变分配**：高效但需要业务知识

### 5.4 备份恢复 vs 复制迁移
- **备份恢复**：简单但需要停机
- **复制迁移**：零停机但设置和协调成本高

### 5.5 聚合设计的权衡（文档数据库）
- **单聚合**：一次get获取全部数据，开发者使用简单，但问题数据会冗余
- **多聚合**：问题数据可复用，不冗余，但检索和渲染更复杂

### 5.6 各数据库类型的核心权衡

| 数据库类型 | 核心权衡 |
|-----------|---------|
| 关系型 | 一致性优先于可用性和分区容忍（CA偏向） |
| 键值 | 极高的读写性能，但查询能力受限（仅key查询） |
| 文档 | 灵活性和开发体验好，但复杂索引降低扩展性 |
| 列族 | 高写入吞吐和大规模扩展，但学习曲线最陡 |
| 图 | 关系遍历极快且内置算法，但数据建模困难 |
| NewSQL | 关系型功能+NoSQL扩展性，但部分仅为DBaaS |
| 云原生 | 零运维负担，但供应商锁定和新技能门槛 |
| 时序 | 时间窗口分析最佳，但不是通用数据库 |

## 六、Sysops Squad 案例

### 6.1 场景一：论证数据库拆分的必要性

**参与者**：Addison（架构师）、Devon（DBA）、Dana（数据架构负责人）

**核心冲突**：Dana不同意拆分数据库，要求提供有力证据。

**论证过程**：

1. **数据库连接问题**：运营报表运行时工单功能冻结——报表查询使用并行线程消耗了所有数据库连接，导致工单查询超时。

2. **连接池估算**：按最终规划的分布式中服务数量和服务实例数，单数据库需要额外2,000个连接——单个数据库无法提供。

3. **容错性需求**：虽然拆分服务提供了部分容错，但单体数据库宕机会导致所有服务不可用。拆分后形成"领域孤岛"——调查问卷数据库宕机不影响工单功能。

4. **架构量子概念**：Addison向Dana解释了通过拆分数据库，核心工单功能可以独立运行，不再同步依赖其他系统部分。

**结果**：Dana被说服，她同意拆分数据库，但提出数据库中有大量外键和视图的问题。Devon表示五步流程可以解决这个问题。

### 6.2 场景二：多语言持久化（Polyglot Persistence）——调查问卷数据迁移

**参与者**：Devon、Dana、Skyler（前端开发者）、Addison、Parker（产品负责人）

**争议焦点**：Devon建议将Customer Survey从关系型迁移到文档数据库（JSON），但Dana不同意。

**Skyler的视角**：从UI角度看，处理关系型调查数据极其困难——即使新增一个问题也是"重大变更"。

**Addison的引导**：让团队关注业务价值。与产品负责人Parker沟通后发现：
- 市场部频繁需要修改调查问卷
- 即使最小的变更请求也需几天——市场部不愿提需求因为知道会失败
- 核心痛点：**缺乏灵活性**和**响应速度**

**业务论证**：将调查问卷数据改为文档数据库能显著提升灵活性和变更响应时间。

**聚合模型选择**：

团队面临两个选择：

**方案A：单聚合文档（Single Aggregate）**
```json
{
  "survey_id": "19999", 
  "description": "Survey to gauge customer...",
  "questions": [
    {"question_id": "50001", "question": "Rate the expert", "answer_type": "Option", ...},
    {"question_id": "50000", "question": "Did the expert fix the problem?", ...}
  ]
}
```
- 优势：一次get获取整个调查问卷，Skyler在UI层几乎不需要聚合数据
- 劣势：问题在每个调查文档中冗余

**方案B：多聚合文档（Multiple Aggregates with References）**
- 优势：问题数据不重复，可在多个调查中复用
- 劣势：检索和渲染更复杂

**最终决策**：
- 只有5种调查类型（每种产品类别一个）
- 大多数变更涉及添加/删除问题
- 团队**愿意用少量问题数据冗余换取UI开发的便利性和变更速度**
- 选择**单聚合文档**

**ADR（架构决策记录）**：
```
ADR: 使用文档数据库存储客户调查问卷

上下文：客户维修完成后收到调查问卷，共5种类型，基于电子产品类别。
当前存储在关系数据库中，团队希望迁移到JSON文档数据库。

决策：使用文档数据库存储客户调查问卷。
- 市场部需要更高的灵活性和更及时的变更
- 文档数据库简化了UI开发并可更好地促进变更

影响：
- 单聚合设计意味着更新通用问题需要修改多个文档
- 从关系数据库迁移到文档数据库时需要暂时关闭调查功能
```

## 七、核心要点总结

1. **拆分数据比拆分应用更难**——数据是公司最重要资产，风险更高
2. **决策前必须权衡**数据分解器（拆的驱动力）和数据集成器（合的驱动力）
3. **五步流程是核心方法论**：分析 → 分配Schema → 分离连接 → 物理分离 → 独立运行
4. **边界上下文是变更控制的关键**：通过合约抽象保护调用方不受数据库模式变更影响
5. **连接配额是共享数据库场景下的实用工具**：从均匀分配开始，通过适应度函数持续优化
6. **多语言持久化是架构演进的必然选择**：不同数据有不同特性，应选择最优数据库类型
7. **不要让数据库团队孤军奋战**——架构师、开发者、DBA和产品负责人需要紧密协作
8. **记录ADR**：关键架构决策（如切换数据库类型）必须有书面论证和影响分析
