# 第五章：基于组件的分解模式（Component-Based Decomposition Patterns）

## 章节概述

第五章系统介绍了**基于组件的分解模式**，这是一套用于将单体应用安全、迭代式地迁移至分布式架构（如基于服务的架构和微服务）的实践方法。当单体应用的代码库具有一定结构并按命名空间（或目录）组织时，这种方法尤为有效。

本章共介绍了**六个核心模式**，它们既可以按顺序组合使用（从单体迁移到分布式），也可以在迁移过程中单独使用（针对持续维护）。每个模式包含三部分：**模式描述**（工作原理、重要性和结果）、**适应度函数（Fitness Functions）治理**（自动化检查机制）、以及**Sysops Squad 案例演示**（实际应用场景）。

此外，本章还引入了**架构故事（Architecture Stories）**的概念——与描述功能需求的用户故事不同，架构故事专门记录影响应用结构的代码重构，用于满足业务驱动力（如可扩展性提升、更快上市等）。

## 核心概念与定义

### 关键术语

| 术语 | 定义 |
|------|------|
| **组件（Component）** | 应用的逻辑构建块，通常通过命名空间、包结构或目录结构标识，是服务的最小候选单元。组件必须是命名空间的**叶子节点**。 |
| **根命名空间（Root Namespace）** | 被其他命名空间节点扩展的命名空间节点。例如 `ss.survey` 被 `ss.survey.templates` 扩展时，`ss.survey` 即根命名空间。根命名空间也称为**子域（Subdomain）**。 |
| **孤立类（Orphaned Classes）** | 存在于根命名空间中的类文件，由于该命名空间已被扩展，这些类不属于任何可定义的组件。 |
| **组件依赖（Component Dependency）** | 当一个命名空间中的类与另一个命名空间中的类交互时形成。分为传入耦合（Afferent Coupling, CA）和传出耦合（Efferent Coupling, CE）。总耦合 CT = CA + CE。 |
| **组件域（Component Domain）** | 执行某种相关功能的组件逻辑分组，是最终形成域服务的基础。 |
| **域服务（Domain Service）** | 粗粒度的、独立部署的软件单元，包含特定域（如票务、客户、报表）的所有功能。 |
| **基于服务的架构（Service-Based Architecture）** | 一种分布式架构拓扑：用户界面远程访问粗粒度域服务，所有服务共享一个单体数据库。建议作为迁移到微服务的中间步骤。 |
| **适应度函数（Fitness Function）** | 在CI/CD管道中触发的自动化治理机制，用于持续分析和验证代码库的正确性。 |

### 组件度量指标

| 指标 | 说明 | 用途 |
|------|------|------|
| 组件名称（Component Name） | 描述性标识符，应足够清晰以自描述。 | 沟通、文档、图示 |
| 组件命名空间（Component Namespace） | 物理或逻辑标识，表示组件源代码的组织位置。 | 标识组件边界 |
| 百分比（Percent） | 组件语句数 / 应用总语句数 | 识别过大或过小的组件 |
| 语句数（Statements） | 组件内所有源文件语句的总和 | 判断组件复杂度和相对大小 |
| 文件数（Files） | 组件内源文件（类、接口等）的总数 | 了解类的组织结构 |

### 组件大小判断标准

- 组件大小应在总体均值的一到两个标准差范围内
- 每个组件占代码的比例应大致均匀分布
- 语句数是相对较好的指标（优于文件数或行数，因为不同开发者的类设计风格差异大）

## 问题清单

### 模式一：Identify and Size Components（识别并调整组件大小）

| 编号 | 问题 | 严重程度 |
|------|------|----------|
| P5-1 | 不清楚应用中存在哪些组件，缺少组件清单 | 高 |

| P5-3 | 某些组件过小（功能不足），碎片化严重 | 中 |

| P5-6 | 缺少自动化的组件治理机制，新组件或组件大小变化未被感知 | 中 |

| 编号 | 问题 | 严重程度 |
|------|------|----------|
| P5-7 | 相同的域名逻辑（如通知、审计、格式化）在多个组件中重复实现 | 高 |
| P5-8 | 如果不合并公共功能，拆分后将产生大量重复服务 | 高 |
| P5-9 | 公共域功能与公共基础设施功能混淆不清 | 中 |
| P5-10 | 合并公共组件可能导致该组件的传入耦合过高（太多组件依赖它） | 中 |
| P5-11 | 难以自动化发现重复的域功能（识别具有主观性） | 中 |

### 模式三：Flatten Components（扁平化组件）

| 编号 | 问题 | 严重程度 |
|------|------|----------|
| P5-12 | 组件建立在其他组件之上（命名空间嵌套），产生"山丘"结构 | 高 |
| P5-13 | 根命名空间中存在孤立类（孤儿类），这些类不属于任何可定义组件 | 高 |
| P5-14 | 当命名空间被扩展后，原有命名空间不再是组件而是子域，但仍包含源代码 | 高 |
| P5-15 | 根命名空间中的共享代码被视为孤立类，需要移入独立组件 | 中 |
| P5-16 | 共享代码过多（如共享组件占比过高），可能导致拆分后共享库依赖难以维护 | 中 |

| 编号 | 问题 | 严重程度 |
|------|------|----------|
| P5-17 | 不清楚组件之间的依赖关系图，无法判断是否适合拆分 | 高 |
| P5-18 | 无法评估迁移的可行性（feasibility） | 高 |
| P5-19 | 无法估算迁移的整体工作量（golf ball / basketball / airliner） | 高 |
| P5-20 | 不确定是需要重构（refactoring）还是重写（rewrite）代码 | 高 |
| P5-21 | 某些组件耦合度过高（如传入耦合为20），但并非所有依赖方都需要该组件的全部功能 | 中 |
| P5-22 | 开发团队跳过了依赖分析直接开始拆分，导致迁移困难 | 高 |
| P5-23 | 共享组件（如通知、共享代码）掩盖了核心功能组件之间的真实依赖关系 | 中 |

### 模式五：Create Component Domains（创建组件域）

| 编号 | 问题 | 严重程度 |
|------|------|----------|
| P5-24 | 组件未能按域逻辑分组，无法形成粗粒度的域服务 | 高 |
| P5-25 | 命名空间未与业务域对齐（如账单相关的组件命名空间不以 `customer` 开头） | 高 |
| P5-26 | 拆分应用时缺少域作为中间抽象层 | 高 |
| P5-27 | 组件域的划分需要与业务干系人（如产品负责人）协作，否则可能不准确 | 中 |
| P5-28 | 域服务形成后，可能有组件被遗漏或无法归入任何域 | 中 |

### 模式六：Create Domain Services（创建域服务）

| 编号 | 问题 | 严重程度 |
|------|------|----------|
| P5-29 | 已定义的组件域仍然在单体应用中，尚未物理拆分为独立服务 | 高 |
| P5-30 | 太早拆分导致后续需要频繁修改已迁移的域服务（因组件归属调整） | 中 |
| P5-31 | 直接从单体跳到微服务粒度过细，面临数据分解、分布式事务、运维自动化等全部挑战 | 高 |
| P5-32 | 域服务内部组件可能逐渐偏离域的定义，形成自己的"非结构化的单体服务" | 中 |

## 解决方案

### 模式一：Identify and Size Components（识别并调整组件大小）

**目标**：识别和编目应用中的架构组件，并正确调整组件大小，使组件分布均匀。

**解决步骤**：

1. **建立组件清单**：遍历整个代码库，识别所有命名空间（或目录），为每个组件创建条目，包含名称、命名空间、百分比、语句数和文件数五个指标。

2. **分析组件大小**：计算每个组件的语句总数和代码百分比，使用标准差识别异常组件。

3. **拆分过大组件**：
   - 使用**功能分解**（functional decomposition）或**领域驱动**方法识别大组件内的子域
   - 将大组件拆分为多个较小、更具内聚性的组件
   - 例如：将占22%代码的 `Trouble Ticket` 拆分为 `Ticket Creation`、`Ticket Assignment`、`Ticket Routing`、`Ticket Completion` 四个组件

4. **合并过小组件**：如果组件过小且功能相关，可考虑合并。

5. **治理机制**：
   - **适应度函数：维持组件清单**（Maintain component inventory）——检测新增或删除的组件
   - **适应度函数：组件代码占比不超过阈值**（No component shall exceed some percent）——超过阈值的组件发出告警
   - **适应度函数：组件标准差检查**（No component shall exceed some number of standard deviations from the mean）——使用三倍标准差作为阈值识别离群组件

### 模式二：Gather Common Domain Components（收集公共域组件）

**目标**：识别并合并重复的**域功能**（非基础设施功能），减少分布式架构中潜在的重复服务。

**域功能 vs 基础设施功能**：
- **域功能**：业务处理逻辑的一部分（如通知、数据格式化、数据验证），仅部分流程使用
- **基础设施功能**：运维性质（如日志、指标收集、安全），所有流程通用

**解决步骤**：

1. **发现公共域功能的方法**：
   - **共享类分析**：如果一个类被多个不同命名空间的类使用，可能是公共域功能（如 `SMTPConnection` 被5个不同组件的类使用，说明邮件通知功能分散了）
   - **命名空间名称分析**：具有相同叶子节点名称的组件可能实现相同功能（如 `ss.ticket.audit`、`ss.billing.audit`、`ss.survey.audit` 都涉及审计功能）

2. **合并决策前的耦合分析**：
   - 计算每个分散组件当前的传入耦合（CA）
   - 模拟合并后的新组件的传入耦合
   - 如果合并后总传入耦合不变（原来的分散组件 CA 之和等于新组件的 CA），则是安全合并
   - **注意**：如果合并后耦合显著增加，可能需要保留为独立组件

3. **实现方式选择**：
   - **共享服务（Shared Service）**：运行时依赖
   - **共享库（Shared Library）**：编译时绑定
   - 详见第8章对两种方式的利弊讨论

4. **治理机制**：
   - **适应度函数：查找命名空间叶子节点名称相同的组件**（Find common names in leaf nodes）——发现可能重复的域功能
   - **适应度函数：查找组件间共享的类**（Find common code across components）——识别跨组件使用的公共类

### 模式三：Flatten Components（扁平化组件）

**目标**：确保源文件只存在于明确定义的组件（叶子节点命名空间）中，消除根命名空间中的孤立类。

**解决步骤**：

1. **识别问题**：遍历所有命名空间，找出：
   - 根命名空间（被其他节点扩展的命名空间）
   - 根命名空间中包含的孤立类（orphaned classes）

2. **扁平化方向一：向下合并**（Collapse）
   - 将叶子节点的代码合并到根命名空间
   - 例如：将 `ss.survey.templates` 中的代码合并到 `ss.survey`，使 `ss.survey` 成为单一组件
   - **适用场景**：功能不复杂、变化不频繁

3. **扁平化方向二：向上拆分**（Expand）
   - 将根命名空间中的孤立类通过功能分解或DDD拆分为新的叶子节点组件
   - 例如：将 `ss.survey` 中的代码拆分为 `ss.survey.create`（创建并发送调查）和 `ss.survey.process`（处理收到的调查）
   - **适用场景**：功能复杂、各子功能独立性强

4. **处理共享代码**：
   - 根命名空间中的共享代码（如接口、抽象类、通用工具）应移入以 `.shared`（或特定后缀如 `.sharedcode`、`.commoncode`）结尾的独立组件
   - 例如：将 `ss.survey` 根命名空间中的共享类移入 `ss.survey.shared`

5. **共享代码度量**：
   - 统计所有 `.shared` 组件的语句总数
   - 如果占总代码的45%，说明共享代码太多，拆分为分布式架构后共享库依赖会难以维护
   - 统计 `.shared` 组件的数量，预测拆分后将产生多少共享库或共享服务

6. **治理机制**：
   - **适应度函数：根命名空间中不应存在源代码**（No source code should reside in a root namespace）——检测孤立类并告警

### 模式四：Determine Component Dependencies（确定组件依赖关系）

**目标**：分析组件之间的传入和传出依赖（耦合），判断迁移的可行性和工作难度。

**三个核心问题**：
1. 现有单体应用是否适合拆分？
2. 迁移的总体工作量大概是多大？
3. 是需要重构代码还是重写代码？

**解决步骤**：

1. **生成组件依赖图**：
   - 使用IDE插件或静态分析工具生成组件（非类）级别的依赖关系可视化图
   - 图中方框代表组件，连线代表耦合点

2. **三种依赖图场景判断**：

| 场景 | 依赖程度 | 可行性 | 工作量 | 方式 |
|------|----------|--------|--------|------|
| **高尔夫球（Golf Ball）** | 最小，仅单一依赖 | 是 | 相对简单 | 重构（将现有代码移入独立服务） |
| **篮球（Basketball）** | 较高，一侧耦合重 | 可能 | 较困难 | 重构 + 部分重写 |
| **客机（Airliner）** | 极高，全连通 | 否 | 极高 | 完全重写应用 |

3. **分析耦合细节**：
   - 记录每个组件的 CA（传入耦合）和 CE（传出耦合）
   - 计算 CT = CA + CE（总耦合）

4. **耦合重构机会**：
   - 如果组件A的传入耦合很高（如CA=20），但并非所有依赖方都需要A的全部功能
   - 可以将A拆分为A1（包含少数依赖方需要的功能，CA=14）和A2（包含大多数功能，CA=6）
   - 从而降低各组件的耦合度

5. **过滤共享组件的干扰**：
   - 共享组件（编译时的类引用）通常会实现为共享库而非服务
   - 过滤这些组件后，可以更清晰看到核心功能组件之间的真实依赖关系

6. **治理机制**：
   - **适应度函数：组件总依赖数不超过阈值**（No component shall have more than some number of total dependencies）——建议阈值15
   - **适应度函数：组件间依赖限制**（Some component should not have a dependency on another component）——使用 ArchUnit 等工具精细控制

### 模式五：Create Component Domains（创建组件域）

**目标**：将组件逻辑分组到域中，为创建粗粒度域服务奠定基础。

> **核心理念**：服务与组件的关系通常是一对多的（一个服务包含多个组件），组件域是实现这种映射的桥梁。

**解决步骤**：

1. **识别域候选**：
   - 与业务干系人（产品负责人、业务发起人）协作，识别出应用中的主要业务域
   - 典型域划分：Ticketing（票务）、Customer（客户）、Reporting（报表）、Admin（管理）、Shared（共享）

2. **验证域划分**：
   - 确保所有组件都能归入某个域
   - 确保同一域内的组件之间具有良好内聚性
   - 如果组件无法归入任何域，需要重新与业务干系人协调

3. **重构命名空间以对齐域**：
   - 修改组件命名空间，使其反映域/子域/组件的层次结构：`ss.<域>.<子域>.<组件>`
   - 例如：将 `ss.billing.payment` 改为 `ss.customer.billing.payment`
   - 例如：将 `ss.survey` 改为 `ss.ticket.survey`
   - 将 `ss.expert.profile` 改为 `ss.admin.experts`（避免不必要的子域层级）

4. **治理机制**：
   - **适应度函数：根命名空间下只允许特定域列表**（All namespaces should be restricted to list of domains）——防止意外创建新域

### 模式六：Create Domain Services（创建域服务）

**目标**：将已定义的组件域从单体应用中**物理提取**出来，形成独立部署的域服务，创建基于服务的架构。

**解决步骤**：

1. **前置条件**：确保所有组件域已识别完毕并完成命名空间重构（不要过早拆分！）

2. **迁移计划制定**：
   - 确定迁移顺序（一次一个域服务）
   - 规划用户界面如何远程访问新域服务的功能

3. **提取域服务**：
   - 将组件域内的源代码从单体项目工作区移至新项目工作区
   - 配置远程访问机制（REST、消息等）
   - 维护共享数据库（service-based architecture 的基础拓扑）

4. **渐进式迁移**：
   - 先从基于服务的架构开始（粗粒度域服务 + 共享数据库）
   - 学习各域服务的特点
   - 再决定是否需要进一步拆分为微服务

5. **治理机制**：
   - **适应度函数：域服务中所有组件的命名空间应以相同前缀开头**（All components in a domain service should start with the same namespace）——防止域服务变成非结构化的单体

> **核心建议**：不要在识别和重构完所有组件域之前就开始提取域服务。否则，如果后续发现某个组件应属于已迁移的域服务，就需要修改已在运行中的服务，增加了不必要的开销。

## 关键权衡

### 1. 组件粒度的平衡
- **过粗**：组件功能太多，耦合度高，难以拆分为服务
- **过细**：组件碎片化，管理复杂，服务数量爆炸
- **平衡方案**：使用语句数和标准差作为客观参考，保持组件在1-2个标准差范围内

### 2. 公共组件合并与耦合
- **合并优势**：消除代码和功能重复，减少拆分后服务数量
- **合并风险**：合并后单组件传入耦合过高，形成过多的依赖集中点
- **决策依据**：合并前后的总传入耦合是否显著增加。如果分散组件的CA之和等于合并组件CA，则是安全的

### 3. 共享服务 vs 共享库
- **共享服务**：运行时依赖，独立部署，松耦合但增加网络开销
- **共享库**：编译时绑定，性能好，但版本管理和依赖地狱是常见问题
- **决策**：需根据具体情况选择（详见第8章）

### 4. 扁平化方向：合并 vs 拆分
- **向下合并（Collapse）**：代码简单、变化少时适用，减少不必要组件
- **向上拆分（Expand）**：代码复杂、各功能独立性强时适用，增加模块化程度
- **决策依据**：功能的复杂度、变更频率、独立演化需求

### 5. 直接微服务 vs 先服务化架构
- **直接微服务**：一步到位，但立即面临数据分解、分布式事务、运维自动化等所有复杂挑战
- **先服务化架构**：渐进式路径，以粗粒度域服务为中间步骤，学习后再决定是否需要拆分
- **推荐方案**：先迁移到基于服务的架构，再根据需要进一步细化为微服务

### 6. 迁移时机：全部分析完再拆 vs 边分析边拆
- **全部分析完再拆**：需等待全部域识别和重构完成，但能避免重复修改已迁移服务的开销
- **边分析边拆**：快速见效，但可能需频繁回归修改
- **推荐方案**：在所有组件域识别和命名空间重构完成前，不应用 Create Domain Services 模式

### 7. 架构故事的粒度
- **过于频繁**：每次小重构都创建架构故事，产生噪声
- **过于罕见**：重大结构变化未被记录和追踪
- **建议**：当重构影响应用整体结构并满足业务驱动时创建架构故事

## Sysops Squad 案例

### 背景
Sysops Squad 是一个IT支持票务管理系统，团队正在进行从单体架构到分布式架构的迁移。架构师 Addison 和 Austen 在资深架构师 Logan 的指导下，逐步应用六个分解模式。

### 应用各模式的完整过程

#### 第一步：Identify and Size Components（识别并调整组件大小）

**初始状态分析**：
- 应用总共 82,931 条语句，包含 18 个组件
- 发现 **Reporting（ss.reporting）** 组件包含 27,765 条语句，占 33% 的代码库，严重偏离均值

**解决方案**：
Addison 对 Reporting 组件进行功能分解，发现其包含三类报表：
- 票务报表（工单统计、工单频率、解决时间等）
- 专家报表（专家利用率、专家分布等）
- 财务报告（维修成本、专家成本、利润报告等）

同时发现所有报表类别共用一套通用代码（工具类、计算器、共享数据查询、报表分发、数据格式化）。

**结果**：
创建架构故事，将 Reporting 拆分为 4 个组件：
| 组件名 | 命名空间 | 占比 | 语句数 | 文件数 |
|--------|----------|------|--------|--------|
| Reporting Shared | ss.reporting.shared | 7% | 5,309 | 20 |
| Ticket Reports | ss.reporting.tickets | 8% | 6,955 | 58 |
| Expert Reports | ss.reporting.experts | 9% | 7,734 | 48 |
| Financial Reports | ss.reporting.financial | 9% | 7,767 | 36 |

注意：`ss.reporting` 命名空间仍然存在，但它不再是组件，而是一个子域。

#### 第二步：Gather Common Domain Components（收集公共域组件）

**问题发现**：
Addison 发现三个组件都涉及**通知客户**功能：

| 组件 | 命名空间 | 职责 |
|------|----------|------|
| Customer Notification | ss.customer.notification | 通用通知 |
| Ticket Notify | ss.ticket.notify | 通知客户专家已出发 |
| Survey Notify | ss.survey.notify | 发送调查问卷邮件 |

**耦合分析**：

合并前的传入耦合：
| 组件 | CA | 被依赖方 |
|------|-----|----------|
| Customer Notification | 2 | Billing Payment, Support Contract |
| Ticket Notify | 2 | Ticket, Ticket Route |
| Survey Notify | 1 | Survey |
| **分散总计** | **5** | |

合并后的传入耦合：
| 组件 | CA | 被依赖方 |
|------|-----|----------|
| Notification | 5 | Billing Payment, Support Contract, Ticket, Ticket Route, Survey |

关键发现：合并前后总传入耦合不变（都是5），合并是**安全**的。

**结果**：
移除三个通知组件（`ss.customer.notification`、`ss.ticket.notify`、`ss.survey.notify`），创建统一的 `ss.notification` 组件。

#### 第三步：Flatten Components（扁平化组件）

**第一部分：Ticket 组件**

发现 `ss.ticket` 根命名空间中存在 45 个孤立类文件，而 `ss.ticket.assign` 和 `ss.ticket.route` 已经是叶子节点组件。

Addison 与开发者 Sydney 分析后发现，45个孤立类实现了三类功能：
- 工单创建和维护（创建、更新、取消工单等）
- 工单完成逻辑
- 大部分工单功能的共享代码

**决策**：保留 `ss.ticket.assign` 和 `ss.ticket.route` 作为独立组件（因其复杂性和频繁变更），将孤立类拆分为三个新组件：

| 组件 | 命名空间 | 职责 |
|------|----------|------|
| Ticket Shared | ss.ticket.shared | 公共代码和工具 |
| Ticket Maintenance | ss.ticket.maintenance | 工单创建和维护 |
| Ticket Completion | ss.ticket.completion | 完成工单并发起调查 |
| Ticket Assign | ss.ticket.assign | 指派专家（保留） |
| Ticket Route | ss.ticket.route | 路由工单（保留） |

**第二部分：Survey 组件**

发现 `ss.survey`（5个文件）和 `ss.survey.templates`（7个文件）的结构。Addison 与开发者 Skyler 确认，当初分离模板的命名空间没有充分理由（"当时觉得是个好主意"）。

由于调查功能很少变化且不复杂，决定采用**向下合并**方式：将 `ss.survey.templates` 的7个类移入 `ss.survey`，删除 `ss.survey.templates` 组件。

**最终结果**：
- 消除了所有"山丘"结构（组件堆叠组件）
- 所有源代码只存在于叶子节点命名空间
- Ticket 从组件变为子域（ss.ticket），包含5个叶子组件

共 18 个组件：Login, Billing Payment, Billing History, Customer Profile, Expert Profile, KB Maint, KB Search, Notification, Reporting Shared, Ticket Reports, Expert Reports, Financial Reports, Ticket Shared, Ticket Maintenance, Ticket Completion, Ticket Assign, Ticket Route, Support Contract, Survey, User Maintenance

#### 第四步：Determine Component Dependencies（确定组件依赖关系）

**初步分析**：
Addison 使用 IDE 插件生成了完整的组件依赖图——图显示**大量依赖关系**，最初让她感到沮丧。

**关键洞察**：
她注意到：
1. **Notification 组件**依赖最多（作为共享组件，意料之中）
2. **Ticketing 和 Reporting 域内**也显示大量依赖——但这些主要是编译时类引用（接口、帮助类、实体类），应实现为共享库而非服务

**过滤共享代码后**：
过滤掉共享组件后，剩下的核心功能组件之间依赖相当少，大多数组件相对独立。

**结论**：
Addison 和 Austen 一致认为 Sysops Squad 应用**适合拆分为分布式架构**。

#### 第五步：Create Component Domains（创建组件域）

**域识别**：
Addison、Austen 与产品负责人 Parker 协作，确定了五个主要域：

| 域 | 命名空间 | 包含功能 |
|-----|----------|----------|
| Ticketing | ss.ticket | 工单处理、客户调查、知识库 |
| Reporting | ss.reporting | 所有报表功能 |
| Customer | ss.customer | 客户档案、账单、支持合同 |
| Admin | ss.admin | 用户维护、专家管理 |
| Shared | ss.shared | 登录、通知（被其他域使用） |

**命名空间重构**：

**Ticket 域**：
| 组件 | 原命名空间 | 目标命名空间 |
|------|-----------|-------------|
| KB Maint | ss.kb.maintenance | ss.ticket.kb.maintenance |
| KB Search | ss.kb.search | ss.ticket.kb.search |
| Survey | ss.survey | ss.ticket.survey |

**Customer 域**：
| 组件 | 原命名空间 | 目标命名空间 |
|------|-----------|-------------|
| Billing Payment | ss.billing.payment | ss.customer.billing.payment |
| Billing History | ss.billing.history | ss.customer.billing.history |
| Support Contract | ss.supportcontract | ss.customer.supportcontract |

**Admin 域**：
| 组件 | 原命名空间 | 目标命名空间 |
|------|-----------|-------------|
| Expert Profile | ss.expert.profile | ss.admin.experts |
| User Maintenance | ss.users | ss.admin.users |

**Reporting 域**：已经对齐，无需重构。

**Shared 域**：
| 组件 | 原命名空间 | 目标命名空间 |
|------|-----------|-------------|
| Login | ss.login | ss.shared.login |
| Notification | ss.notification | ss.shared.notification |

#### 第六步：Create Domain Services（创建域服务）

**最终实施**：
Addison、Austen 与开发团队一起制定了迁移计划，将每个组件域逐步提取为独立部署的域服务，形成基于服务的架构。

**架构变化**：
- 用户界面从直接调用单体内部功能 → 远程访问各域服务
- 各域服务共享同一个单体数据库
- 5个域对应5个独立部署的域服务：Ticketing Service、Reporting Service、Customer Service、Admin Service、Shared Service

**后续章节展望**：
- 第6章：分解单体数据（共享数据库拆分）
- 第7章：将域服务进一步拆分为更细粒度的微服务

## 六个模式摘要对照表

| 序号 | 模式名称 | 核心作用 | 主要操作 | 前置模式 |
|------|----------|----------|----------|----------|
| 1 | Identify and Size Components | 建立组件清单，调整大小 | 统计语句数/百分比/文件数，拆分或合并组件 | 无 |
| 2 | Gather Common Domain Components | 消除重复域功能 | 发现公共域逻辑，耦合分析，合并组件 | 模式1 |
| 3 | Flatten Components | 消除孤立类 | 向下合并或向上拆分，处理共享代码 | 模式1、2 |
| 4 | Determine Component Dependencies | 评估迁移可行性 | 生成依赖图，分析耦合，判断工作量级别 | 模式1、2、3 |
| 5 | Create Component Domains | 逻辑分组为域 | 与业务协作识别域，重构命名空间 | 模式1、2、3、4 |
| 6 | Create Domain Services | 物理拆分为独立服务 | 提取域代码，建立服务化架构 | 模式1、2、3、4、5 |
