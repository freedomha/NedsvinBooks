# 第十二章：事务性 Saga（Transactional Sagas）—— 问题与解决方案

## 一、章节概述

本章深入探讨分布式架构中的**事务性 Saga 模式**。Saga 的概念最早可追溯到 1987 年 ACM 会议论文，最初用于限制早期分布式架构中数据库锁的范围。在微服务架构中，Saga 被定义为一系列本地事务的序列：每个更新发布一个事件，触发序列中的下一个更新；若任一更新失败，Saga 会发出一系列**补偿更新（compensating updates）**来撤销之前的变更。

然而这只是 Saga 的八种可能类型之一。本章详细剖析每种类型的内部工作机制及其权衡，尤其关注**错误发生时的处理**——毕竟分布式事务缺乏原子性，正是问题出现时才体现了它们的复杂性。

本章通过三个维度的组合定义了八种 Saga 模式：

| 维度 | 可选值 |
|------|--------|
| **通信方式（Communication）** | 同步（Synchronous）/ 异步（Asynchronous） |
| **一致性（Consistency）** | 原子性（Atomic）/ 最终一致性（Eventual） |
| **协调方式（Coordination）** | 编排（Orchestrated）/ 编舞（Choreographed） |

三种维度的交叉产生 2×2×2 = 8 种组合，每种都有其独特的名称和上标缩写（按字母顺序排列，便于记忆）：

| 模式名称 | 上标 | 通信 | 一致性 | 协调 |
|---------|------|------|--------|------|
| Epic Saga | sao | 同步 | 原子 | 编排 |
| Phone Tag Saga | sac | 同步 | 原子 | 编舞 |
| Fairy Tale Saga | seo | 同步 | 最终 | 编排 |
| Time Travel Saga | sec | 同步 | 最终 | 编舞 |
| Fantasy Fiction Saga | aao | 异步 | 原子 | 编排 |
| Horror Story | aac | 异步 | 原子 | 编舞 |
| Parallel Saga | aeo | 异步 | 最终 | 编排 |
| Anthology Saga | aec | 异步 | 最终 | 编舞 |

## 二、核心概念与定义

### 2.1 分布式事务的核心问题

分布式事务在分布式架构中面临三个根本性挑战：

1. **缺乏原子性**：无法像单体应用中的数据库事务那样保证所有操作要么全部成功、要么全部回滚。
2. **缺乏事务隔离**：在分布式事务完成之前，其他服务可能已经基于中间状态的数据采取了行动。
3. **错误处理复杂**：补偿更新可能失败、产生副作用，或导致状态不一致。

### 2.2 补偿更新（Compensating Updates）

补偿更新是一种反向操作，用于在分布式事务范围内撤销其他服务已执行的数据写入操作（如撤销更新、重新插入之前删除的行、删除之前插入的行）。补偿更新试图将分布式数据源恢复到事务开始前的状态，但存在大量复杂问题和挑战。

### 2.3 最终一致性与状态管理

基于**有限状态机**的状态管理方法：始终知道事务性 Saga 的当前状态，并通过重试或自动/手动纠正操作来最终纠正错误条件。这种方法响应性更好，最终用户无需等待补偿更新完成。

### 2.4 Saga 状态机（Saga State Machine）

状态机描述分布式架构中所有可能的路径。它始终从一个起始状态开始，包含转换状态以及转换时应执行的相应动作。关键要素：
- **START（起始节点）**：Saga 的入口点
- **转换状态**：过程中的中间状态
- **CLOSED（结束节点）**：Saga 的出口点
- **转换动作表**：列出初始状态、转换状态和对应的转换动作

## 三、八种 Saga 模式详解

### 3.1 Epic Saga(sao) 模式

**（同步 + 原子 + 编排）**

这是"传统"的 Saga 模式，也被称为**编排型 Saga（Orchestrated Saga）**。

**工作原理**：
- 编排器服务协调包含多个服务更新的工作流
- 所有调用要么全部成功，要么全部失败
- 使用补偿更新框架：中介者监控调用成功状态，若某个请求失败则向其他服务发出补偿调用

**评分**：
| 维度 | 评级 |
|------|------|
| 耦合度 | 非常高 |
| 复杂度 | 低 |
| 响应性/可用性 | 低 |
| 可扩展性/弹性 | 非常低 |

**优点**：
- 事务协调模仿单体系统行为，架构师和开发人员最熟悉
- 通过编排器拥有清晰的工作流所有者

**缺点**：
- 所有维度上耦合度最高——八种模式中耦合最紧
- 编排器必须确保所有参与者都成功或失败，产生时序瓶颈
- 补偿更新面临各种失败模式和边界条件
- 对性能、可扩展性、弹性等操作特性有负面影响

**适用场景**：需要严格事务一致性、业务方要求状态变更必须同步的场景。

---

### 3.2 Phone Tag Saga(sac) 模式

**（同步 + 原子 + 编舞）**

名称来源于著名的儿童游戏"电话传话"：消息在服务之间依次传递。

**工作原理**：
- 首个被调用的服务成为协调点（称为**前控制器/Front Controller**）
- 该服务完成后将请求传递给工作流中的下一个服务
- 发生错误时，每个服务必须内置逻辑向链条上回传补偿请求
- 领域服务必须包含更多关于工作流上下文的逻辑，包括错误处理和路由

**评分**：
| 维度 | 评级 |
|------|------|
| 耦合度 | 高 |
| 复杂度 | 高 |
| 响应性/可用性 | 低 |
| 可扩展性/弹性 | 低 |

**优点**：
- 比 Epic Saga 略微松耦合
- 无编排器意味着更少的瓶颈，正常路径可达到更高吞吐量
- 同步调用确保每个领域服务在调用下一个之前完成工作，消除竞态条件

**缺点**：
- 复杂度随工作流的语义复杂度线性增长
- 对于复杂工作流，前控制器会变得和中介器一样复杂
- 错误条件下性能较差，因为每个服务都必须展开调用链
- 缺少编排器引入更多回调协调

**适用场景**：简单工作流、不需要频繁处理错误条件、追求较高并行扩展能力。

---

### 3.3 Fairy Tale Saga(seo) 模式

**（同步 + 最终一致性 + 编排）**

童话故事提供简单易循的愉快情节，该模式因此得名。

**工作原理**：
- 编排器负责协调请求、响应和错误处理
- 编排器不负责管理事务——每个领域服务保留自己的事务责任
- 编排器可以管理补偿调用，但无需在活动事务内进行

**评分**：
| 维度 | 评级 |
|------|------|
| 耦合度 | 高 |
| 复杂度 | 非常低 |
| 响应性/可用性 | 中等 |
| 可扩展性/弹性 | 高 |

**优点**：
- 最方便的选择（编排、同步）与最宽松的限制（最终一致性）组合
- 最大吸引力在于缺乏全局事务——每个领域服务管理自己的事务行为
- 低复杂度，简单易行，结局美好
- 编排器无需维护太多时间敏感状态，负载均衡更好

**缺点**：
- 两维度仍处于最大耦合（同步通信 + 编排协调）
- 需要接受最终一致性带来的数据暂时不同步

**适用场景**：可接受最终一致性的场景，是许多微服务架构中的常见选择。

---

### 3.4 Time Travel Saga(sec) 模式

**（同步 + 最终一致性 + 编舞）**

从时间角度看一切都是解耦的，每个服务拥有自己的事务上下文，工作流一致性是逐步实现的。

**工作原理**：
- 每个服务接收请求、执行操作，然后将请求转发给下一个服务
- 可以实现**责任链（Chain of Responsibility）**设计模式或**管道与过滤器（Pipes and Filters）**架构风格
- 适用于单向步骤序列的工作流
- 每个服务"拥有"自己的事务性

**评分**：
| 维度 | 评级 |
|------|------|
| 耦合度 | 中等 |
| 复杂度 | 低 |
| 响应性/可用性 | 中等 |
| 可扩展性/弹性 | 高 |

**优点**：
- 适合"发射后不管（fire and forget）"类工作流：电子数据摄入、批量事务等
- 耦合度中等，去除了事务耦合
- 提供极高的可扩展性和弹性

**缺点**：
- 工作流复杂度与编舞方案可行性成反比——越复杂越难管理
- 缺少全局事务协调，需额外努力同步数据
- 复杂错误处理会严重影响响应性

**适用场景**：高吞吐量的简单单向工作流。

---

### 3.5 Fantasy Fiction Saga(aao) 模式

**（异步 + 原子 + 编排）**

此模式名称意为"幻想小说"——虽然这种组合存在，但实用性存疑。

**工作原理**：
- 类似 Epic Saga，但采用异步通信
- 编排器必须跟踪所有进行中事务的状态
- 异步性破坏了串行假设，引入死锁、竞态条件等并行系统挑战

**评分**：
| 维度 | 评级 |
|------|------|
| 耦合度 | 高 |
| 复杂度 | 高 |
| 响应性/可用性 | 低 |
| 可扩展性/弹性 | 低 |

**问题示例**：
- 事务工作流 Alpha 开始时，因异步性，事务工作流 Beta 可能同时开始
- 编排器必须跟踪多个待处理事务的状态
- 工作流 Gamma 可能依赖于尚未完成的 Alpha 的结果——如何建模？

**优点**：
- 试图通过异步提高 Epic Saga 的性能

**缺点**：
- 耦合度高且难以协调
- 设计复杂、调试困难、运维复杂
- 在高事务性系统中几乎不可能实现高可扩展性
- 通常被迫使用该模式是因为错误地尝试在保持事务性同时提高 Epic Saga 性能

**更好的替代方案**：通常应选择 Parallel Saga(aeo)，将原子一致性切换为最终一致性。

---

### 3.6 Horror Story(aac) 模式

**（异步 + 原子 + 编舞）**

最差的组合——名副其实的"恐怖故事"。

**工作原理**：
- 没有中介器管理跨多个服务的事务一致性
- 使用异步通信
- 每个领域服务必须跟踪多个待处理事务的撤销信息（可能因异步性而乱序）
- 错误条件下各编舞服务需相互协调

**典型恐怖场景**：事务 Alpha 启动，待处理时事务 Beta 也启动。Alpha 的某个调用失败——编舞服务们必须倒序撤销每个（可能乱序的）事务元素。

**评分**：
| 维度 | 评级 |
|------|------|
| 耦合度 | 中等 |
| 复杂度 | 非常高 |
| 响应性/可用性 | 低 |
| 可扩展性/弹性 | 中等 |

**它是如何产生的**（经典的反模式路径）：
1. 架构师从 Epic Saga(sao) 开始
2. 发现复杂工作流导致性能慢
3. 想到异步通信和编舞可以提高性能
4. 孤立地应用这些优化，没有考虑与一致性和协调维度的纠缠
5. 结果：最严格的一致性要求配上最松散的通信和协调方式

**缺点**：
- 组合了最严格的一致性约束（原子性）与最松散的两种风格（异步 + 编舞）
- 错误条件的多样性和复杂性令人望而生畏
- 需要大量的服务间"闲聊"

**更好的替代方案**：Anthology Saga(aec)，去除全局事务性。

---

### 3.7 Parallel Saga(aeo) 模式

**（异步 + 最终一致性 + 编排）**

在传统 Epic Saga 基础上放松两个关键限制：异步通信和最终一致性，使之成为更容易实现的模式。

**工作原理**：
- 使用中介器，适合复杂工作流
- 异步通信提供更好的响应性和并行执行
- 一致性由领域服务负责
- 错误发生时，中介器可异步发送补偿消息

**评分**：
| 维度 | 评级 |
|------|------|
| 耦合度 | 低 |
| 复杂度 | 低 |
| 响应性/可用性 | 高 |
| 可扩展性/弹性 | 高 |

**优点**：
- 低耦合——去除了全局事务耦合、采用异步通信
- 低复杂度——编排让工作流和错误处理设计更简单
- 高可扩展性——隔离事务边界使架构可按领域概念自由扩展
- 高响应性——没有协调事务的瓶颈
- 适合服务间性能差异大的场景

**缺点**：
- 异步通信使时序和同步问题难以解决（竞态条件、死锁、队列可靠性等）
- 缺乏事务性将更多负担放在中介器上

**适用场景**：需要高可扩展性的复杂工作流。

---

### 3.8 Anthology Saga(aec) 模式

**（异步 + 最终一致性 + 编舞）**

与 Epic Saga(sao) 完全对立——最松耦合的模式。

**工作原理**：
- 使用消息队列异步发送消息
- 无编排器，领域服务需包含更多工作流上下文
- 每个服务维护自己的事务完整性
- 可使用**标签耦合（Stamp Coupling）**传递工作流状态

**评分**：
| 维度 | 评级 |
|------|------|
| 耦合度 | 非常低 |
| 复杂度 | 高 |
| 响应性/可用性 | 高 |
| 可扩展性/弹性 | 非常高 |

**优点**：
- 无瓶颈、无耦合阻塞点
- 最高的性能和可扩展性潜力
- 响应性和可扩展性均为所有模式中最佳

**缺点**：
- 高解耦使协调困难，对复杂或关键工作流几乎不可行
- 复杂度高——特别是处理数据一致性错误时
- 不适合复杂工作流

**适用场景**：极高的吞吐量通信、简单或极少错误条件的工作流，如管道与过滤器架构。

## 四、问题清单

本章识别的关键问题：

| # | 问题 | 描述 |
|---|------|------|
| 1 | **缺乏事务隔离（Transaction Isolation）** | 分布式事务存在时，其他服务可能在事务完成前基于中间数据采取了行动（副作用/Side Effects） |
| 2 | **补偿失败（Compensation Failure）** | 架构师和开发者倾向于假设补偿更新总会成功，但实际上补偿更新也可能失败，导致状态不一致 |
| 3 | **响应性差** | 原子分布式事务中，最终用户必须等待所有纠正操作（补偿更新）完成后才能得到响应 |
| 4 | **无法执行回滚** | 某个服务可能无法成功撤销之前的操作，编排器必须有协调代码来处理失败 |
| 5 | **服务锁定问题** | 中介器调用服务更新数据时，其他请求可能依赖第一次请求的结果——是否应锁定参与服务？锁定保证有效性但破坏性能和可扩展性 |
| 6 | **死锁与竞态条件** | 异步通信 + 事务性组合时，多个工作流并行可能导致死锁和竞态条件 |
| 7 | **最终用户被不必要地耦合到业务流程** | 原子分布式事务中，Sysops Squad 专家不得不关心调查是否发送成功——而他们只想处理下一个工单 |
| 8 | **副作用链（Side Effect Chain）** | 撤销事务后，下游服务可能已基于被撤销的数据采取了更多行动（如乌龟叠乌龟，永无止境） |

## 五、解决方案

### 5.1 从补偿更新转向状态管理（最终一致性）

**核心理念**：管理 Saga 的状态而非发出补偿更新。

**实现方式**：
- 使用有限状态机始终追踪 Saga 当前状态
- 通过重试和错误分析异步解决问题
- 若无法自动解决，将错误发送给管理员或监督者进行手动修复

**对比**：

| 方法 | 补偿更新（原子） | 状态管理（最终一致） |
|------|------------------|---------------------|
| 响应性 | 差——用户需等待纠正完成 | 好——用户无需关心后台错误 |
| 数据一致性 | 立即恢复 | 错误时数据可能暂时不同步 |
| 对用户影响 | 大——用户被迫等待错误处理 | 小——系统后台处理错误 |
| 复杂度 | 高——补偿逻辑复杂 | 中——状态机设计需谨慎 |

### 5.2 Saga 状态机的实际应用

以 Sysops Squad 新建问题工单的工作流为例：

```
START → CREATED → ASSIGNED → ACCEPTED → COMPLETED → CLOSED
                                          ↘ REASSIGN ↗
                              COMPLETED → NO_SURVEY → CLOSED
```

**状态转换动作表**：

| 初始状态 | 转换状态 | 转换动作 |
|---------|---------|---------|
| START | CREATED | 分配工单给专家 |
| CREATED | ASSIGNED | 路由工单给指定专家 |
| ASSIGNED | ACCEPTED | 专家修复问题 |
| ACCEPTED | COMPLETED | 发送客户调查 |
| ACCEPTED | REASSIGN | 重新分配给其他专家 |
| REASSIGN | ASSIGNED | 路由工单给指定专家 |
| COMPLETED | CLOSED | 工单 Saga 完成 |
| COMPLETED | NO_SURVEY | 发送客户调查 |
| NO_SURVEY | CLOSED | 工单 Saga 完成 |

**关键设计原则**：
- **NO_SURVEY 状态**：调查服务不可用时，不向用户报错，而是进入 NO_SURVEY 状态，系统后台持续重试
- 每个状态只可能有一种或几种确定的转换路径
- 始终知道当前状态，并能够最终恢复到正确状态

### 5.3 技术实现工具

**注解（Java）/自定义属性（C#）方法**：

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.TYPE)
public @interface Saga {
    public Transaction[] value();
    public enum Transaction {
        NEW_TICKET, CANCEL_TICKET, NEW_CUSTOMER,
        UNSUBSCRIBE, NEW_SUPPORT_CONTRACT
    }
}
```

**用途**：
- 在源码中集中记录和文档化所有 Saga
- 将服务与 Saga 关联（如 `@Saga(Transaction.NEW_TICKET)` 标注在服务入口点上）
- 便于编写 CLI 工具遍历代码库查询 Saga 信息：
  ```bash
  $ ./sagatool.sh NEW_TICKET -services
  -> Ticket Service
  -> Assignment Service
  -> Routing Service
  -> Survey Service
  ```

## 六、关键权衡总结

### 6.1 八种模式总览

| 模式 | 通信 | 一致性 | 协调 | 耦合度 | 复杂度 | 响应性 | 可扩展性 |
|------|------|--------|------|--------|--------|--------|----------|
| Epic Saga(sao) | 同步 | 原子 | 编排 | 非常高 | 低 | 低 | 非常低 |
| Phone Tag(sac) | 同步 | 原子 | 编舞 | 高 | 高 | 低 | 低 |
| Fairy Tale(seo) | 同步 | 最终 | 编排 | 高 | 非常低 | 中 | 高 |
| Time Travel(sec) | 同步 | 最终 | 编舞 | 中 | 低 | 中 | 高 |
| Fantasy Fiction(aao) | 异步 | 原子 | 编排 | 高 | 高 | 低 | 低 |
| Horror Story(aac) | 异步 | 原子 | 编舞 | 中 | 非常高 | 低 | 中 |
| Parallel Saga(aeo) | 异步 | 最终 | 编排 | 低 | 低 | 高 | 高 |
| Anthology Saga(aec) | 异步 | 最终 | 编舞 | 非常低 | 高 | 高 | 非常高 |

### 6.2 原子事务 + 补偿更新 vs 状态管理 + 最终一致性

| | 原子事务 + 补偿更新 | 状态管理 + 最终一致性 |
|---|---|---|
| **优点** | 所有数据恢复到之前状态；允许重试和重启 | 响应性好；对最终用户影响小 |
| **缺点** | 无事务隔离；补偿可能产生副作用；补偿可能失败；最终用户响应性差 | 错误时数据可能不同步；最终一致性可能需要时间 |

### 6.3 选择指南

| 场景 | 推荐模式 |
|------|---------|
| 简单工作流 + 需要事务一致性 | Epic Saga(sao) |
| 简单单向工作流 + 极高吞吐量 | Time Travel(sec) 或 Anthology Saga(aec) |
| 可接受最终一致性 + 复杂工作流 | Fairy Tale(seo) 或 Parallel Saga(aeo) |
| 需要高可扩展性 + 复杂工作流 | Parallel Saga(aeo) |
| 简单工作流 + 追求高并行扩展 | Phone Tag(sac) |
| **绝对避免** | Horror Story(aac)、Fantasy Fiction(aao) |

**核心原则**：
- 原子事务是分布式架构中最困难的问题之一，范围越广越糟糕
- 架构师不应因为熟悉而默认选择 Epic Saga——应评估是否有更合适的模式
- 许多现实场景并非事务性的（如星巴克不使用两阶段提交）
- 模式的存在是对共性的认知，**不代表问题已被优雅解决**

## 七、Sysops Squad 案例

### 7.1 场景背景

Sysops Squad 专家通过移动应用完成工作后将工单标记为"完成"。该工作流涉及：
- Ticket Service（工单服务）：更新工单状态
- Survey Service（调查服务）：发送客户满意度调查
- Analytics Service（分析服务）：异步收集工单分析数据

### 7.2 Epic Saga 方案暴露的问题

**问题一：副作用（Side Effects）**

正常流程：
1. 专家标记工单完成 → Ticket Orchestrator 接收请求
2. 同步调用 Ticket Service 将状态改为 "complete"
3. Ticket Service 异步发送分析数据到队列 → Analytics Service 处理
4. 调用 Survey Service 发送调查

异常流程（Survey Service 不可用）：
- 补偿更新需要撤销 Ticket Service 的状态变更
- 但 Analytics Service **已经处理了该工单的分析数据**——这是副作用
- 即使让 Ticket Service 再发消息让 Analytics Service 忽略该数据，也需要极其复杂的代码和时序逻辑
- 更糟的是：Analytics Service 可能已基于该数据执行了进一步的下游操作

**问题二：补偿失败（Compensation Failure）**

- Ticket Orchestrator 向 Ticket Service 发出补偿更新
- Ticket Service 返回错误——补偿更新失败
- 工单状态仍是 "complete"，重试可能又遇到 "Ticket already marked as complete" 错误
- 系统处于不一致状态，不知道应向最终用户发送什么响应

**问题三：响应性差**

- 原子分布式事务中，如果发生错误，最终用户必须等待所有补偿更新完成后才能收到错误响应
- Sysops Squad 专家被迫等待，无法立即处理下一个工单

**问题四：最终用户被不必要地耦合**

- 工单完成的业务流程中包含了发送调查
- 在单体架构中这发生在事务内
- 但专家实际上不关心调查是否发送成功——他们只想处理下一个工单
- **原子分布式事务使最终用户不必要地语义耦合到业务流程**

### 7.3 推荐方案

放弃 Epic Saga(sao)，改用 **Fairy Tale Saga(seo)** 或 **Parallel Saga(aeo)**：

- 采用异步最终一致性
- 错误发生时进入特殊状态（如 NO_SURVEY），后台自动处理
- 最终用户（专家）不受错误影响，可以立即处理下一个工单
- 响应性更好，系统在后台处理纠正操作

## 八、核心启示

1. **不要因熟悉而默认选择 Epic Saga**——它在分布式架构中会引入大量偶然复杂性。
2. **分布式事务不提供隔离性**——在事务完成前，其他服务可能已基于中间数据采取了行动。
3. **补偿更新不是万能的**——它们可能失败、产生副作用链，并且降低最终用户的响应性。
4. **最终一致性 + 状态管理通常是更好的选择**——对最终用户影响小，系统复杂度可控。
5. **架构决策不能孤立看待**——看似提升性能的异步通信和编舞，在不考虑一致性和协调维度纠缠的情况下，可能导致最差的 Horror Story 模式。
6. **"模式是对共性的认知，不代表问题已被优雅解决"**——认识到某个模式的存在并不等同于拥有了干净的解决方案。
