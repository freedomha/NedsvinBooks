# 第九章：数据所有权与分布式事务

## 章节概述

一旦数据在分布式架构中被拆分，就必须将其重新组合以使系统正常工作。这意味着需要确定哪些服务拥有哪些数据、如何管理分布式事务，以及服务如何访问它们需要但不拥有的数据。本章探讨了在分布式架构中将数据重新组合的所有权和事务方面的关键问题。

**核心挑战**：服务对数据表的写入权限可能重叠，导致单一所有权规则失效，需要多种技术手段来解决共同所有权和联合所有权问题。

---

## 核心概念与定义

### 数据所有权的基本规则

**核心规则**：对表执行写入操作的服务拥有该表的所有权。

这条规则在**单一所有权**场景中运作良好，但在以下场景中变得复杂：
- **联合所有权（Joint Ownership）**：多个服务对同一张表执行写入操作
- **共同所有权（Common Ownership）**：大多数或所有服务都对同一张表执行写入操作

### ACID 事务

ACID 事务是在单个原子工作单元中执行多个数据库更新，要么全部提交，要么全部回滚。

| 属性 | 说明 |
|------|------|
| **原子性（Atomicity）** | 事务中的所有更新必须全部提交或全部回滚 |
| **一致性（Consistency）** | 事务过程中数据库不会处于不一致状态或违反完整性约束 |
| **隔离性（Isolation）** | 未提交的事务数据在事务完成前对其他事务不可见 |
| **持久性（Durability）** | 事务提交成功后，数据更新是永久的，不受后续系统故障影响 |

### BASE 事务（分布式事务）

分布式事务不支持 ACID 属性，而是支持 BASE：

| 属性 | 说明 |
|------|------|
| **基本可用（Basic Availability）** | 分布式事务中的所有服务或系统预期可参与事务 |
| **软状态（Soft State）** | 分布式事务进行中时，原子业务请求的状态尚未完成或未知 |
| **最终一致性（Eventual Consistency）** | 给予足够时间，分布式事务的所有部分将成功完成，数据最终同步 |

> **关键洞见**：在化学中，酸（acid）和碱（base）是相反的；在软件架构中，ACID 事务与 BASE 事务同样是对立的。

## 问题清单

### 问题1：单一数据所有权问题
- 当只有一个服务写入表时，所有权明确
- 但其他服务可能需要对该表进行只读访问
- 如何处理跨服务的数据读取？（见第十章）

### 问题2：共同所有权问题
- 大多数或所有服务需要写入同一张表（如审计表 Audit）
- 无法直接判断谁应该拥有该表
- 共享数据库方案会重新引入数据共享问题（变更控制、连接耗尽、可扩展性、容错性）

### 问题3：联合所有权问题
- 同一领域内的多个服务对同一张表执行写入操作
- 涉及数据一致性、性能、服务依赖等复杂权衡

### 问题4：分布式事务不支持 ACID
- 原子性：每个服务独立提交，只覆盖整体请求的一部分
- 一致性：一个服务失败导致数据不同步；跨服务无法应用外键约束
- 隔离性：服务提交后数据立即对其他请求可见
- 持久性：单个服务提交不保证整个业务事务中的数据永久性

### 问题5：最终一致性的实现与错误处理
- 如何选择适当的最终一致性模式？
- 错误发生时如何处理（补偿事务、死信队列）？
- 如何在响应性与一致性之间权衡？

---

## 解决方案

### 一、数据所有权问题的解决方案

#### 1.1 单一所有权（Single Ownership）

**策略**：直接将表分配给唯一写入的服务，形成紧密的有界上下文。

**示例**：Wishlist Service 写入 Wishlist 表 → Wishlist Service 拥有 Wishlist 表。

**建议**：优先解决单一所有权场景，为处理更复杂的场景扫清障碍。

---

#### 1.2 共同所有权的解决方案

**策略**：创建一个专属服务作为数据的唯一所有者。

**具体做法**：
- 创建新服务（如 Audit Service）作为唯一可读写该表的服务
- 其他服务通过消息传递发送数据给专属服务

**通信方式选择**：
| 场景 | 推荐方式 |
|------|----------|
| 不需要返回信息或确认 | 异步发后即忘消息 + 持久化队列 |
| 需要返回确认号或数据库键 | REST、gRPC 或请求-回复消息（伪同步） |

**使用持久化队列的好处**：
- 消息存储在磁盘上，保证投递
- 服务或代理故障时不会丢失消息

---

#### 1.3 联合所有权的解决方案

##### 方案A：表拆分技术（Table Split Technique）

**原理**：将单张表拆分为多张表，每个服务拥有自己负责的数据部分。

**步骤**：
1. 创建新的分离表（如从 Product 表拆分出 Inventory 表）
2. 将现有数据预填充到新表
3. 从原表中删除对应列
4. 建立服务间通信以保持数据一致性

**示例 DDL**：
```sql
CREATE TABLE Inventory (product_id VARCHAR(10), inv_cnt INT);
INSERT INTO Inventory VALUES (product_id, inv_cnt)
  AS SELECT product_id, inv_cnt FROM Product;
COMMIT;
ALTER TABLE Product DROP COLUMN inv_cnt;
```

**同步挑战**：
- 新增产品时：Catalog Service 生成产品 ID 插入 Product 表，然后通知 Inventory Service
- 删除产品时：Catalog Service 先删除 Product 记录，再通知 Inventory Service 删除对应库存行
- 关键权衡：CAP 定理——选择一致性还是可用性？

**权衡总结**：

| 优势 | 劣势 |
|------|------|
| 保持有界上下文 | 表结构需要改动和重组 |
| 实现单一数据所有权 | 可能存在数据一致性问题 |
| | 无跨表更新的 ACID 事务 |
| | 数据同步困难 |
| | 可能出现表间数据复制 |

---

##### 方案B：数据域技术（Data Domain Technique）

**原理**：创建共享数据域，多个服务共同拥有共享表，形成更广泛的有界上下文。

**特点**：
- 服务间完全独立，Catalog Service 可独立增删产品，Inventory Service 可独立调整库存
- 不需要服务间协调

**使用前需重新评估**：为什么需要分离的服务？（可扩展性差异、容错需求、吞吐量差异、代码波动性隔离）

**问题**：
- 数据模式变更需要多服务协调（增加开发工作量、测试范围、部署风险）
- 写入责任治理困难

**权衡总结**：

| 优势 | 劣势 |
|------|------|
| 良好的数据访问性能 | 数据模式变更涉及更多服务 |
| 无可扩展性和吞吐量问题 | 测试范围扩大 |
| 数据保持一致 | 写入责任治理复杂 |
| 无服务依赖 | 部署风险增加 |

---

##### 方案C：委托技术（Delegate Technique）

**原理**：指定一个服务为表的唯一所有者（委托人），其他服务通过委托服务执行写入操作。

**选择委托服务的两种策略**：

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| **主域优先级（Primary Domain Priority）** | 将所有权分配给最能代表数据主域的服务（执行最多 CRUD 操作的服务） | 一般推荐 |
| **运维特性优先级（Operational Characteristics Priority）** | 将所有权分配给需要更高运维特性（性能、可扩展性、可用性）的服务 | 高频操作场景 |

**通信方式对比**：

| 方式 | 优势 | 劣势 |
|------|------|------|
| 同步通信 | 数据一致性保证 | 性能较低 |
| 异步通信 | 性能更好 | 仅最终一致性，无更新保证，数据完整性风险 |

**建议**：通常推荐主域优先级选项，配合内存缓存副本或分布式缓存来解决性能和容错问题。

**权衡总结**：

| 优势 | 劣势 |
|------|------|
| 形成单一表所有权 | 服务耦合度高 |
| 良好的数据模式变更控制 | 非所有者写入性能低 |
| 对非所有者抽象数据结构 | 非所有者无法执行原子事务 |
| | 非所有者服务容错性低 |

---

##### 方案D：服务合并技术（Service Consolidation Technique）

**原理**：将多个表所有者（服务）合并为单个合并服务，将联合所有权转为单一所有权。

**解决**：服务依赖问题和联合所有权问题。

**新问题**：
- 服务粒度更粗 → 测试范围增大
- 部署风险增加（修改一处可能影响整个服务）
- 容错性降低（服务某部分失败导致全部失败）
- 可扩展性受影响（不活跃的功能也不得不随高频功能一起扩展）

**权衡总结**：

| 优势 | 劣势 |
|------|------|
| 保持原子事务 | 可扩展性粒度变粗 |
| 良好的整体性能 | 容错性降低 |
| | 部署风险增加 |
| | 测试范围扩大 |

示例场景的最终选择（基于图 9-1 的 Wishlist/Catalog/Inventory/Audit 示例）：

| Product 表（联合所有权） | 委托技术，Catalog Service 为单一所有者 |

### 三、最终一致性模式

#### 3.1 后台同步模式（Background Synchronization Pattern）

**原理**：使用独立的外部服务或进程周期性检查数据源并保持同步。

**实现方式**：
- 批量作业（夜间运行）
- 定期唤醒服务（如每小时）

**数据变更检测方式**：事件流、数据库触发器、源表与目标表数据对比。

**适用场景**：
- 数据不需要立即保持同步的场景（如客户取消订阅后，合同和账单信息存在多几个月也无妨）
- 封闭的异构系统间同步（如订单系统与发票系统）

**权衡总结**：

| 优势 | 劣势 |
|------|------|
| 服务解耦 | 数据源耦合 |
| 响应性好（用户无需等待） | 实现复杂 |
| | 破坏有界上下文 |
| | 业务逻辑可能重复 |
| | 最终一致性达成慢 |

> **关键警告**：该模式破坏有界上下文，不适合微服务等需要紧密有界上下文的分布式架构。因为后台进程必须有所有表的写入权限，实际上共享了数据所有权。

---

#### 3.2 编排请求模式（Orchestrated Request-Based Pattern）

**原理**：在业务请求处理期间（用户等待时）同步所有数据源，使用编排器管理整个分布式事务。

**编排器职责**：了解业务流程、参与者、组播逻辑、错误处理、合约所有权。

**两种实现方式**：

| 方式 | 特点 | 问题 |
|------|------|------|
| 主服务兼编排器 | 不增加新服务 | 职责过载、紧耦合、同步依赖 |
| 独立编排服务（推荐） | 解放主服务 | 增加网络跳转和服务调用 |

**业务流程示例**（客户取消订阅）：
1. Unsubscribe Orchestrator 接收请求
2. 同步调用 Customer Profile Service 删除用户
3. 收到确认后，并行调用 Support Contract 和 Billing Payment Service
4. 所有服务确认后，响应客户端

**错误处理复杂性**：

当部分服务成功、部分失败时，编排器面临决策：
1. 重试失败的服务？
2. 执行补偿事务回滚已成功的操作？
3. 告知用户出错并尝试修复？
4. 忽略错误？

**推荐：补偿事务**——回滚已成功的操作。但这要求编排器拥有重新插入数据的完整信息，且补偿事务本身也可能失败，需要人工介入。

**权衡总结**：

| 优势 | 劣势 |
|------|------|
| 服务解耦 | 响应速度较慢 |
| 数据一致性强 | 错误处理复杂 |
| 原子业务请求 | 通常需要补偿事务 |

---

#### 3.3 事件模式（Event-Based Pattern）

**原理**：使用事件和异步发布/订阅消息模型，服务监听并响应事件。这是微服务和事件驱动架构中最流行、最可靠的最终一致性模式。

**工作流程**：
1. Customer Profile Service 接收取消订阅请求，删除数据
2. 发布"customer unsubscribed"事件到消息主题或事件流
3. Support Contract 和 Billing Payment Service 监听事件并处理
4. Customer Profile Service 不需要等待其他服务完成即可响应客户

**实现要点**：
- 标准 pub/sub 消息（ActiveMQ、RabbitMQ、AmazonMQ）：使用持久订阅者，确保消息不丢失
- 事件流（Apache Kafka）：消息持久化并在主题中保留合理时间

**错误处理**：
- 服务不可用：持久订阅者确保服务恢复后接收消息
- 服务处理失败：消息代理重试一定次数后发送到死信队列（DLQ）
- 死信队列：自动进程尝试修复，无法修复则转人工处理

**权衡总结**：

| 优势 | 劣势 |
|------|------|
| 服务解耦 | 错误处理复杂 |
| 数据一致性时效性好 | |
| 响应速度快 | |

---

### 四、三种最终一致性模式对比

| 维度 | 后台同步 | 编排请求 | 事件模式 |
|------|----------|----------|----------|
| 一致性达成速度 | 慢 | 快 | 较快 |
| 服务解耦 | 好（服务间） | 好（服务间） | 好 |
| 数据源耦合 | 高 | 低 | 低 |
| 响应性 | 好 | 差 | 好 |
| 错误处理 | 简单 | 复杂（需补偿事务） | 复杂（需死信队列） |
| 有界上下文 | 破坏 | 保持 | 保持 |
| 适用场景 | 异构封闭系统 | 需强一致性的业务请求 | 微服务、事件驱动架构 |

## 关键权衡

### 1. 一致性 vs 可用性（CAP 定理）

分布式架构必须进行网络分区，CAP 定理表明一致性和可用性只能取其一。

### 2. 同步 vs 异步通信

| 同步 | 异步 |
|------|------|
| 更好的数据一致性 | 更好的性能 |
| 牺牲性能 | 牺牲数据一致性 |
| 需要确认时使用 | 不需要确认时使用 |

### 3. 服务粒度 vs 数据所有权

| 细粒度服务 | 粗粒度服务 |
|------------|------------|
| + 更好的可扩展性 | + 更简单的数据所有权 |
| + 更好的容错性 | + 保持原子事务 |
| + 更小的测试范围 | + 更好的性能 |
| - 数据所有权复杂 | - 部署风险大 |
| - 服务间通信开销 | - 可扩展性受限 |

### 4. 委托技术的两种优先级

| 主域优先级 | 运维特性优先级 |
|------------|----------------|
| 按业务领域 CRUD 频次分配 | 按性能/可扩展性需求分配 |
| 更好的领域建模 | 更好的运维特性 |
| 一般推荐此方式 | 适用于高频操作场景 |

### 5. 有界上下文保护 vs 数据访问便利性

- 保护有界上下文：利于变更控制、独立部署、测试隔离
- 便利数据访问：利于性能、简化开发
- 需要在两者间权衡

## Sysops Squad 案例

### 案例背景

Sysops Squad 团队在分解单体数据库的同时，开始形成服务与数据之间的有界上下文，分配表所有权。

### 关键场景1：专家资料表（Expert Profile Table）所有权冲突

**冲突描述**：
- **Sydney 观点**：Ticket Assignment Service 频繁查询专家资料表（按位置和技能匹配），应将表分配给它
- **Addison 观点**：User Maintenance Service 负责维护专家信息的更新，应该是表的拥有者
- **约束**：Dana 规定服务不能连接到多个数据库或模式
- **解决方案**：按照"写入者拥有"规则，User Maintenance Service 拥有专家资料表

**ADR：单一表所有权用于有界上下文**
- **决策**：当只有一个服务写入表时，该服务拥有该表。其他有界上下文中的服务不能直接访问该表的数据库或模式。
- **后果**：需要只读访问的服务可能面临性能和容错问题（详见第十章）。

### 关键场景2：调查表（Survey Table）联合所有权

**冲突描述**：
- Ticket Completion Service 写入：工单完成时间戳、执行任务的专家
- Survey Service 写入：发送调查的时间戳、调查结果
- 两个服务都需要写入同一张 Survey 表 → 联合所有权

**方案分析**：
| 方案 | 是否可行 | 原因 |
|------|----------|------|
| 表拆分 | 否 | Survey 表结构不适合拆分 |
| 共同数据域 | 否 | Ticket Completion Service 已连接 ticketing 数据域，不能连接多个模式 |
| 委托技术 | **是** | Ticket Completion Service 在通知 Survey Service 启动调查流程时，将数据作为消息负载传递 |

**ADR：Survey Service 拥有 Survey 表**

- **决策**：Survey Service 是 Survey 表的唯一所有者。Ticket Completion Service 通知 Survey Service 时，将必要数据作为事件负载传递，消除对 Survey 表的直接写入需求。
- **后果**：
  - 工单完成信息需作为消息负载传递
  - 调查记录的创建从工单完成流程中分离，由 Survey Service 独立处理

### 关键启示

1. **数据库团队和开发团队必须协作**：数据和代码的拆分需要双方紧密配合
2. **服务不允许连接多个数据库/模式**：这是数据库团队制定的关键约束
3. **写入即所有权**：无论有多少服务需要读取，只有执行写入的服务拥有表所有权
4. **委托技术结合事件驱动**：利用已有的事件通知通道传递数据，消除联合写入需求

---

## 总结

本章系统性地阐述了分布式架构中数据所有权和分布式事务的核心挑战与解决方案。关键要点：

1. **数据所有权的基础规则是"写入者拥有"**，但联合所有权和共同所有权使这条规则复杂化
2. **共同所有权**通过创建专属服务解决；**联合所有权**有四种主要技术：表拆分、数据域、委托、服务合并
3. **分布式事务不支持 ACID**，而是采用 BASE 模型（基本可用、软状态、最终一致性）
4. **三种最终一致性模式**各有适用场景：后台同步适合异构系统，编排请求适合需要强一致性的业务，事件模式适合微服务
5. **没有任何方案是完美的**，每种技术都有其权衡——架构师需要在一致性、可用性、性能、耦合度之间做出明智抉择
