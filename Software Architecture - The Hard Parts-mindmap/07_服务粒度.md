# 第7章 服务粒度 (Service Granularity)

## 一、章节概述

第7章聚焦于分布式架构中一个核心难题：**如何确定服务的正确粒度（大小）**。架构师和开发团队经常在"拆还是不拆"之间挣扎。本章提出了一套系统化的分析方法——通过**粒度分解器（Granularity Disintegrators）**和**粒度整合器（Granularity Integrators）**两种对立力量来客观评估服务粒度决策，避免主观臆断。

核心观点：
- 粒度不是由类的数量或代码行数决定的，而是由**服务做什么**决定的
- 粒度的秘诀在于**分解器与整合器之间的平衡**
- 架构决策应通过与业务干系人协作分析权衡来做出的

---

## 二、核心概念与定义

### 2.1 模块化 (Modularity) vs 粒度 (Granularity)

| 概念 | 定义 | 关注点 |
|------|------|--------|
| 模块化 (Modularity) | 将系统拆分为独立的部分 | **是否拆分**以及**如何拆分**（见第3章） |
| 粒度 (Granularity) | 这些独立部分的**大小** | 服务应该多大/多小 |

分布式系统中的大多数问题不是源于模块化，而是源于**粒度**。

### 2.2 衡量粒度的客观指标

由于代码行数和类数量受个人编码风格影响甚大，作者推荐两个相对客观的指标：

1. **语句数 (Number of Statements)**：一个语句是源代码中一个完整的动作，通常以分号（Java/C/C++/Go/JavaScript）或换行符（Python/F#）终止
2. **公开接口/操作数量 (Number of Public Interfaces/Operations)**���服务暴露的入口点数量

### 2.3 粒度分解器与粒度整合器

两种对立的力量共同决定服务粒度：

| 类型 | 核心问题 | 作用 |
|------|----------|------|
| **粒度分解器** | "什么时候应该考虑将服务拆分成更小的部分？" | 推动拆分 |
| **粒度整合器** | "什么时候应该考虑将服务合并在一起？" | 推动合并/保持不拆 |

常见错误：开发团队**过度关注分解器而忽略整合器**。正确的粒度来自于这两种力量达到的**平衡点**。

## 三、粒度分解器 (Granularity Disintegrators)

六种推动服务拆分的主要驱动力：

### 3.1 服务范围与功能 (Service Scope and Function)

**核心问题**：服务是否做了太多不相关的事情？

两个分析维度：
- **内聚性 (Cohesion)**：服务中各个操作之间的关联程度和方式
- **组件大小**：服务中所有类的语句总数或公开入口点数量

**案例分析**：

| 场景 | 内聚性 | 是否适合拆分 |
|------|--------|--------------|
| 通知服务：SMS + Email + 邮寄信件 | 高内聚（都属于"通知客户"） | **不适合**单凭功能拆分 |
| 客户服务：档案管理 + 偏好设置 + 用户评论 | 低内聚（属于更宽泛的"客户"范畴） | **适合**拆分 |

**关键教训**："单一职责"是高度主观的——通知客户是一个职责还是三个？单凭功能拆分是不够的，需要结合其他分解器。

**命名测试**：如果拆分后剩余功能难以用一个好的自描述名称命名，说明拆分方式有问题。例如：
- ❌ `Notification Service → Email Service + Other Notification Service`
- ❌ `Notification Service → Email Service + Non-Email Service`
- ✅ `Notification Service → Email Service + SMS Service + Letter Service`

### 3.2 代码变更率 (Code Volatility)

**核心问题**：变更是否只影响服务的一部分？

也称为**基于易变性的分解 (Volatility-based Decomposition)**。通过源代码版本控制系统客观测量代码变更频率。

**案例：通知服务**
- SMS通知：平均每6个月变更一次
- Email通知：平均每6个月变更一次
- 邮寄信件通知：**平均每周变更一次**

**分析**：
- 作为单一服务：邮件信件代码的任何变更都需要测试和重新部署整个服务（含SMS和Email）
- 影响：测试范围扩大、部署风险增加、SMS和Email功能在部署时可能不可用
- **解决方案**：拆分为"电子通知服务"和"邮寄信件通知服务"，将频繁变更隔离到独立的小服务中

**收益**：
- 测试范围显著缩小
- 部署风险降低
- 变更时不影响其他功能

### 3.3 可扩展性与吞吐量 (Scalability and Throughput)

**核心问题**：服务的不同部分是否需要不同的扩展级别？

通过客观衡量服务不同功能的可扩展性需求来判断是否拆分。

**案例：通知服务**
- SMS通知：220,000条/分钟
- Email通知：500条/分钟
- 邮寄信件通知：1条/分钟

**分析**：
- 作为单一服务：Email和邮寄信件功能被**不必要地**扩展到SMS的水平
- 影响：成本增加、弹性降低（MTTS—平均启动时间受影响）
- **解决方案**：拆分为三个独立服务，各自独立扩展

### 3.4 容错性 (Fault Tolerance)

**核心问题**：是否存在导致服务中关键功能失败的故障？

**案例：通知服务**
- Email功能持续出现内存不足(out-of-memory)问题，导致致命崩溃
- 由于是单一服务，崩溃导致SMS和邮寄信件处理也一起宕机

**解决方案**：拆分为三个独立服务（SMS、Email、Letter），Email崩溃不影响其他两个。

**重要注意事项**：拆分时要确保剩余功能具有强内聚性。
- ❌ Email Service + SMS-Letter Service（内聚性弱，名称糟糕）
- ✅ Email Service + SMS Service + Letter Service（每个都有好名字，内聚性强）

**规则**：无论基于什么分解器拆分，始终检查"剩余"功能是否能形成强内聚。

### 3.5 安全性 (Security)

**核心问题**：服务的某些部分是否需要比其他部分更高的安全级别？

**常见陷阱**：只考虑数据存储安全，而忽略了**数据访问方式**的安全。

**案例：客户档案服务**
- 功能1：基本档案维护（姓名、地址等）
- 功能2：信用卡信息维护

**风险**：虽然信用卡数据可能被保护，但访问不安全——访问服务获取客户姓名的人可能也能访问信用卡功能。

**解决方案**：拆分为两个独立服务
- 客户档案服务（基本档案维护）
- 信用卡服务（信用卡信息维护）

将信用卡操作隔离到单一目的的服务中，可以从服务级别进行更精细的访问控制。

### 3.6 可扩展性 (Extensibility)

**核心问题**：服务是否总是需要扩展以添加新的上下文？

**案例：支付服务**
- 当前支付方式：信用卡、礼品卡、PayPal
- 未来需求：奖励积分、商店积分、ApplePay、SamsungPay等

**分析**：
- 单一服务：每次新增支付方式需要测试整个支付服务、重新部署所有支付功能
- 影响：测试范围大、部署风险高、添加新功能困难
- **解决方案**：拆分为独立服务（信用卡处理、礼品卡处理、PayPal交易处理），新增支付方式只需开发、测试、部署一个新服务

**使用建议**：
- ✅ 支付处理：未来很可能增加新支付方式 → 应该拆分
- ❌ 通知服务：不太可能不断扩展通知方式 → 不必拆分
- **策略**：仅在可以确认上下文功能会持续扩展时才使用此驱动因素，否则等待模式形成后再决策

## 四、粒度整合器 (Granularity Integrators)

四种推动服务合并（或不拆分）的主要驱动力：

### 4.1 数据库事务 (Database Transactions)

**核心问题**：分离的服务之间是否需要ACID事务？

**案例：客户资料服务 + 密码服务**

| 方面 | 分析 |
|------|------|
| 拆分优势 | 安全性更好——密码操作可从服务级别限制访问 |
| 拆分劣势 | 注册新客户时无法使用ACID事务 |
| 问题场景 | 档案服务插入档案数据并提交 → 密码服务插入失败 → 数据不一致 |
| 结果 | 需要复杂且容易出错的事务补偿机制（见第11章事务Saga模式） |

**决策准则**：如果从业务角度看需要原子性的ACID事务，应将服务合并为一个。

**架构决策模式**：向业务干系人提出如下权衡问题：
> "拆分服务可以隔离频繁变更，提高敏捷性，但会失去数据库事务的数据一致性。哪个更重要？"

### 4.2 工作流与编排 (Workflow and Choreography)

**核心问题**：服务之间是否需要相互通信？

服务间通信（也称为东西向通信）在细粒度服务中可能会增加到产生负面影响的程度。

**影响一：容错性降低**

多个服务形成传递依赖。例如：Service C宕机 → 所有依赖C的服务都不可用。

**悖论**：容错性是分解器之一，但当拆分的服务需要相互通信时，从业务请求的角度看，容错性并没有真正提升。如果功能紧密耦合并相互依赖，考虑保持服务在一起。

**影响二：性能与响应性下降**

**案例**：客户服务拆分为5个独立服务（A~E）
- 假设每次请求有300ms的网络和安全延迟
- 通过编排检索所有客户信息需要5跳 → **共1500ms额外延迟**
- 合并为一个服务可以消除这些延迟

**决策准则**：
- 计算需要服务间通信的请求比例
- 评估请求的关键性

| 场景 | 建议 |
|------|------|
| 30%请求需要通信 + 70%纯原子请求 | 可能保持分离 |
| 70%请求需要通信 + 30%纯原子请求 | 考虑合并 |
| 关键请求（需要极快响应）落在需通信的30%中 | 考虑合并 |

**影响三：可靠性与数据完整性**

分散服务各自提交事务，部分成功部分失败导致数据不一致：
- 需要补偿事务回滚
- 需要状态标记来追踪事务进度
- **非常混乱的局面**（详见第11章事务Saga模式）

### 4.3 共享代码 (Shared Code)

**核心问题**：服务之间是否需要共享代码？

**适用场景**：共享领域功能（包含业务逻辑）而非基础设施功能（日志、安全、工具类）。

**三个考量因素**：

| 因素 | 说明 | 阈值示例 |
|------|------|----------|
| **共享领域代码比例高** | 包含业务逻辑的共享代码占比高 | 如果共享代码占集体代码库的40%以上，考虑合并 |
| **共享代码频繁变更** | 频繁变更需要频繁协调多个服务的变更 | 即使共享库不大，频繁变更也驱动合并 |
| **无法版本化的缺陷修复** | 某些业务功能必须同时应用于所有服务 | 频繁出现时应考虑合并 |

**关键区分**：
- ❌ 基础设施代码（日志、审计、认证、授权、监控）→ **不是**合适的整合驱动力
- ✅ 领域共享代码（包含业务逻辑）→ **是**合适的整合驱动力

### 4.4 数据关系 (Data Relationships)

**核心问题**：虽然服务可以拆分，但**数据能拆分吗？**

这是**权衡最少的整合驱动因素**——因为大多数情况下，为了拆分服务而重新组织数据库表实体关系是不现实的。

**案例**：

| 函数 | 表1 | 表2 | 表3 | 表4 | 表5 | 表6 |
|------|-----|-----|-----|-----|-----|-----|
| A | 拥有 | 拥有 | | 拥有 | | 拥有 |
| B | | | 拥有 | | 访问 | |
| C | | | 访问 | | 拥有 | |

拆分成三个服务后：
- Service A 拥有表1、2、4、6
- Service B 拥有表3
- Service C 拥有表5

**问题**：Service B需要访问Service C的表5数据，Service C需要访问Service B的表3数据。

**受限于上下文边界（Bounded Context）**：
- Service B不能直接���询表5（由C拥有）
- Service C不能直接查询表3（由B拥有）
- 结果：需要不断来回的服务间通信

**解决**：基于数据依赖关系，将Service B和C合并为一个服务，避免延迟、容错性和可扩展性问题。

## 五、关键权衡总结

### 5.1 分解器驱动因素总览

| 分解器驱动因素 | 应用原因 |
|----------------|----------|
| 服务范围 | 单一目的服务，紧密内聚 |
| 代码变更率 | 敏捷性（减少测试范围，降低部署风险） |
| 可扩展性 | 降低成本，更快的响应 |
| 容错性 | 更好的整体可用性 |
| 安全访问控制 | 对特定功能更好的安全访问控制 |
| 可扩展性 | 敏捷性（易于添加新功能） |

### 5.2 整合器驱动因素总览

| 整合器驱动因素 | 应用原因 |
|----------------|----------|
| 数据库事务 | 数据完整性和一致性 |
| 工作流 | 容错性、性能和可靠性 |
| 共享代码 | 可维护性 |
| 数据关系 | 数据完整性和正确性 |

### 5.3 权衡协商的模式

架构师不应单方面决策，而应与产品负责人/业务赞助人协作讨论。提出如下形式的权衡声明：

**示例1**：敏捷性 vs 数据一致性
> "拆分服务可以隔离频繁代码变更（提高敏捷性、可测试性、可部署性→更快的上市时间），但会失去数据库事务。哪个更重要？"

**示例2**：安全性 vs 数据一致性
> "保持服务在一起支持数据库事务以确保数据一致性，但敏感的合并服务安全性降低。哪个更重要？"

**示例3**：可扩展性 vs 响应性
> "拆分支付服务提供更好的可扩展性以便添加新支付方式，但增加的工作流会影响支付响应性。哪个更重要？"

## 六、Sysops Squad 案例

### 6.1 工单分配粒度 (Ticket Assignment Granularity)

**背景**：工单创建后需要分配给专家。涉及两个组件：
- **工单分配 (Ticket Assignment)**：根据技能、位置、可用性确定分配给哪位顾问
- **工单路由 (Ticket Routing)**：定位专家、转发工单到移动设备、发送SMS通知

**争论焦点**：
- Taylen（技术主管）：分配算法复杂且频繁变更（每月2-3次），应隔离为独立服务（基于易变性分解）
- Skyler：分配和路由本质是一个功能——分配了就必须路由

**关键分析**：
- 两个功能是**紧密同步绑定**的——一个功能离开另一个无法独立存在
- 如果路由失败，需要回到分配重新选择 → **大量服务间协调**
- 两个功能扩展需求相同，无吞吐量差异
- 两个功能完全相互依赖，容错性不是分解驱动力
- 分离为两个服务需要工作流，导致性能、容错性和可靠性问题

**决策**：合并为**单一工单分配服务**

**ADR关键内容**：
- 工单分配后立即路由，两者紧密绑定且相互依赖
- 两者扩展需求相同，无吞吐量差异
- 分离需要工作流通信，导致性能和可靠性问题
- **代价**：对分配算法的变更需测试和部署整个服务

**架构折中**：在代码中使用**独立的命名空间**分隔分配、路由和共享代码，满足代码组织需求。

### 6.2 客户注册粒度 (Customer Registration Granularity)

**背景**：客户注册涉及四种数据：
- 档案信息（姓名、地址等）
- 信用卡信息（按月计费）
- 密码和安全问题信息
- 购买产品列表

**三种可选方案**：
1. 单一合并服务（所有功能在一起）
2. 四个独立服务（档案、信用卡、密码、产品）
3. 两个服务（档案+产品 vs 信用卡+密码，基于安全敏感/非敏感区分）

**关键权衡**：事务性 vs 安全性

| 方案 | 优势 | 劣势 |
|------|------|------|
| 分离服务 | 更好的安全访问控制 | 不支持"全有或全无"的ACID事务 |
| 合并服务 | 支持原子事务 | 安全性较弱 |

**业务约束**：
- Parker（产品负责人）：**绝对不能**出现有客户记录但没有对应信用卡或密码记录的情况
- Sam（安全专家）：信用卡和密码信息必须安全

**解决方案**：**单一合并服务 + Tortoise安全库双重防护**

**架构 vs 设计的洞察**：
- 安全性可以通过**设计**（使用自定义加密库）来控制，而非必须通过**架构**（拆分为独立部署单元）
- Parker学会了区分：在API网关层和服务网格层使用Tortoise安全库实现双重安全检查

**ADR关键内容**：
- 客户注册和注销需要单一原子工作单元
- 使用Tortoise安全库在API层和服务网格层双重保护，缓解安全风险
- **代价**：任何功能变更都需要测试和部署整个服务，所有功能需一起扩展

**权衡结果**：数据一致性（全有或全无）优先于架构级安全隔离，通过设计层面的安全库来弥补。

## 七、核心启示

1. **去掉主观意见和直觉**：使用分解器和整合器**客观分析**权衡，形成是否拆分服务的坚实依据
2. **不要只关注分解器**：很多团队追求无限细粒度，忽视了整合器的力量
3. **粒度不等于代码行数**：粒度由服务**做什么**而非**多大**决定
4. **架构师是权衡的促进者**：不是控制者，而是引导各方理解并协商权衡
5. **设计与架构的区别**：某些问题可以通过设计解决（如安全库），而不必通过架构解决（拆分服务）
6. **命名测试**：拆分后如果难以命名，说明拆分方式可能有问题
7. **数据是硬约束**：在服务拆分时，数据关系往往是最难处理的整合力量
